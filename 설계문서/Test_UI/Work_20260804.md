## 1. `DM_App_Optic_Measure()` 측정시간 단축 (200ms → 24ms)

### 1-1. 배경

기존 구조는 20샘플 각각 앞에 `DM_HW_Drv_SystemSleep_10ms()`를 넣어 매번 10ms씩 대기(총 200ms). 그런데 LED는 루프 진입 전 딱 1번 켜져서 버스트 내내 계속 켜진 채로 유지되므로, **RC 안정화(100kΩ+22nF, τ≈2.2ms)가 실제로 필요한 건 첫 샘플뿐**이고 나머지 19번의 10ms 대기는 불필요한 여유였음을 확인 (10ms ≈ 4.5τ ≈ 99% 안정화).

### 1-2. 배터리 회복 목적 추가

LED가 켜져 있는 시간 자체가 배터리(CR1632, 내부저항으로 인한 전압강하)에 부담을 주므로, **LED를 끈 직후에도 10uF 캐패시터가 배터리로부터 재충전될 시간**이 필요하다고 판단. 배터리 내부저항 추정치(τ=R×C, 수백 µs~수 ms) 기준으로는 짧아도 되지만, TIM4가 10ms 틱 기반이라는 점을 고려해 **10ms(1틱)로 통일**하기로 결정.

### 1-3. 최종 구조

```
LED ON → RC 안정화 대기 10ms(1회) → 20샘플 연속 측정(~200us×20≈4ms) →
LED/PTR OFF → 회복 대기 10ms(1회)
```

채널당 총 소요시간: **200ms → 약 24ms** (약 8배 단축).

## 2. 대기 루프 재구성 및 ADC 호출량 관리

### 2-1. 문제 발생 — Sample_Load_Wait 재악화 (5:02 → 5:35)

1절의 단축으로 `DM_App_Optic_Measure()`가 훨씬 빨리 끝나게 되면서, `Sample_Load_Wait_Step_Handler()`의 바깥 폴링 루프가 같은 5분(실측 목표)을 채우기 위해 **훨씬 더 많이 반복**하게 됨 — 그 결과 5분간 `DM_HW_Drv_ADC_Read()` 총 호출수가 약 25,000회 → **약 95,000회**로 급증. `ADC_READ_TIME_US`(200us) 보정값의 미세한 오차가 호출수에 비례해 증폭되어, `Sample_Load_Wait`가 기존 5:02에서 **5:35**로 재악화됨.

### 2-2. 대응 — 스틱 체크 폴링 주기 완화

- `DM_App_Main_Sq_Sleep_And_CheckStick_250ms()` 신규 추가(10ms 대기 25회 + 스틱체크 1회 = 250ms).
- `Stick_Insert_Step_Handler`, `Over_Sample_Check_Step_Handler`, `Low_Sample_Check_Step_Handler`, `Reaction_Wait_Step_Handler`의 대기 루프를 기존 10ms짜리 `DM_App_Main_Sq_Sleep_And_CheckStick()`에서 이 250ms 버전으로 교체.
- `Sample_Load_Wait_Step_Handler()`의 내부 측정 사이클은 500ms(49×10ms 순수대기 + 1회 체크) → 최종적으로 **250ms 헬퍼를 4회 호출하는 1초 사이클**로 재구성(T/BT Band 측정 빈도가 0.5초→1초로 됨에 따라 감지 반응속도는 최대 1초 지연되지만 5분 대기 기준 무시 가능 수준).
- 위 재구성으로 5분간 총 ADC 호출수가 약 **18,000회** 수준으로 복귀.
- 더 이상 호출되지 않게 된 원래 10ms짜리 `DM_App_Main_Sq_Sleep_And_CheckStick()` 함수는 삭제.

## 3. TIM4 ARR / `ADC_READ_TIME_US` 재보정

### 3-1. 기존 보정값(ARR=144, 7/31)이 "오염된" 측정 기반이었음을 발견

기존 ARR=144는 `Sample_Load_Wait`(ADC 측정이 섞인 `GetSystemTick()`) 실측으로 보정한 값이었음. `ERR_RUN_TIME`(2분, ADC가 전혀 개입하지 않는 순수 TIM4 tick 카운트)으로 별도 재측정한 결과 **1:56**(4초/3.33% 빠름)이 나와, 144가 "순수 TIM4 주기"가 아니라 ADC untracked-tick 보정과 뒤섞여 산출된 값이었을 가능성이 확인됨.

### 3-2. 재보정

- 1:56@ARR=144 측정치로 역산(`(144+1)×10/9.667≈150` → ARR=149)한 값을 적용, 실물 보드에서 **정확히 2:00** 확인.
- `ADC_READ_TIME_US`도 연속읽기 패턴 기준으로 재실측하여 200 → **220**으로 갱신.

### 3-3. 최종 결과 및 사용자 결정

위 재보정 + 2절의 폴링 재구성을 모두 반영한 `Sample_Load_Wait` 최종 실측: **5:06**(목표 대비 +6초, 약 2%). `ADC_READ_TIME_US`를 225로 더 올려도 이론상 개선폭은 0.09초에 불과함을 계산으로 확인(필요 보정치는 약 553us로 물리적으로 비현실적) → **사용자가 6초 잔여오차를 그대로 수용하기로 결정, 추가 튜닝 중단.**

## 5. LED/배터리 회로 전류 분석

### 5-1. LED 전류 계산 (LTST-C191KGKT 데이터시트 기반)

회로: VDD(2.5V, PWM출력 High) → R(510Ω) → LED Anode→Cathode → GPIO Open-drain(Low 싱크) → GND. LED는 Green(AlInGaP), VF=1.9~2.4V@IF=20mA.

$$I = \frac{V_{DD}-V_F}{R} \approx 1\text{~}2mA$$

데이터시트 전 스펙의 기준 전류(20mA)의 5~10%밖에 안 되는 수준으로, 이전에 확인된 "ADC 1샘플당 57.64카운트(12비트 풀스케일의 1.4%)"라는 낮은 신호 레벨의 근본 원인으로 추정됨. 510Ω이 2.5V 레일 대비 과도하게 큰 값으로 보이나, 실제 저항값 변경(하드웨어 변경 필요)은 이번 세션에서 진행하지 않음.

### 5-2. CR1632 배터리 내부저항 분석

Energizer CR1632 데이터시트의 pulse 테스트(400Ω/6.8mA/2.7V)로 역산한 내부저항은 신품 기준 약 25~30Ω, IR 그래프상 방전 후반부(EOL 근접)엔 90~120Ω까지 상승. ADC(3mA)+LED(가정 10mA) 동시 인출 시 전압강하를 배터리 수명 구간별로 계산한 결과, **신품 상태에서도 LDO(2.5V) 대비 마진이 매우 빠듯함**을 확인 — 실제 VDD 새그는 오실로스코프로 LED-on 구간을 직접 찍어 확인 필요(이번 세션에서는 계산만 수행, 실측은 미완료).

4. `DM_Optic_Handle_App.c`: `DM_App_Optic_TuneTargetADC()`의 `iError`를 `int32_t`→`int16_t`로 축소(오버플로우 위험이 있는 `wCurrentPWM`/`iSlope_Inv`는 안전하게 `int32_t` 유지)

### 6-3. 실측 결과 — 오히려 증가, 목적 실패

| | 이전 | 이후 | 차이 |
|---|---|---|---|
| RO code | 6911 | 6914 | +3 |
| RO data | 259 | 273 | +14 |
| RW data | 386 | 387 | +1 |

`.map` 파일로 직접 원인 확인:
- **2번은 컴파일러가 완전히 인라인**해버려 별도 심볼조차 남지 않음 — 순 절감 0.

### 6-4. 결론

**"본문이 몇 줄 안 되는 작은 함수를 파라미터화해서 공용화하는 방식은, 이 컴파일러(사이즈 최적화)에서는 실질적 이득이 거의 없거나 오히려 손해"**라는 게 실측 결론. 사용자 결정에 따라 **4개 항목 전부 원복**하여 세션 시작 시점 코드로 복귀.

## 7. 신규 LED(LTST-C193KGKT-5A) 검토 및 Bin 지정 구매 결정

### 7-1. 배경

기존 LED(LTST-C191KGKT) 대신 `LTST-C193KGKT-5A`를 검토. 처음에 VF/mcd 스펙만 보고 "VF는 더 낮고 mcd는 더 높다"는 판단이 있었으나, 데이터시트를 직접 대조하며 검증.

### 7-2. 테스트 전류 불일치 발견 — 직접 비교 무효

| | 기존(C191KGKT) | 신규(C193KGKT-5A) |
|---|---|---|
| 테스트 전류 | IF=20mA | IF=5mA |
| VF | 1.9~2.4V | 1.7~2.3V |
| IV(mcd) | 18.0~71.0 | 4.5~28.0 |

두 데이터시트의 **테스트 전류 자체가 다름**(20mA vs 5mA)을 확인 — raw 숫자 비교는 무효. 오히려 raw 숫자만 보면 mcd는 신규가 더 낮음(28 vs 71). 다만 실제 회로 동작전류(~1~2mA)는 20mA보다 5mA에 훨씬 가까워, **신규 데이터시트가 실사용 조건 예측에 더 신뢰할 만함**(외삽 배율이 20mA→1.2mA의 약 17배 대신 5mA→1.5mA의 약 3.3배로 훨씬 짧음).

### 7-3. 회로 실동작 전류 계산 (VDD 2.5V, R 510Ω, 자기일관 계산)

$$I = \frac{V_{DD}-V_F}{R}$$

Bin별(VF Rank E2/E3/E4) 대입 결과:

| Bin | VF 범위 | 전류 범위 |
|---|---|---|
| E2 | 1.7~1.9V | 1.18~1.57mA |
| E3 | 1.9~2.1V | 0.78~1.18mA |
| E4 | 2.1~2.3V | 0.39~0.78mA |

Bin 미지정 구매 시 전류가 최대 **약 4배**(1.57/0.39) 차이날 수 있음을 확인.

### 7-4. "저항을 낮추면 bin 편차가 줄어드는가" — 검증 결과 틀린 가설이었음을 발견 및 정정

처음엔 저항을 낮추면 bin 편차 영향이 줄어들 것으로 추정했으나, 수식으로 검증한 결과 **틀린 가설**이었음을 확인:

$$\frac{\Delta I}{I_{avg}} = \frac{\Delta V_F/R}{(V_{DD}-V_{F,avg})/R} = \frac{\Delta V_F}{V_{DD}-V_{F,avg}}$$

**R이 분자/분모에서 약분되어 사라짐** — 저항값을 얼마로 바꾸든 전류의 상대적(배율) 편차는 전혀 줄어들지 않음(510Ω/100Ω/50Ω 전부 동일하게 4.03배로 계산 확인). 이 상대 편차를 줄이는 실질적 방법은 (1) VDD를 높이거나, (2) **VF bin을 좁혀서 지정 구매**, (3) 정전류 드라이버 사용, 세 가지뿐임을 정리.

### 7-5. Bin 지정 구매 결정

- **VF: E2(1.7~1.9V)** 지정 — E3보다 평균전류도 높고 상대편차(28.6% vs 40%)도 더 낮아 유리함을 계산으로 확인 (VF가 낮을수록 분모 `VDD-VF_avg`가 커져 상대편차가 줄어드는 구조)
- **IV: K(7.1~11.2mcd @5mA)** 지정 — VF bin과 IV bin은 데이터시트상 서로 독립된 별도 분류라, 밝기 균일성까지 확보하려면 IV bin도 같이 지정해야 함을 확인

**최종 예상 성능** (VDD 2.5V, R 510Ω, LTST-C193KGKT-5A E2/K bin 기준):
- 전류: 1.18~1.57mA
- 밝기: 약 1.7~3.5mcd (5mA 기준값을 실전류로 선형 환산)

## 8. USART 서비스 명령 추가 — 테스트 카운트 리셋('R'/'r') 및 RawDump 헤더(버전/LOT)

### 8-0. 통신 스펙 (참고용)

`DM_HW_Drv_USART_Init()`(`USER/Drive/DM_HW_Drv.c`) 기준: **9600 baud, 8bit, stop 1, parity none**. TX는 폴링 방식, RX는 인터럽트 방식(RXNE)으로 구현됨.

### 8-1. 배경

`_nSCAN_MAX_CNT`(30회) 도달 시 `ERROR_OVER_USED`로 진입하는데, 이 카운트(`gs_bTestCompleteCount`, EEPROM 저장)를 초기화할 수 있는 명령이 기존 코드에 전혀 없었음을 확인(기존엔 `'M'`/`'m'`+Enter로 EEPROM 원시 덤프를 보내는 명령만 존재). 서비스/수리 시나리오를 위해 리셋 명령 추가를 결정.

### 8-2. 구현 — `'R'`/`'r'` + Enter 리셋 명령

- `DM_Main_Sq_App.c`/`.h`: `DM_App_Main_Sq_Reset_TestCompleteCount()` 신규 추가 — EEPROM과 RAM 캐시(`gs_bTestCompleteCount`) 둘 다 0으로 리셋
- `User_Main.c`의 `USART1_RX_TIM5_CC_IRQHandler()`: 기존 `'M'`/`'m'` 단일문자+Enter 패턴을 확장해 `'R'`/`'r'`도 같은 방식으로 처리(수신한 커맨드 문자를 저장해뒀다가 Enter 시 `'M'`이면 덤프, `'R'`이면 리셋 분기)

### 8-3. 구현 — RawDump에 펌웨어 버전/LOT 헤더 추가

`DM_App_Main_Sq_Send_RawDump()` 맨 앞에 고정폭 헤더(21바이트)를 추가로 전송하도록 요청받아 구현:

- `_strFIRMWARE_VER` 4바이트, `_REAL_FIRMWARE_VER` 8바이트, `_strLOT_UPPER_4CHAR` 4바이트, `_strLOT_LOWER_5NUM` 5바이트
- 공용 헬퍼 `DM_App_Main_Sq_Send_FixedStr(pcStr, bLen)` 신규 추가 — 지정한 바이트 수만큼 정확히 전송(짧으면 0 패딩, 길면 절단)

구현 중 `_REAL_FIRMWARE_VER`의 당시 값(`"v2.1.1_alpha.2"`, 14자)이 요청된 8바이트를 초과해 뒷부분이 잘리는 문제를 발견해 알림 → 사용자가 값을 `"v2.1.1.2"`(정확히 8자)로 직접 수정하여 해결, 코드 변경은 불필요.

RawDump 총 페이로드: 기존 248바이트 → **269바이트**(21바이트 헤더 추가).

### 8-4. 현재 `Send_RawDump()` 전체 데이터 양식 (참고용, 총 269바이트)

**0. 헤더 (21바이트, 고정폭 문자열)**

| 필드 | 바이트 |
|---|---|
| `_strFIRMWARE_VER` | 4 |
| `_REAL_FIRMWARE_VER` | 8 |
| `_strLOT_UPPER_4CHAR` | 4 |
| `_strLOT_LOWER_5NUM` | 5 |

**1. 상태 카운터/코드 (4 word = 8바이트, 각 word는 High byte 먼저)**

InsertCount → TestCompleteCount → ErrorStep → ErrorCode

**2. 초기 스틱 PTR 데이터 (8 word = 16바이트)**

`DM_App_Optic_MeasureInitialStick()`에서 측정한 4채널×2(Duty50%/100%) 원본값

**3. 저장된 결과 레코드 7개 (각 16 word = 32바이트 × 7 = 224바이트)**

각 레코드 내부 구성(16 word):

| 순서 | 항목 | word 수 |
|---|---|---|
| ① | PWM 값 (OPTIC_CH_0~3) | 4 |
| ② | Empty Band 데이터 (`BAND_T/BT/BC/C`) | 4 |
| ③ | Result Band 데이터 (`BAND_T/BT/BC/C`) | 4 |
| ④ | 계산 결과 (`RES_T_INTENSITY, RES_C_INTENSITY, RES_YES_NO`) | 3 |
| ⑤ | Dummy | 1 |

레코드는 `gs_bStickInsertCnt % 7`로 순환 저장되는 7슬롯 링버퍼라, 인덱스 자체는 시간순이 아니고 `InsertCount`와 대조해야 최신순을 알 수 있음.

## 9. `CodeingCompleteReport.md` 최신화

`USER/` 전체를 코드 기준으로 재검토해, 4/29 작성 후 갱신되지 않아 실제 동작과 달라진 부분과 누락된 기능을 반영.

### 9-1. 3-1절 정정 — 스틱 감지 방식 서술이 실제와 다름

기존 서술("전기 신호로 깨어나 0.15초 디바운싱")은 7/31에 이미 삭제된 구식 GPIO 디바운스 메커니즘 기준이었음(코드 전체에 `Debounce` 문자열 검색 결과 0건으로 확인). 실제로는 스틱 삽입 스위치가 Halt 웨이크업 **트리거 용도로만** 쓰이고, 깨어난 직후 **광학 센서(OPTIC_CH_3)로 실제 스틱 존재 여부를 재확인**하는 방식(`DM_App_Main_Sq_Idle_Step_Handler()`)으로 정정.

### 9-2. 4절 추가 — 스틱 유효성 검증 단계 누락

`DM_App_Optic_MeasureInitialStick()`이 스틱 삽입 직후 4채널 초기 반사율을 정상범위와 대조해 불량/이물질 등을 걸러내는 로직이 보고서에 전혀 언급되지 않아, "1. 스틱 인식 및 유효성 검증" 단계를 검사 흐름 맨 앞에 신규 추가(기존 1~4번 항목은 2~5번으로 밀림).

### 9-3. 확인 후 그대로 둔 부분

2절(소프트웨어 구조), 3-2/3-3절(자동 0점 조절/정밀 나눗셈 알고리즘), 4절의 샘플감지~결과확정 흐름(5분/3분 등 시간 수치 포함)은 현재 코드(`DM_Main_Sq_App.h`의 시간 상수 등)와 대조해도 정확함을 확인, 수정하지 않음.
