## 1. MCU Pin Map 변경 반영

### 배경

하드웨어 팀에서 PCB Pin Map을 아래와 같이 확정/변경함.
06/16 검토에서 지적된 **PC1(PTR_PW) True Open-Drain 문제**를 핀 재배치로 근본 해결한 구조.

### 변경된 Pin Map

| 신호 | 기존 | 변경 | 타입 |
|---|---|---|---|
| LED_PWM | PB2 | PB2 (변경 없음) | PWM |
| nLED1 | PB4 | **PC0** | Open Drain |
| nLED2 | PB3 | **PC1** | Open Drain |
| PTR_PW | PC1 | **PB3** | Push-Pull |
| PTR1 (ADC) | PB5 | PB5 (변경 없음) | ADC |
| PTR2 (ADC) | PB6 | PB6 (변경 없음) | ADC |
| PTR3 (ADC) | PB7 | PB7 (변경 없음) | ADC |
| LCD_COM0 | PC0 | **PB4** | Push-Pull |
| LCD_SEG0 | PC5 | PC5 (변경 없음) | Push-Pull |
| LCD_SEG1 | PC6 | PC6 (변경 없음) | Push-Pull |
| LCD_SEG2 | PD0 | PD0 (변경 없음) | Push-Pull |
| LCD_SEG3 | PB0 | PB0 (변경 없음) | Push-Pull |
| SW_STRIP (STP_CK) | PB1 | PB1 (변경 없음) | Input |

**설계 포인트:** Push-Pull이 필요한 기능(PTR_PW, LCD_COM0)은 HS 핀(PB3/PB4)으로, Sink만 하면 되는 기능(LED1/LED2 ON/OFF)은 True OD 핀(PC0/PC1)으로 재배치하여 전기적 특성에 맞춘 교차 배치.

## 2. 광학 튜닝(Optic Tuning) 실측 검증 및 컴파일러 최적화 버그 발견

Pin Map 변경 반영 후, 실제 스틱으로 `DM_App_Optic_MeasureInitialStick()` → `DM_App_Optic_TuneTargetADC()` → `DM_App_Optic_MeasureEmptyPTR()` 전체 시퀀스를 실측하며 검증 진행.

### 2-1. TIM2 PWM 극성 수정 검증 (완료)

1차 실측(Pin Map 변경 직후, TIM2 극성 미수정 상태)에서 PWM199→399로 올릴 때 ADC가 오히려 폭락(1437→34 등)하는 현상 발견. 원인은 `DM_HW_Drv_LED_TIM2_Init()`의 `TIM2_OCPolarity_Low`가 06/15 "역조립 대응" 값 그대로 남아있어 nLED1/nLED2(표준 Low=ON 복원)와 극성이 안 맞았기 때문.

```diff
- TIM2_OCPolarity_Low,
+ TIM2_OCPolarity_High,   /* PB2=Anode(source): CCR=399 → 항상 High → 100% ON */
```
```diff
- /* Drive cathode pin HIGH to ensure LED is OFF */
- GPIO_WriteBit(LED_PWM_GPIO_PORT, LED_PWM_GPIO_PIN, SET);
+ /* Drive anode pin LOW to ensure LED is OFF (no source current) */
+ GPIO_WriteBit(LED_PWM_GPIO_PORT, LED_PWM_GPIO_PIN, RESET);
```

수정 후 재측정: PWM199→399 시 ADC가 정상적으로 증가함을 확인 (예: 1440→2971, 1436→2974, 1268→2624, 1346→2777). **극성 수정 검증 완료.**

### 2-2. `_nTAGET_LIGHT` 파라미터 조정 (완료)

`Parameter_define.h`의 `_nTAGET_LIGHT`(튜닝 목표 ADC Count)가 800으로 설정되어 있었는데, 모든 채널의 PWM199 실측값(1266~1440)보다 낮아 `DM_App_Optic_TuneTargetADC()`가 항상 검증되지 않은 외삽 구간(PWM<199)으로 내려가야 하는 구조적 문제 발견.

```diff
- #define _nTAGET_LIGHT   800
+ #define _nTAGET_LIGHT   2000
```

4채널 PWM199~399 실측 범위(최대 1440 ~ 최소 2624) 안에 여유있게 들어오는 값으로 상향하여, 튜닝이 항상 보간(interpolation) 구간에서 이루어지도록 함.

### 2-3. `gs_awEmptyBand_LowData` 일부 채널 0 발생 → 원인 조사

`_nTAGET_LIGHT` 조정 후에도 `MeasureEmptyPTR()` 결과 중 CH_1, CH_3(둘 다 각 LED의 "두 번째 연속 측정" 채널)만 반복적으로 정확히 0이 나오는 현상 발견. 아래 가설들을 순서대로 배제:

| 가설 | 결과 |
|---|---|
| 스틱에 샘플이 이미 묻어 Band 위치 반사율이 붕괴 | 배제 (완전 마른 새 스틱으로 확인) |
| PWM 극성/튜닝 외삽 문제 재발 | 배제 (목표값 2000이 보간 구간 안인데도 재발) |
| 같은 LED 연속 재점등 시 전기적 문제로 LED가 실제로 안 켜짐 | 배제 (육안으로 LED 정상 점등 확인) |
| 디버거가 브레이크포인트에서 TIM2까지 같이 정지시켜 관찰 결과를 왜곡 | 확인됨 (이 디버거 환경의 특성이나, 본 버그의 직접 원인은 아니었음) |

최종 원인: **컴파일러 최적화로 인해 `for (bCh = 0; bCh < OPTIC_CH_MAX; bCh++)` 루프의 `bCh`가 실제 실행에서 0→2→4로 증가(1, 3을 스킵)하여, 해당 인덱스의 `DM_App_Optic_Measure()` 호출 자체가 누락됨.** 그 결과 `pBuffer[1]`, `pBuffer[3]`이 한 번도 쓰이지 않아 초기값(0)이 그대로 남은 것 — 광학/전기적 문제가 전혀 아니었음.

### 2-4. 조치 (완료)

`bCh`를 `volatile`로 선언하여 정상적으로 0,1,2,3 순서대로 카운트되도록 수정. 동일 구조(비-volatile `bCh` 루프 안에서 `DM_App_Optic_Measure()` 호출)를 가진 나머지 두 함수에도 동일하게 적용.

`USER/App/DM_Optic_Handle_App.c`:
```diff
  uint8_t DM_App_Optic_MeasureInitialStick(uint16_t* pBuffer)
  {
-     uint8_t bCh;
+     volatile uint8_t bCh;
```
```diff
  uint8_t DM_App_Optic_TuneTargetADC(uint16_t* pInitBuffer, uint16_t wTargetADC)
  {
-     uint8_t bCh;
+     volatile uint8_t bCh;
```
```diff
  uint8_t DM_App_Optic_MeasureEmptyPTR(uint16_t* pBuffer)
  {
-     uint8_t bCh;
+     volatile uint8_t bCh = 0;
```

### 2-5. 남아있는 디버깅용 임시 코드 (정리 대기)

이번 조사 과정에서 `DM_App_Optic_Measure()`에 육안 확인/브레이크포인트용으로 추가된 임시 코드가 아직 파일에 남아있음:

- `uint16_t dwCCT;` (전역) + `dwCCT = tCh;` — 브레이크포인트 지점 확보용, 다른 곳에서 미사용(죽은 코드)
- 샘플링 루프 내 `DM_HW_Drv_SystemSleep_10ms();` 7연속 호출(원래 1회) — LED 점등을 육안으로 확인하기 위한 의도적 지연. 샘플 1개당 10ms→70ms로 늘어나 전체 측정시간이 20개×70ms≈1.4초로 원래 설계(~200ms) 대비 7배 증가. 주석은 여전히 "~200ms"로 남아있어 실제와 불일치.

**최종 검증/양산 빌드 전에 반드시 원복 필요** (다음 세션에서 처리 예정).
