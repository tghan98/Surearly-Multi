## 1. Pa082 경고 수정 (volatile 다중 읽기)

`DM_App_Optic_MeasureEmptyPTR()`의 286번 줄에서 `volatile uint8_t bCh`를 한 문장 안에서 3번(`pBuffer[bCh]`, `(OPTIC_CH_t)bCh`, `gs_wOptic_PWM[bCh]`) 읽어 **"Warning[Pa082]: undefined behavior: the order of volatile accesses is undefined"** 발생.

`bCh`(volatile)를 루프 진입 시 한 번만 non-volatile 로컬(`bChIdx`)에 캐싱해서 이후 인덱싱/인자에 재사용하도록 수정 — 최적화 버그 방지용 volatile 루프 카운터 특성은 유지하면서 경고만 제거. (이 `bChIdx`는 이후 4절에서 다시 제거됨 — 아래 참조)

## 2. 코드 사이즈 절감 검토 및 적용

STM8L151F3(8KB Flash) 대상으로 `USER\`, `Core\main\` 코드를 검토하고, 빌드 map 파일(`Debug\List\OVULATION_MULTI_New.map`)로 실측 기반 절감을 진행.

**시작 시점 (아무 작업 전):** ro code 6,771B + ro data 487B = **7,258B / 8,192B (88.6%)**

### 2-1. UART CSV 전송 → Raw uint16_t 전송으로 전환

`DM_App_Main_Sq_Send_CSV_Data()`가 EEPROM 이력을 사람이 읽을 수 있는 CSV(ASCII 변환 + 헤더 문자열)로 UART 전송하던 것을, 회수 기기 진단 목적에 맞게 **ASCII 변환 없이 EEPROM 값을 그대로(uint16_t, 2바이트 그대로) 전송**하는 방식으로 재작성.

- `DM_HW_Drv_USART_SendString()` / `DM_HW_Drv_USART_SendInt()` 삭제 → `DM_HW_Drv_USART_SendWord(uint16_t)` (High byte 먼저 전송) 신규 추가
- `DM_App_Main_Sq_Send_CSV_Data()` → `DM_App_Main_Sq_Send_RawDump()`로 재작성 (헤더 문자열/콤마 포맷팅 전부 제거, InsertCnt/TestCompCnt/ErrStep/ErrCode 4워드 + StickPtr 8워드 + Result 7채널×16워드를 그대로 전송)
- `User_Main.c`의 USART1 RX ISR 호출부 갱신

**실측 결과:** ro code 6,771→6,520B, ro data 487→188B → 합계 **6,708B (81.9%)**, 절감 **550B**

### 2-2. LCD 애니메이션 함수 테이블화

`DM_App_LCD_Sq_StickInsert_Process`(15단계), `DM_App_LCD_Sq_ErrOverUsed_Process`(8단계)의 반복적인 switch-case(아이콘 on/off + 타이머 세팅 패턴)를 `LCD_ANIM_STEP_t {bCh, bState, bDelay}` const 테이블 + 공통 while 루프로 교체. 원본의 fallthrough(지연 없이 즉시 다음 단계 진행) 동작까지 while 루프로 동일하게 재현.

**실측 결과:** `DM_LCD_Stick_Check_App.o` ro code 806→562B(-244B), ro data 13→82B(+69B) → **net -175B**

### 2-3. 에러 처리 보일러플레이트 함수화

## 6. "Count 변수 스킵" 버그 재조사 — 근본 원인 정정

### 6-1. 증상 재발

`_nTAGET_LIGHT`/`OPTIC_TUNE_TOLERANCE` 변경 및 `TuneTargetADC` 재활성화 이후, `gs_awEmptyBand_LowData`가 `{1013, 0, 898, 0}`로 나오는 현상 재발 — 7/28에 "해결"했던 것과 동일한 패턴(각 LED의 2번째 연속 측정 채널만 정확히 0).

### 6-2. 근본 원인 정정: 컴파일러 루프 스킵 → 지역변수 손상(가상 레지스터 충돌)

기존 가설("`bCh`가 volatile이 아니면 컴파일러가 루프를 스킵한다")로 `DM_App_Optic_MeasureEmptyPTR()`의 `bChIdx`를 `volatile`로 만들어봤으나, 사용자가 직접 **전역 변수로 선언하면 정상 동작, 지역 변수로 선언하면 오동작**하는 것을 실측으로 확인. 이는 "루프 스킵"이 아니라 **IAR STM8 "small" 코드 모델이 지역변수를 공유 가상 레지스터(`.vregs`, 0x0000~0x000F: `?b0~?b15`, `?w0~?w7` 등)에 배치할 때, 함수 호출(`DM_App_Optic_Measure()`)을 넘나드는 생존 구간 추적이 잘못되어 콜리의 지역변수가 같은 슬롯을 덮어쓰는 문제**임을 시사.

(참고: map 파일의 RAM 배치를 확인한 결과 전역변수 영역(0x0000~0x005E)과 CSTACK(0x0300~0x03FF) 사이에 약 673바이트의 완전히 빈 공간이 있어, "스택 오버플로우가 전역을 침범"하는 시나리오는 배제됨 — 가상 레지스터 재사용 쪽이 훨씬 타당.)

**이 문제는 IAR STM8 컴파일러에 한정된 것으로 파악(사용자 확인).** 다른 툴체인으로 이전 시 이 우회책이 여전히 필요하다고 가정하지 말 것.

### 6-3. 조치: volatile → static 전면 전환

함수 호출을 넘나드는 모든 로컬 "Count(카운터/인덱스)" 변수를 `static`으로 전환 (고정 주소 확보로 가상 레지스터 충돌 원천 차단). 기존 `volatile`도 더 이상 필요 없어 `static`으로 대체.

| 파일 | 변경된 변수 |
|---|---|
| `DM_Optic_Handle_App.c` | `bCh`(3개 함수), `bIter`, `i`(MeasureInitialStick), `i,j`(Measure) |
| `DM_Main_Sq_App.c` | `i`×5(Sample_Load_Wait/Over_Sample_Check/Low_Sample_Check/Reaction_Wait/Result_Out), `i,idx`(Save_Result_To_Rom), `i,j`(Send_RawDump) |
| `DM_HW_Drv.c` | `i`×2(EEPROM_Write/Read), `bConvCount`(ADC_Read) |
| `DM_LCD_Stick_Check_App.c` | `i`×2(SetState/Refresh) |
| `DM_Rom_Handl_App.c` | `i`(Get_StickPtrData) |
| `DM_Utill.c` | `nCnt`(CalculateIntensity) |

`= 0` 인라인 초기화가 있던 `bIdx`, `idx`는 `static` 선언 시 초기화가 프로그램 로드 시 딱 한 번만 실행되는 문제가 있어, 루프 진입 전 별도 대입문으로 리셋 로직을 옮김. 나머지는 `for(x=0;...)` 루프 자체가 매 호출 리셋하므로 안전.

이후 `bChIdx`는 `bCh`가 더 이상 volatile이 아니게 되어 Pa082 우회 목적이 사라졌으므로 **완전히 제거**하고 `bCh`를 직접 사용하도록 정리.

## 7. Map 파일 기반 스택 오버플로우 확인 가능 여부 (검토만, 보류)

Map 파일로 확인 가능한 것: 전역/static 변수 크기(125B), CSTACK 예약 크기(256B, 0x0300~0x03FF), 그 사이 여유 공간(약 643B).
Map 파일로 확인 **불가능**한 것: 실제 런타임 최대 스택 사용량 (IAR Stack Usage/Call Graph 분석이 이 프로젝트에 활성화되어 있지 않음 — map에 해당 섹션 없음).

사용자 판단: 현재는 전역 125B + 여유 643B로 충분해 보여 추가 조치 보류. 필요 시 IAR Stack Usage 분석 활성화 또는 스택 페인팅(런타임 워터마크) 방식으로 재검토 예정.

## 8. 보류 — STP_CK 역할 재정의 (미완료, 9절 BOOK 이슈로 인해 중단)

STP_CK(스틱 감지 핀)는 **Halt 모드 wake-up 트리거 및 진짜 wake-up인지 확인하는 용도로만** 사용하고, 시퀀스 진행 중(스틱 삽입 후 대기/측정 루프 내내) `DM_App_Stick_Get_Status() == STICK_STATUS_REMOVED` 체크로 계속 폴링하며 중도 이탈시키는 코드는 제거하기로 결정. 대상 9곳 확인:

- `DM_Main_Sq_App.c`: Stick_Insert_Step_Handler(while 루프), Sample_Load_Wait/Over_Sample_Check/Low_Sample_Check/Reaction_Wait_Step_Handler(각 for 루프) — 5곳
- `DM_Optic_Handle_App.c`: MeasureInitialStick(루프 내 + EEPROM 저장 전 최종 체크), TuneTargetADC(bIter 루프), MeasureEmptyPTR(루프) — 4곳
- (제외) `DM_App_Main_Sq_Idle_Step_Handler()`의 `#if 0`로 비활성화된 wake-up 후 재확인 로직은 "진짜 wake-up 확인" 용도에 해당하므로 유지

실제 코드 제거 작업 중 사용자가 작업을 중단하고 LCD 확인 관련 요청(9절)으로 전환 — **아직 미완료, 다음 세션에서 이어서 처리 예정.**

## 9. LCD 시퀀스 전용 테스트 모드 구현

시퀀스는 딜레이만 걸리고 LCD 애니메이션만 눈으로 확인하고 싶다는 요청으로, `Parameter_define.h`에 `_DEBUG_LCD_SEQ_ONLY`(기본 1) / `_DEBUG_SEQ_STEP_DELAY`(500 = 5초) 스위치를 추가하고 `DM_Main_Sq_App.c`의 7개 스텝 핸들러(Stick_Insert / Sample_Load_Wait / Over_Sample_Check / Low_Sample_Check / Reaction_Wait / Result_Scan / Result_Out) 전부에 `#if _DEBUG_LCD_SEQ_ONLY` 분기 추가.

- 정상 경로만 타도록(에러 분기 제외) 구현, Result_Scan은 YES/NO를 매 사이클 번갈아 표시
- **Stick_Insert만 예외**: STICK_INSERT LCD 애니메이션이 15단계×500ms≈7.5초짜리 자체 완결형이라, 5초 고정 딜레이를 쓰면 애니메이션이 잘리므로 "LCD 애니메이션이 `LCD_SQ_IDLE`로 자연 종료될 때까지 대기"로 처리
- 전체 사이클이 원래 13분에서 약 32.5초로 단축됨

## 10. BOOK 아이콘 이상 동작 — 하드웨어 결함 오판 후 실제 원인(USART Remap 누락) 규명

### 10-1. 증상 발견 및 배제해나간 가설들

LCD 시퀀스 테스트 중 BOOK 아이콘(PC5, `LCD_SEG0`)만 "희미하게/절반만" 켜지는 현상 발견. 순서대로 가설 검증:

1. **PC5의 GPIO 모드 제약** — STM8L151F3 데이터시트 Table 4 확인 결과 PC5는 PC0/PC1(True Open-Drain 전용)과 달리 OD/PP 둘 다 지원 → **배제**
2. **OSC32_IN(PC5 대체 기능) 크리스탈/캐패시터 부하** — 사용자가 실물 확인, 미실장 → **배제**
3. **wake-up 직후 타이밍 문제** — BOOK은 STICK_INSERT 애니메이션 12번째 단계(wake-up 후 약 4.5초 시점)라 "직후"가 아니고, GPIO 재초기화도 4채널 동일 → **배제**
4. **소프트웨어 로직 차이** — `DM_App_LCD_Refresh()`는 4채널을 완전히 동일한 루프로 구동. "ALL OFF" 단계에서도 BOOK만 안 꺼진다는 관찰로, 동일 명령(`SEG=COM`)에 대해 물리적 결과만 다르다는 것을 확인 → 이 시점까지는 **하드웨어 결함(글라스 접점/PCB 트레이스 불량)으로 잠정 결론**

### 10-2. 직접 GPIO 강제 테스트

`DM_App_Main_Sq_Idle_Step_Handler()`에 `DM_App_LCD_COM_Control(SET); DM_App_LCD_SEG_Control(CH_LCD_YES, SET); while(1);`을 삽입해 멀티미터로 실측 — COM=2.5V, BOOK(SEG0)=2.5V(명령한 적 없는데도 COM과 동일), 나머지=0V. **BOOK이 아무 명령 없이도 COM 전압을 따라간다**는 점에서 하드웨어 결함 가설이 한층 강화됨.

### 10-3. LCD 핀 제어 방식 리팩터링 (배열 → switch-case, 직접 레지스터)

혹시 배열 인덱싱이나 `GPIO_WriteBit()` 자체의 문제 가능성을 배제하기 위해, `DM_LCD_Stick_Check_App.c`의 `gs_pLCD_PORT[]`/`gs_bLCD_PIN[]` 배열을 제거하고 `DM_App_LCD_SEG_Control()`/`DM_App_LCD_COM_Control()`을 `switch-case` + `LCD_XXX_PORT->ODR |= LCD_XXX_PIN` / `&= ~LCD_XXX_PIN` 직접 레지스터 조작으로 재작성. (인덱싱 오류 없음을 코드로도 재확인)

### 10-4. 결정적 단서 — USART_Init() 직후 BOOK이 High로 전환

`User_Main_Init()`에서 `DM_HW_Drv_USART_Init()` 실행 직후 BOOK 핀이 High로 전환되는 것을 사용자가 발견. `stm8l15x_syscfg.h`의 `REMAP_Pin_TypeDef` 확인 결과 **PC5는 USART1_TX(remap) 및 SPI1_NSS(remap)의 대체 핀 위치로 문서화**되어 있음을 확인.

- 1차 조치: `main.c`에서 `User_Main_Init()` 호출 전 `SYSCFG_REMAPDeInit()`(모든 remap 레지스터 리셋값화) 추가 → **효과 없음, BOOK 계속 High**
- 재검토: `stm8l15x_syscfg.c`의 `REMAP_Pin_USART1TxRxPortA` 주석 — "USART1 Tx-Rx **(PC3-PC2)** remapping to PA2-PA3" — 즉 **USART1의 진짜 기본(remap 없음) 핀은 PC3/PC2**이고, 프로젝트가 사용하려는 PA2/PA3는 remap을 **명시적으로 ENABLE**해야만 실제로 적용됨
- 그런데 `DM_HW_Drv_GPIO_Init()`은 PA2/PA3를 USART 핀으로 GPIO만 설정했을 뿐 **`SYSCFG_REMAPPinConfig()`를 한 번도 호출한 적이 없었음** — 별개의 실제 버그(USART1이 의도한 PA2/PA3가 아니라 다른 곳으로 나가고 있었을 가능성)

### 10-5. 최종 조치 및 해결 확인

`DM_HW_Drv_USART_Init()` 최상단에 `SYSCFG_REMAPPinConfig(REMAP_Pin_USART1TxRxPortA, ENABLE);` 추가(USART_DeInit/Init 이전). 재빌드 후 **BOOK 핀이 정상적으로 Low로 확인됨 — 문제 해결.**

**결론: 이 버그는 하드웨어 결함이 아니라 USART1 SYSCFG remap 설정 누락으로 인한 PC5 핀 점유 충돌이었음.** 10-1~10-2단계에서 "하드웨어 결함"으로 여러 차례 판단했던 것은 오판이었고, 실제로는 소프트웨어가 의도치 않게 주변기능 핀을 점유하고 있었던 것이 원인. (향후 유사 증상 발생 시 `stm8l15x_syscfg.h`의 `REMAP_Pin_TypeDef` 목록에서 해당 핀이 다른 주변기능의 remap 대상인지부터 확인할 것.)

**임시로 추가했다가 제거한 디버깅 코드**: `_DEBUG_LCD_BOOK_ONLY`(BOOK만 강제 구동), `_DEBUG_LCD_REFRESH_20MS`→`_DEBUG_LCD_REFRESH_100MS`(Refresh 주기 조정) — 원인 규명 후 전부 삭제, 현재 코드베이스에는 남아있지 않음.
