# 펌웨어 계층별(Layered) 분석 프롬프트

원래 작성하신 5계층 구조(HW → HW Driver → Module → Application → System Integration)를 그대로 유지하고, 각 단계에 실행 지시·산출물 형식·계층 위반 체크 항목을 보강했습니다.

---

## 프롬프트 원문

너는 임베디드 펌웨어 아키텍트야. 아래 펌웨어 소스 코드를 **하드웨어에 가까운 계층부터 상위 계층까지 순서대로** 분석해서, 각 계층이 무엇을 하는지, 계층 간 경계가 잘 지켜지고 있는지를 파악해줘. 목적은 취약점 진단이 아니라 **아키텍처 이해 및 계층 구조 검증**이야. 각 단계마다 분석 결과를 지정된 산출물 형식으로 정리해줘.

### 1. 하드웨어(HW) 분석

목적: 회로도 없이 소스 코드만으로 하드웨어 구성을 역으로 추정한다.

- Pin Map을 확인하고, 각 Pin이 어떤 동작(GPIO/ADC/PWM/UART 등)에 쓰이는지 코드(레지스터 설정, 초기화 함수, HAL 설정 구조체)에서 근거를 찾아 정리해줘.
- 연결된 MCU Peripheral(ADC, DMA, Timer, SPI, I2C, UART 등) 목록을 정리하고, 각 Peripheral이 어떤 외부 Pin과 연결되어 동작하는지, 혹은 외부 Pin 없이 내부적으로만 쓰이는지(예: SysTick 대신 Timer를 System Tick으로 쓰는 경우) 구분해줘.
- 산출물: 아래 표 형식으로 정리

  | Pin/Peripheral | 연결 대상 | 트리거 방식(DMA/Interrupt/Polling) | 외부 연결 여부 | 추정 용도 |
  |---|---|---|---|---|
  |  |  |  |  |  |

### 2. HW 종속 코드 / 드라이버 분석

목적: MCU 레지스터 및 Vendor HAL을 감싼 1차 캡슐화 계층(예: `HW_Drive.c`, `HW_XXX_Drive.c`)을 분석한다.

- MCU 레지스터 직접 접근 코드, Vendor HAL(예: STM32 HAL) 호출 코드가 어디에 모여 있는지 찾아줘. 파일이 `HW_XXX_Drive.c` 형태로 분할되어 있으면 각 파일이 어떤 인터페이스(GPIO/UART/SPI/ADC 등)를 담당하는지 매핑해줘.
- 각 드라이버 함수의 특징을 판단 기준에 따라 정리해줘: 관점(핀 제어/레지스터 설정/인터럽트 처리), 대표 함수 시그니처 예시, 상태 관리 여부(대부분 없음), MCU 종속도(대부분 매우 높음 - MCU 변경 시 재작성 필요).
- 산출물: 아래 표 형식으로 정리

  | 파일/모듈 | 담당 인터페이스 | 대표 함수 예시 | 상태 관리 | MCU 종속도 |
  |---|---|---|---|---|
  | HW_GPIO_Drive.c | GPIO | `HW_GPIO_Write(PIN_A, HIGH)` | 없음 | 매우 높음 |

### 3. 드라이버 조합 모듈 분석

목적: 여러 드라이버를 조합해 의미 있는 "기능 단위"를 수행하는 모듈(예: 모터 제어, 센서 측정, 디스플레이)을 분석한다.

- 각 모듈이 어떤 드라이버 함수들을 조합해서 동작하는지 정리해줘. 예: `StepperMotor_MoveToAbsMm()`이 내부적으로 `HW_PWM_SetDuty()`, `HW_GPIO_Write()`를 어떤 순서/조건으로 호출하는지.
- 각 모듈의 상태(정지/이동 중/에러/캘리브레이션 등) 관리 로직이 있는지 확인하고 상태 전이(State Machine)가 있으면 정리해줘.
- **계층 위반 체크**: 모듈 코드 안에서 드라이버를 거치지 않고 MCU 레지스터나 HAL을 직접 호출하는 부분이 있으면 별도로 표시해줘 (캡슐화 위반 사례).
- 산출물: 아래 표 형식 + 위반 사례 목록

  | 모듈명 | 조합된 드라이버 | 대표 함수 예시 | 상태 관리 | MCU 종속도 |
  |---|---|---|---|---|
  | 모터 제어 모듈 | HW_PWM, HW_GPIO | `StepperMotor_MoveToAbsMm(15.5)` | 있음 (정지/이동/에러 등) | 낮음 |

  **계층 위반 사례**: [파일명:라인] - 모듈 코드에서 HAL/레지스터 직접 접근 발견 시 기재

### 4. 애플리케이션(Application) 분석

목적: "이 제품이 무엇을, 언제, 어떤 순서로 수행해야 하는가"에 대한 비즈니스 로직과 사용자 시나리오(Use Case)를 파악한다. 하위 Module 계층이 제공하는 "부품"들을 조립해 제품 고유의 기능/가치를 만드는 계층이다.

- 이 제품의 주요 Use Case(사용 시나리오)를 목록화해줘 (예: "측정 시작", "캘리브레이션 수행", "결과 전송").
- 각 Use Case가 어떤 모듈들을 어떤 순서로 호출하는지 시퀀스(단계별 흐름)로 정리해줘.
- Use Case별 예외/에러 처리 로직(재시도, 타임아웃, 알람 등)이 있으면 함께 정리해줘.
- **계층 위반 체크**: Application 코드에서 드라이버나 HAL을 직접 호출하는 부분이 있으면 표시해줘.
- 산출물:
  - Use Case 목록 (Use Case명 / 목적 / 관련 모듈 / 트리거 조건)
  - Use Case별 시퀀스 흐름 (예: `측정 시작 → OptiSensor_GetFilteredValue() → 결과 검증 → Display_Show() → Comm_SendResult()`)
  - 계층 위반 사례 목록

### 5. 시스템 통합(System Integration) 분석

목적: 개별 Application(진단 앱, UI 앱, 통신 앱 등)들을 하나로 묶어 제품 전체의 상태와 우선순위를 조율하는 System Manager/Orchestrator 계층을 분석한다.

- 시스템 전체 상태(State)와 상태 전이 조건을 정리해줘 (예: 대기 → 측정 중 → 결과 처리 → 에러/복구).
- 여러 Application이 동시에 요청을 발생시킬 때 우선순위 조정, 리소스 충돌(공유 자원, 공유 버스 등) 처리 로직을 찾아 정리해줘.
- 시스템 레벨 이벤트/스케줄링 구조(RTOS Task 우선순위, 이벤트 큐, 메시지 브로커 등)를 정리해줘.
- 전원 관리, Watchdog, Fault/예외 상황에서의 전체 시스템 대응(Fail-safe 동작)도 확인해줘.
- 산출물:
  - 시스템 상태 다이어그램(텍스트 기반 State Machine)
  - Application 간 조율 로직 요약 (누가 누구를 언제 호출/중재하는지)
  - Fail-safe/예외 대응 요약

### 6. 종합 요약 (Synthesis)

위 1~5단계 분석 결과를 하나로 묶어 아래 형식으로 정리해줘.

- 전체 계층 구조 다이어그램 (HW → Driver → Module → Application → System, 각 계층의 대표 구성 요소 포함)
- 계층별 핵심 요약 (계층당 2~3줄)
- 발견된 계층 위반 사례 종합 목록 (심각도 및 개선 제안 포함)
- 확실하지 않거나 추가 확인이 필요한 부분 (가정/추정 표시)
- 다음 분석 단계 제안 (예: 특정 Use Case 심화 분석, 특정 모듈 디컴파일/동적 분석 등)

---

### 사용 팁

- 코드베이스가 크면 "1~3단계만 먼저 해줘" 또는 "모터 제어 모듈만 집중 분석해줘"처럼 범위를 지정할 수 있습니다.
- 계층 위반 사례는 아키텍처 품질 이슈로 이어지므로, 발견 즉시 파일명/라인 번호와 함께 표시하도록 요청해두었습니다.
- 표 형식으로 산출물을 요청해두어, 이후 스프레드시트나 문서로 정리하기 쉽습니다.
