MCU Pin의 정의는 위와 같다.

1. MCU System Clock은 2MHz로 한다. 

2. GPIO 설정 
1) LED_PWM_GPIO_PIN은 TIM2_CH2 PWM 출력 설정
2) LED1_GPIO_PIN, LED2_GPIO_PIN GPIO OUTPUT에 Default High 설정 
3) LCD Pin은 모두 GPIO OUTPUT 설정에 Default Low 설정 
4) USART Pin 각 핀에 맞는 설정 
5) ADC Pin는 각 채널 ADC  Pin 설정 

3. LED1, LED2 PWM 제어 
1) LED_PWM_GPIO_PIN에서 TIM2_CH2로 5 kHz PWM 출력 듀티로 LED의 광량을 제어 한다.
(1) High LED ON Time , Low LED OFF Time
2) LED1_GPIO_PIN과 LED2_GPIO_PIN는 동작할 LED 선택(Pin이 Low 이면 LED ON, High 이면 OFF)

4. LCD 및 STP_CK(스틱 체크)  동작 
1) TIM4는 10msec 주기 Core 슬립 위이크업 타이머( 10msec Core 슬립 후 스립 해제 해당 인터럽트 코드 동작)
2) LCD 동작 
(1) TIM4의 10msec 타임 인터럽트 마다 LCD_COM_PIN 반전 
(2) OFF 타입에 있는 SEG들은 LCD_COM_PIN과 같은 상으로 동작, ON 타임 일 때 다른 상으로 동작 
(3) LCD Channel은  각각 혹은 전부 ON, OFF, BLINK(500msec 주기 define으로 변경 가능) 동작을 한다.



5. 채널간 ADC 실행 
(1) 채널 선택 ADC 실행 - 100 Kohm Pull down 저항에 22nF 콘덴서라 최대 사이클 필요 300 이상  
(2) ADC 완료까지 Core Sleep

6. USART 초기 설정 통신 속도 9600 , 수신은 인터럽트로 , 전송은 폴링 방식으로 한다
초기화 코드 생성하고 수신 인터럽트 생성 

7. STP_CK_PIN는 스틱 삽입 시 Low으로 되고 제거 되면 High가 된다 
1) half() 모드에서 STP_CK_PIN는에서 하강에지 인터럽트가 발생 하면 Wake up하고 STP_CK_PIN이 150msec 동안 스틱이 삽입 상태 인지 확인한다.
2) 삽입 상태이면 Wake up 상태를 유지 하고 다음 실행 준비를 하고 오동작으로 발생한 인터럽트면 다시 half()모드가 되고 STP_CK_PIN에 하강에지 인터럽트를 대기 한다.

  유효숫자)를 얻기 위해서입니다.

  이 방식은 초등학교 때 배우는 '세로셈 나눗셈' 원리를 그대로 코드로 옮긴 것입니다.

  1. 코드의 동작 원리 (세로셈 나눗셈)

  루프 내부를 한 단계씩 뜯어보면 다음과 같습니다.

   1 for(nCnt=0; nCnt<4; nCnt++){
   2   tmp = Divedend / Divisor;           // 1. 현재 몫(한 자리)을 구함
   3   Quotient = Quotient * 10 + tmp;     // 2. 결과값 자릿수를 올리고 몫을 더함
   4   Divedend = Divedend - tmp * Divisor; // 3. 나머지를 구함 (Divedend % Divisor와 동일)
   5
   6   Divedend = Divedend * 10;           // 4. 나머지에 10을 곱해 다음 자릿수 계산 준비
   7 }

  2. 4번 반복하는 이유: "고정 소수점(Fixed-point) 구현"

  만약 100을 80으로 나눈다고 가정해 보겠습니다. (결과는 1.25)

   * 1회차 (1의 자리): 100 / 80 = 1. 결과: 1. 나머지: 20. 다음 계산을 위해 20 * 10 = 200으로 만듦.
   * 2회차 (소수점 첫째): 200 / 80 = 2. 결과: 12. 나머지: 40. 다음 계산을 위해 40 * 10 = 400으로 만듦.
   * 3회차 (소수점 둘째): 400 / 80 = 5. 결과: 125. 나머지: 0. 다음 계산을 위해 0 * 10 = 0으로 만듦.
   * 4회차 (소수점 셋째): 0 / 80 = 0. 결과: 1250.

  결과적으로 1.25라는 값을 1250이라는 정수로 얻게 됩니다. 즉, 결과값에 1000을 곱한 효과를 내어 정밀도를 확보하는 것입니다.

  3. 왜 그냥 (Divedend * 1000) / Divisor를 안 하나요?

  가장 중요한 질문입니다. 보통은 (A * 1000) / B를 하면 간단합니다. 하지만 이 펌웨어에서는 다음 두 가지 이유로 위와 같은 루프 방식을
  사용합니다.

   1. 오버플로우(Overflow) 방지:
       * 현재 변수 타입이 uint16_t (최대값 65,535)입니다.
       * 만약 Divedend가 ADC 측정값인 3000이라면, 여기에 1000을 곱하는 순간 3,000,000이 되어 16비트 범위를 훌쩍 넘어가 버립니다.
       * 루프 방식을 쓰면 중간 계산값이 항상 Divisor * 10 수준을 넘지 않으므로 안전합니다.

   2. STM8L의 성능 최적화:
       * 8비트 MCU인 STM8은 32비트 나눗셈이나 실수 연산이 매우 느리고 코드 용량을 많이 차지합니다.
       * 위 방식은 단순한 16비트 나눗셈과 곱셈만 반복하므로 매우 효율적입니다.

  결론
  이 함수는 "16비트라는 좁은 방 안에서 오버플로우 없이 소수점 셋째 자리까지 정밀한 나눗셈 결과(정수 형태)를 얻기 위한 최적의
  알고리즘"입니다.

  이렇게 얻은 결과값(1250 등)은 Parameter_define.h에 정의된 1040, 1050 같은 임계값(Threshold)과 직접 비교하는 데 사용됩니다. (1.040, 1.050의
  의미)

  경우 잠재적인 위험 요소는 존재합니다.

  구체적으로 분석한 내용은 다음과 같습니다.

  1. 오버플로우(Overflow) 위험 분석
  이 함수에서 가장 위험한 부분은 Divedend = Divedend * 10;입니다.

   * 안전한 이유: STM8L의 ADC는 12비트(0~4095)입니다. 루프 내부에서 Divedend는 항상 Divisor보다 작은 상태(나머지 값)가 됩니다. 따라서
     Divedend * 10의 최대값은 약 4095 * 10 = 40,950 수준입니다.
   * 데이터 타입: Divedend는 uint16_t이므로 최대 65,535까지 저장할 수 있습니다. 즉, 40,950은 이 범위 안에 들어오므로 계산 과정에서 데이터가
     깨지지 않습니다.
   * 주의 사항: 만약 나중에 다른 용도로 사용하면서 Divisor 값이 6,554 이상인 데이터를 넣게 되면, 6554 * 10 = 65,540이 되어 오버플로우가
     발생하고 계산 결과가 엉뚱하게 나올 수 있습니다.

  2. 연산 범위(Magnitude)의 한계
   * 결과값 한계: 결과인 Quotient 역시 uint16_t입니다.
   * 만약 Divedend가 Divisor보다 65배 이상 크다면 (예: 6500 / 100), 결과값은 65,000을 넘게 되어 오버플로우가 발생합니다.
   * 하지만 광학 센서 특성상 측정값(Divedend)이 기준값(Divisor)의 65배가 되는 상황은 센서 고장이 아닌 이상 발생하기 어렵기 때문에, 실제
     사용에는 문제가 없습니다.

  3. 반올림이 아닌 '버림(Truncation)'
   * 이 함수는 소수점 넷째 자리에서 반올림하는 것이 아니라 그냥 버립니다.
   * 예를 들어 실제 계산값이 1259.9라면, 수학적으로는 1260이 맞지만 이 함수는 1259를 반환합니다.
   * 의료 기기 판정 로직에서는 일관성이 중요하므로, 모든 데이터에 동일한 '버림'이 적용된다면 임계값(Threshold) 설정 시 이를 감안했을
     것이므로 버그라고 보기는 어렵습니다.

  4. 제로 나누기(Division by Zero) 방어
   * if(Divedend && Divisor) 조건문이 있어, Divisor가 0일 때 시스템이 멈추거나 에러가 발생하는 것을 방지하고 0을 반환하도록 되어 있습니다.
     이는 임베디드 환경에서 매우 바람직한 예외 처리입니다.

  요약
   * 버그인가? 아닙니다. 12비트 ADC 값을 처리하기 위해 메모리와 연산 속도를 최적화한 기법입니다.
   * 문제가 생길 조건: 입력 파라미터가 6554를 넘어가거나, 결과값이 65535를 넘어가는 매우 큰 수의 나눗셈을 할 때는 사용할 수 없습니다.
   * 현재 프로젝트에서는? ADC 값이 4095 이하이므로 아무 문제 없이 정상 동작합니다.
