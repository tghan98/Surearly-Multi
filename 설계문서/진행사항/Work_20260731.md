# 작업 일지 - 2026-07-31

**프로젝트:** Surearly Multi / MFx_New_Ver
**MCU:** STM8L151F3 / IAR Embedded Workbench (STM8)
**주제:** ① PTR 광센서(PT11-21C/L41/TR8) ADC 이상 현상 조사 — 센서 불량 여부 판정 / ② 스틱 삽입 스위치(STP_CK) 오동작 문제 해결 (OPTIC_CH_3 기반 판정으로 전환)

## 1. 증상 발견 (2026-07-30)

PTR 포토트랜지스터 `PT11-21C/L41/TR8` 사용 보드에서 LED Duty 50%/100% 조건으로 ADC 값을 확인하던 중 이상 발견.

- **정상 기대치:** Duty 50% → 1000~2000, Duty 100% → 2000~4000
- **문제 보드 실측치:** Duty 50%/100% 모두 **800 이하**로 출력

### 1-1. 1차 조치 및 결과

문제 보드에서 센서를 분리하여 다른(정상) 보드의 센서와 맞바꿔 테스트.

- 정상 보드 센서 → 문제 보드에 장착: 정상 출력
- 문제 의심 센서 → 정상 보드에 장착: 비정상 출력 (문제가 센서를 따라다님)

**1차 결론:** 보드/펌웨어 문제가 아니라 **센서 부품 로트 불량**. 문제 센서 교체 후 테스트 기기 5대 모두 정상 동작 중.

## 2. 센서 회로 및 스펙 검토

### 2-1. 회로 구성 확인

```
GPIO(MCU, 2.5V, 센서전원 ON/OFF)
        │
        ▼
     Collector
   PT11-21C/L41/TR8 (포토트랜지스터, 베이스리드 없음)
     Emitter
        │
        ├──────► ADC 입력 (MCU)
        │
       100kΩ ║ 22nF (병렬, GND로)
```

- GPIO는 측정 시에만 Collector에 전원 공급하는 **센서 전원 스위치** 역할(절전 목적)
- 포토트랜지스터는 반사광량에 비례한 광전류(IC)를 Collector→Emitter로 흘리는 **전류원**
- Emitter의 100kΩ이 광전류를 전압으로 변환(`V_ADC = IC × 100kΩ`), 22nF는 RC 저역통과 필터(τ≈2.2ms, 노이즈 억제)

### 2-2. 데이터시트 `Collector-Emitter Saturation Voltage (VCE(sat))` 검토

- 스펙: `IC=2mA, Ee=1mW/cm²` 조건에서 **Max 0.4V**
- 의미: 빛을 받아 완전히 도통(saturation)된 상태에서 남는 잔류 전압. 낮을수록 "확실하게 켜짐" 상태
- 본 회로(VCC=2.5V, 부하 100kΩ)에서는 `(VCC - VCE(sat)) / 100kΩ ≈ 21µA` 이상의 광전류가 요구되는 조건에서 트랜지스터가 포화되어 ADC 출력이 `VCC - VCE(sat)`(약 2.1V) 근방에서 클리핑되는 상한 요인으로 작용 — 이번 조사의 핵심은 아니지만 회로의 동적범위 상한을 결정하는 값으로 확인.

### 2-3. 측정 방법 확인

동일 채널에서 **20회 샘플링 → 정렬 → Min/Max 각 1개(총 2개) 제외 → 나머지 16개 합산**하여 결과값으로 사용 (평균이 아닌 합산값).

## 3. 편차 vs 불량 판정 (추가 사례)

같은 LED 조건에서 센서별 결과값 비교:

| 조건 | 정상으로 보이는 센서 | 문제 의심 센서 | 비율 |
|---|---|---|---|
| Duty 50% | 1398 | 156 | 약 9.0배 |
| Duty 100% | 2795 | 419 | 약 6.7배 |

### 판단 근거

- 데이터시트 `On State Collector Current (IC(ON))` 스펙: `VCE=5V, Ee=1mW/cm²` 조건에서 **Min 0.3mA / Typ 0.8mA** → 제조사가 인정하는 정상 개체차는 최대 **약 2.7배(0.8/0.3)** 수준
- 실측 편차(6.7~9배)는 이 정상 개체차 범위를 **2.5~3배 이상 초과**
- 각 센서 내부적으로는 Duty 50%→100% 시 비율이 2.0배/2.69배로 자체적으로는 일관(선형)되게 반응 → 접촉불량 등 "튀는" 문제가 아니라 감광 감도 자체가 전반적으로 낮은 다이(die) 특성 문제로 판단

**결론: 정상 부품 편차 범위를 벗어난 스펙 미달 불량으로 판정.** (2026-07-30 로트 불량 사례와 동일 계열의 재발 사례로 봄)

## 6. 스틱 삽입 스위치(STP_CK) 오동작 문제 해결

### 6-1. 회로 및 증상

```
STM8L151F3 GPIO(PB1, External Interrupt, INPUT)
        │
      스위치 (누르면 GND 연결)
        │
       100kΩ
        │
      VCC(2.5V)
```

Halt 모드는 이 핀의 EXTI(하강 에지)로 wake-up 가능하나, **기구적 문제로 스틱이 삽입된 상태에서도 스위치 접점이 지속적으로 눌리지 못하고 순간적으로 분리**될 수 있음 — 삽입 상태인데 REMOVE로 오판되는 문제.

기존 대응(10ms 틱 기준 150ms 연속 유지 시 확정하는 카운트 기반 디바운스)로는 해결이 안 되어, 이미 `DM_App_Stick_Get_Status()`를 무조건 `STICK_STATUS_INSERTED`만 반환하도록 임시 블록해둔 상태였음(기존 디바운스 결과를 사실상 무시).

### 6-2. 해결 방향 검토

검토한 옵션:
- A. INSERT/REMOVE 비대칭 디바운스 시간 (REMOVE 확정만 길게)
- B. 시퀀스의 안전한 체크포인트에서만 반영
- C. 옵틱(반사광) 센서로 교차 검증

→ **옵션 C로 결정.** `OPTIC_CH_3`(LED1 + ADC Rear, 4채널 중 가장 안쪽 센서)는 스틱이 실제로 끝까지 삽입돼야만 반사체가 광경로에 존재하므로, Duty 100%에서 ADC가 1000 미만이면 스틱이 없는 것으로 판단 가능. 기구적 유격의 영향을 받는 스위치와 달리 광학적으로 직접 "물체가 그 자리에 있는지"를 보므로 접점 문제 자체가 없음. **STP_CK 스위치는 Halt wake-up 트리거 전용으로만 사용**하기로 확정.

### 6-3. 구현 ① — OPTIC_CH_3 기반 스틱 상태 판정 함수

- `Parameter_define.h`: `OPTIC_STICK_REMOVE_THRESHOLD`(1000), `OPTIC_STICK_CHECK_INTERVAL_MS`(1000) 신규 추가(추후 조정 가능하도록 define화)
- `DM_Optic_Handle_App.c`/`.h`: `DM_App_Optic_Check_StickPresent()` 신규 추가 — OPTIC_CH_3를 PWM 399(Duty100%)로 즉시 1회 실측(캐시 없음), 임계값과 비교해 존재 여부 반환. 일회성 체크(wake-up 확인 등) 용도.
- `DM_LCD_Stick_Check_App.c`:
  - 기존 GPIO 디바운스 메커니즘 전체 삭제: `DM_App_Stick_Process_Debounce()` 함수, `gs_tStick_Status`/`gs_wStick_DebounceCounter`/`gs_tStick_LastRawState` 정적 변수, `STICK_DEBOUNCE_MS`/`STICK_DEBOUNCE_COUNT` 정의. (`Get_Status()`가 이미 항상 INSERTED만 반환해 그 결과가 어차피 안 쓰이던 죽은 코드였음)
  - `User_Main.c`의 TIM4 ISR(10ms)에서 `DM_App_Stick_Process_Debounce()` 호출 제거
  - `DM_App_Stick_Get_Status()`를 `DM_App_Optic_Check_StickPresent()` 기반으로 재작성. 단, 매 호출마다 실측하면(호출부가 10ms 대기 루프 안에 있어) LED/PTR이 10ms마다 켜졌다 꺼지는 문제가 있어, `OPTIC_STICK_CHECK_INTERVAL_MS`(1000ms)마다 한 번만 재측정하고 그 사이엔 캐시값을 반환하는 스로틀 적용.

### 6-4. 구현 ② — 대기 루프 중복 코드 헬퍼화

`DM_Main_Sq_App.c`에 `DM_App_Main_Sq_Sleep_And_CheckStick(bErrCode, tLcdErrStep)` 헬퍼 추가(10ms 대기 + 상태 체크 + 에러 진입을 한 번에 처리). 아래 5곳에 적용해 각각 4~5줄 → 3줄로 축소:

- `Stick_Insert_Step_Handler`(LCD 애니메이션 완료 대기 루프)
- `Sample_Load_Wait_Step_Handler`(내부 100ms 사이클 루프)
- `Over_Sample_Check_Step_Handler`
- `Low_Sample_Check_Step_Handler`
- `Reaction_Wait_Step_Handler`

체크의 위치/주기(각 대기 루프 안, 매 10ms)는 그대로 유지. 검토 중 "체크를 `DM_App_Main_Sq_Process()` 최상단으로 옮기고 루프 내부에서는 제거하면 어떨지" 논의가 있었으나, 이 함수는 스텝 핸들러 내부의 블로킹 루프(최대 5분/3분 등) 때문에 한 번 진입하면 그 스텝이 끝날 때까지 되돌아오지 않는 구조임을 확인 — 체크를 바깥으로 옮기면 긴 대기 도중의 실제 제거가 완전히 감지되지 않게 되므로 그 방향은 폐기하고 현재 방식(루프 내부, 매 tick) 유지로 결정.

`DM_Optic_Handle_App.c` 안의 4곳(`MeasureInitialStick`/`TuneTargetADC`/`MeasureEmptyPTR`)은 이미 채널 측정 단위로 체크하는 다른 패턴이라 대상에서 제외.

### 6-5. 구현 ③ — Wake-up 직후 스틱 확인 로직 정정

`DM_App_Main_Sq_Idle_Step_Handler()`에 `#if 0`로 막혀 있던 구식 코드(TIM4 수동 enable + `GetSystemTick()` 기준 50틱(500ms) 대기 + 옛 스위치 디바운스 상태 체크)를 제거하고 다음으로 교체:

- `DM_HW_Drv_Power_Resume()` 직후 10ms 대기(ADC/클럭 안정화)
- `DM_App_Optic_Check_StickPresent()`를 **직접** 호출 (※ `DM_App_Stick_Get_Status()`가 아님 — 그쪽은 캐시가 있어서 Halt 진입 전의 낡은 값을 반환할 위험이 있어 wake 확인 용도에는 부적합하다고 판단해 우회)
- 삽입 확인되면 `MAIN_SQ_STICK_INSERT`로 진행, 아니면 `MAIN_SQ_IDLE`로 유지되어 다음 `DM_App_Main_Sq_Process()` 호출 시 이 핸들러가 재진입되어 다시 Halt 모드로 복귀

### 6-6. 결론

STP_CK 스위치는 Halt wake-up 트리거 전용으로 역할이 축소되고, 실질적인 스틱 삽입/제거 판정은 전부 OPTIC_CH_3 광학 측정 기반으로 전환됨. 기구적 접점 불량으로 인한 오탐(삽입 중 REMOVE 오판) 문제가 근본적으로 해결될 것으로 기대.

**하드웨어 검증 완료 (2026-07-31):** 실물 보드로 테스트한 결과 스틱 인서트/리무브가 정상 동작함을 확인. (8절의 캐시 우회 전환, 8-4절의 `OPTIC_STICK_CHECK_INTERVAL_MS` 250ms 조정까지 반영된 최종 버전 기준)

## 7. Wake-up 인터럽트 / Halt 모드 설정 확인

### 7-1. Falling Edge 인터럽트 설정 검증

`DM_HW_Drv.c`의 `DM_HW_Drv_SystemHalt_WakeupOnStick()` 코드 재검토:

```c
GPIO_Init(STP_CK_PORT, STP_CK_PIN, GPIO_Mode_In_PU_IT);   /* PB1, Pull-up + 인터럽트 입력 */
EXTI_SetPinSensitivity(EXTI_Pin_1, EXTI_Trigger_Falling); /* Pin1 → Falling Edge */
```

`STP_CK_PORT`/`STP_CK_PIN`(`main.h`: `GPIOB`/`GPIO_Pin_1`)과 `EXTI_Pin_1`이 정확히 일치하고 트리거도 `EXTI_Trigger_Falling`으로 설정되어 있어, **wake-up이 하강엣지 인터럽트로 정상 발생하도록 구성되어 있음을 확인.**

### 7-2. `wfi()`/`halt()` 관련 확인 (의도된 상태)

같은 함수 마지막 부분에서 다음을 발견:

```c
/* Enter Halt Mode */
//halt();
wfi();
```

함수명/주석은 "Halt Mode"이나 실제로는 진짜 Halt 진입 명령(`halt()`)이 주석 처리되어 있고 저전력 정도가 낮은 `wfi()`(Wait For Interrupt)만 호출됨. 사용자 확인 결과 **의도적인 설정** — 개발 중 IAR 디버거 연결을 유지하기 위한 것(`halt()`는 디버거 연결이 끊김). 버그 아님. **단, 양산/최종 빌드 전에는 `halt()`로 되돌려야 함** — 사용자가 직접 판단해 전환할 예정, 먼저 나서서 수정하지 않기로 함.

## 8. Optic 함수 내 스틱 체크 방식 개선 — 캐시 우회로 전환

### 8-1. 문제 인지

`DM_Optic_Handle_App.c`의 4곳 가드 체크(`MeasureInitialStick` 2곳, `TuneTargetADC` 1곳, `MeasureEmptyPTR` 1곳)가 여전히 `DM_App_Stick_Get_Status()`(1초 스로틀 캐시)를 사용 중이었음. 이 함수들의 체크 간격(채널당 약 0.6~3초)이 스로틀 창(1초)과 비슷하거나 더 길어서, 스로틀로 얻는 성능 이득은 거의 없으면서 "직전에 스틱이 빠졌는데 최대 1초 전의 낡은 캐시값을 그대로 믿어버릴" 리스크만 남는 상황임을 확인.

### 8-2. 조치

4곳 모두 `DM_App_Optic_Check_StickPresent()` 직접 호출(캐시 우회, 항상 신선한 측정)로 교체:

- `MeasureInitialStick` — 채널 루프 가드 + EEPROM 저장 전 최종 체크
- `TuneTargetADC` — 채널 루프 가드(4-4절 절충안으로 이미 채널당 1회로 줄여둔 지점)
- `MeasureEmptyPTR` — 채널 루프 가드

이 파일에서 더 이상 `STICK_STATUS_t`/`DM_App_Stick_Get_Status()`를 쓰지 않게 되어 `#include "DM_LCD_Stick_Check_App.h"`도 함께 제거. 결과적으로 `DM_Optic_Handle_App`은 `DM_LCD_Stick_Check_App`에 의존하지 않는 단방향 의존 구조가 됨 (반대 방향, `DM_LCD_Stick_Check_App` → `DM_Optic_Handle_App`만 유지).

### 8-3. "EEPROM 저장 전 최종 체크" 유지 여부 검토

`MeasureInitialStick`의 EEPROM 저장 직전 체크가 "저장 자체는 금방 끝나니 불필요한 게 아니냐"는 질문이 있었으나, 검토 결과 이 체크는 저장 소요시간과 무관하고 **루프의 마지막 채널(`bCh=3`) 측정 중(~1.2초) 제거된 경우를 잡아주는 유일한 지점**임을 확인 — 다른 채널의 "측정 중" 제거는 다음 채널 진입 시 가드가 잡아주지만 마지막 채널 뒤에는 이 체크 말고 다른 가드가 없음. 제거하지 않고 그대로 유지하기로 결정.

### 8-4. `OPTIC_STICK_CHECK_INTERVAL_MS` 조정

`Parameter_define.h`의 `OPTIC_STICK_CHECK_INTERVAL_MS`를 1000 → **250**으로 변경. `DM_Main_Sq_App.c`의 5곳(대기 루프 안, 매 10ms 호출)이 쓰는 `DM_App_Stick_Get_Status()` 캐시 스로틀 주기에만 영향(더 자주 재측정하여 반응성 향상). `DM_Optic_Handle_App.c`의 4곳은 8-2절에서 이미 이 캐시를 우회하도록 바꿔둬서 영향 없음.

## 9. `MeasureInitialStick()` 초기 측정값 범위 검증 추가

### 9-1. 요구사항

`DM_App_Optic_MeasureInitialStick()`이 채널당 PWM199(Duty50%)/PWM399(Duty100%) 두 값을 측정만 하고 별도 검증 없이 저장하던 것을, 다음 정상 범위를 벗어나면 실패로 판정하도록 변경:

- Duty 50%(199): **900~2100**
- Duty 100%(399): **1800~4200**
- 벗어나면 해당 채널의 `ERROR_OPTIC_FAIL_CH0`~`CH3`, LCD는 `LCD_SQ_ERR_STICK_FAIL`

### 9-2. 구현

- `Parameter_define.h`: `OPTIC_INITIAL_MIN_50`(900)/`OPTIC_INITIAL_MAX_50`(2100)/`OPTIC_INITIAL_MIN_100`(1800)/`OPTIC_INITIAL_MAX_100`(4200) 신규 추가
- `DM_Optic_Handle_App.c`의 `MeasureInitialStick()`: 채널당 두 값 측정 직후 범위 체크, 벗어나면 `(uint8_t)(FAIL_OPTIC_CH0 + bCh)` 리턴 — `TuneTargetADC`의 튜닝 실패 시 쓰는 코드와 동일한 값(0x10~0x13, `DM_Main_Sq_App.h`의 `ERROR_OPTIC_FAIL_CH0`~`CH3`와 일치)을 재사용
- `DM_Main_Sq_App.c`: `MeasureInitialStick` 호출부에 `else if (bResult != OPTIC_SUCCESS) { DM_App_Main_Sq_Enter_Error(bResult, LCD_SQ_ERR_STICK_FAIL); return; }` 분기 추가 — 검토 중 이 분기가 원래 빠져 있어서(바로 아래 `TuneTargetADC` 호출부엔 있었음) 새 실패코드가 무시되고 그냥 다음 단계로 넘어가 버리는 문제를 발견해 함께 수정

### 9-3. 하드웨어 검증

`LCD_SQ_ERR_STICK_FAIL` 애니메이션이 실물 보드에서 정상 표시됨을 확인.

## 10. Sample_Load_Wait 타임아웃 후 DROP 아이콘이 꺼지지 않는 버그 수정

### 10-1. 증상

`DM_App_Main_Sq_Sample_Load_Wait_Step_Handler()`가 5분 타임아웃으로 `MAIN_SQ_IDLE`로 전환되어 Halt(슬립)에 들어가야 하는데, **DROP 아이콘이 계속 켜진 채로 남아있음.**

### 10-2. 원인

`DM_HW_Drv_Power_PrepareSleep()`(`DM_HW_Drv.c`)이 슬립 진입 전 LCD 세그먼트 핀들을 강제로 LOW로 리셋하는데, 4개 세그먼트 중 **SEG0/1/2 3개만 리셋하고 SEG3 리셋이 누락**되어 있었음. `main.h`의 핀 매핑상 `LCD_DROP_PORT/PIN`이 정확히 `LCD_SEG3_GPIO_PORT/PIN`(GPIOB, Pin0)에 해당 — DROP이 켜져 있던(HIGH) 상태 그대로 방치되어, LCD refresh(TIM4)가 멈춘 뒤에도 그 전압이 그대로 남아 DROP만 계속 켜진 것처럼 보임. MCU 자체는 정상적으로 Halt 진입했을 가능성이 높고, 이 LCD 핀 하나의 누락이 원인.

### 10-3. 수정

`DM_HW_Drv_Power_PrepareSleep()`의 LCD 핀 리셋 블록에 누락된 한 줄 추가:

```c
GPIO_ResetBits(LCD_SEG3_GPIO_PORT, LCD_SEG3_GPIO_PIN);
```

## 11. 대기 루프 타이밍 부정확 버그 수정 — 반복 횟수 카운트 → `GetSystemTick()` 실측 시간 기준

### 11-1. 증상 발견

`DM_App_Main_Sq_Sample_Load_Wait_Step_Handler()`의 5분 대기가 코드상으로 정말 정확히 5분이 맞는지 질문이 있어 확인.

### 11-2. 원인

`dwWaitTimer`(및 다른 3곳의 `for (i=0; i<TIME; i++)`)는 **"루프를 몇 번 돌았는지"**를 세는 카운터일 뿐, 실제 경과 시간이 아님. 그런데 각 반복 안에서 호출하는 `DM_App_Main_Sq_Sleep_And_CheckStick()`은 내부적으로 `DM_App_Stick_Get_Status()`를 호출하는데, 이게 `OPTIC_STICK_CHECK_INTERVAL_MS`(250ms) 스로틀 때문에 **약 25번에 1번꼴로 실제 옵틱 측정(~600ms)을 수행**함 — 그런데도 카운터는 매번 "1"씩만 감소.

**계산:** 25회 주기당 실제 경과시간 = 24×10ms + 1×610ms = 850ms인데 카운터는 250(=25×10ms)만큼만 깎임 → **실제 소요시간이 의도한 시간의 약 3.4배**로 부풀려짐.

| 구간 | 설계 의도 | 실제(약 3.4배) |
|---|---|---|
| Sample_Load_Wait | 5분 | ~17분 |
| Over_Sample_Check | 5초 | ~17초 |
| Low_Sample_Check | 20초 | ~68초 |
| Reaction_Wait(나머지) | 155초 | ~527초 |

같은 헬퍼(`DM_App_Main_Sq_Sleep_And_CheckStick`)를 쓰는 4곳(Sample_Load_Wait, Over_Sample_Check, Low_Sample_Check, Reaction_Wait) 전부 동일한 문제. 이 기기가 반응시간이 화학적으로 의미있는 진단기기(배란테스트)라 판정 정확도에 영향을 줄 수 있는 문제로 판단.

(참고: `Stick_Insert_Step_Handler`의 LCD 애니메이션 대기 루프는 반복 횟수가 아니라 "애니메이션이 끝났는지"로 종료하는 이벤트 기반 대기라 이 버그와 무관 — 대상에서 제외.)

### 11-3. 수정

4곳 모두 반복 횟수 카운팅 대신 `GetSystemTick()`(10ms 단위 실제 경과 틱 — TIM4 인터럽트로 증가하며, 옵틱 측정 내부의 sleep 호출에도 똑같이 반영되어 실제 시간을 정확히 추적) 기준으로 종료 조건 변경:

```c
uint32_t dwStartTick = GetSystemTick();
while ((GetSystemTick() - dwStartTick) < TIME_CONST)
{
    if (DM_App_Main_Sq_Sleep_And_CheckStick(...)) { return; }
}
```

- `Sample_Load_Wait_Step_Handler`: 외부 `while(dwWaitTimer>0)` → `while((GetSystemTick()-dwStartTick) < SAMPLE_LOAD_WAIT_TIME)`. 내부 ~100ms 측정 주기용 서브루프(10회)는 구조 유지, 종료조건만 틱 기준으로 변경
- `Over_Sample_Check_Step_Handler` / `Low_Sample_Check_Step_Handler`: `for` 카운팅 루프 → `while` + 틱 비교로 교체, 더 이상 안 쓰는 `i` 변수 제거
- `Reaction_Wait_Step_Handler`: `#else` 분기를 중괄호 스코프로 감싸 `dwStartTick`을 그 안에서 선언, `i`는 `_DEBUG_LCD_SEQ_ONLY` 전용으로 그 분기 안으로 이동(실빌드 미사용 변수 경고 방지)

### 11-4. 매직넘버 정리

`Sample_Load_Wait_Step_Handler`만 5분 값(`30000`)이 다른 3곳(`OVER_SAMPLE_CHECK_TIME`, `LOW_SAMPLE_CHECK_TIME`, `REACTION_WAIT_TIME`)과 달리 매직넘버로 직접 쓰이고 있던 것을 발견 — `DM_Main_Sq_App.h`에 `SAMPLE_LOAD_WAIT_TIME`(30000) 상수를 추가해 4곳 전부 이 이름으로 교체.

## 12. `Sample_Load_Wait`만 5분이 아니라 5분 37초가 걸리는 잔여 오차 조사 및 보정

### 12-1. 증상

11절 수정(`GetSystemTick()` 기반) 적용 후 실물 보드로 재검증한 결과, `Sample_Load_Wait`의 실제 대기시간이 여전히 5분이 아니라 **5분 37초**로 측정됨.

### 12-2. 원인

`DM_HW_Drv_ADC_Read()`의 실제 ADC 변환 대기(`while (DM_HW_Drv_ADC_GetConvDone()==0) wfi();`)는 **`DM_HW_Drv_SystemSleep_10ms()`를 거치지 않고 ADC 자체의 EOC 인터럽트로 깨어나는 별도의 `wfi()` 루프**라, `GetSystemTick()`(TIM4 기반)에 전혀 반영되지 않음. `Sample_Load_Wait`는 5분 내내 ~1.3초 주기로 `DM_App_Optic_Measure()`를 반복 호출(채널당 20샘플×2회 변환)하는 구조라 이 "안 잡히는 시간"이 누적됨. 반면 `Over_Sample_Check`/`Low_Sample_Check`/`Reaction_Wait`는 대기 종료 후 **딱 1번만** 측정하므로 같은 누수가 무시할 수준(수십 ms)에 그쳐 이 문제가 `Sample_Load_Wait`에서만 크게 나타남.

계산상 순수 ADC 변환시간(2MHz 클럭, 384사이클 샘플링)만으로는 5분간 약 4초 수준으로 추정되어, 관찰된 37초와는 차이가 있음 — `wfi()` 웨이크업 지연 등 코드만으로 정확히 특정하기 어려운 추가 오버헤드가 있는 것으로 보이나, 정확한 세부 배분은 실측(37초)으로 대신함.

### 12-3. 검토했던 해결 방향과 최종 선택

- **(검토 후 보류) TIM4 상시 구동**: `GetSystemTick()`을 완전한 실시간 시계로 만드는 근본적인 방법이지만, 배터리 저전력 설계와 충돌(TIM4를 매 `SystemSleep_10ms()` 호출 시에만 켜고 끄는 현재 구조가 절전 목적) — 채택하지 않음.
- **(검토 후 보류) ADC 변환시간을 소프트웨어로 미세 보정**: `DM_HW_Drv_ADC_Read()`가 호출될 때마다 알려진 고정 변환시간(µs 단위)을 별도 누적기에 더하고, 10ms(=1틱)를 넘으면 `GetSystemTick()`의 틱에 편입시키는 방식(`User_Main.h`에 `SystemTick_AddUntracked_us()` 선언까지 추가했었음) — 정밀하지만 구현이 다소 복잡하다고 판단해 보류, 관련 선언은 다시 제거.
- **(최종 채택) 실측 기반 단순 보정값 적용**: `DM_Main_Sq_App.h`에 `SAMPLE_LOAD_WAIT_NOMINAL`(30000, 5분 목표)과 `SAMPLE_LOAD_WAIT_CORRECTION`(3700, 실측 37초 보정값)을 별도 define으로 분리하고, `SAMPLE_LOAD_WAIT_TIME = (SAMPLE_LOAD_WAIT_NOMINAL - SAMPLE_LOAD_WAIT_CORRECTION)`으로 정의. 코드(`Sample_Load_Wait_Step_Handler`)는 `SAMPLE_LOAD_WAIT_TIME`을 그대로 참조하므로 수정 불필요, 나중에 실측값이 달라지면 `SAMPLE_LOAD_WAIT_CORRECTION`만 조정하면 됨.

## 13. `DM_HW_Drv_ADC_Read()` 검토 — 전류 소모 분석 및 변환 횟수 절반 절감

### 13-1. 검토 배경

`DM_HW_Drv_ADC_Read()`는 채널당 매 샘플마다 `ADC_ChannelCmd(ENABLE)` → 2회 변환(1회 버림+1회 사용) → `ADC_ChannelCmd(DISABLE)`을 반복하는 구조. 배터리(CR1632 코인셀) 절전 설계 관점에서 이 방식이 맞는지 검토.

### 13-2. 데이터시트(`STM8L151F3.pdf`) 기반 전류 소모 분석

- Table 26 (71p) `IDD(ADC1)` = **1500 µA/MHz** (Typ, VDD=3.0V) — 각주: *"continuous ADC1 conversion"* 측정 기준. 다른 페리페럴(TIM2/3=8, USART1=6, 전체 합계=38 µA/MHz)과 비교해 압도적으로 큰 전류원.
- 현재 설정(시스템클럭 2MHz, `ADC_Prescaler_1`) → **fADC1 = 2MHz → ADC 활성 중 추가 전류 ≈ 3mA**
- 단, 이 1500µA/MHz는 **"Enable 상태"가 아니라 "실제 변환 중"에만 해당** — `ADC_Cmd(ADC1, ENABLE)`로 켜놓고 변환은 안 하는 대기 상태는 훨씬 작은 기준 전류만 소모.
- Table 48 (95p) 기준 변환시간 tconv = (12+384)/2MHz ≈ 198µs/회 → 2회 변환(현재 방식) 시 396µs/샘플 동안 3mA 소모.

### 13-3. 최적화: 채널 select/deselect를 버스트 단위로, 버림용 변환 제거

- 채널을 매 샘플(20회)마다 enable/disable 하면서, 그 때마다 "1회 버림+1회 사용" 2회 변환 → 총 40회 변환
- **`DM_App_Optic_Measure()`가 이미 20샘플을 정렬해서 상위/하위 3개씩(총 6개) 버리고 중간 14개만 합산**하고 있으므로, 채널을 버스트(20샘플) 시작 시 한 번만 select하면 채널 전환으로 인한 첫 샘플 불안정 문제가 있어도 이 기존 이상치 제거 로직이 자연스럽게 흡수 — 별도 버림용 변환이 불필요하다고 판단
- `DM_HW_Drv_ADC_Read(channel)` 1개 함수를 `DM_HW_Drv_ADC_ChannelSelect(channel)` / `DM_HW_Drv_ADC_Read(void)` / `DM_HW_Drv_ADC_ChannelDeselect(channel)` 3개로 분리
- `DM_App_Optic_Measure()`: 20샘플 루프 진입 전 `ChannelSelect()` 1회, 루프 종료 후 `ChannelDeselect()` 1회, 루프 내부는 `DM_HW_Drv_ADC_Read()`만 호출(버림 로직 삭제)

**결과: 채널당 변환 횟수 40회 → 20회로 절반 감소**, 3mA 스파이크가 흐르는 총 누적 시간도 절반으로 줄어듦. 부수 효과로 12절의 "ADC 변환시간이 `GetSystemTick()`에 안 잡히는" 오차 크기도 대략 절반 수준으로 줄어들 것으로 예상(추가 실측 필요).

## 14. 배터리/LDO 디커플링 콘덴서가 ADC 순간전류를 버퍼링할 수 있는지 검토

### 14-1. 배경

CR1632 코인셀 + 10µF(배터리단), LDO 2.5V 출력 + 10µF/1µF(LDO 출력단) 구성에서, ADC 변환 중 순간적으로 흐르는 ~3mA(13절)를 이 콘덴서들이 버퍼링할 수 있는지 검토.

### 14-2. 계산

- ADC 변환시간 tconv ≈ (12+384사이클)/2MHz ≈ 198µs
- LED 전류: `I_LED = (VDD-Vf)/R = (2.5V-2V)/510Ω ≈ 0.98mA` (Vf=2V로 실측 확인됨)
- LED PWM(5kHz, 주기 200µs)과 ADC 변환시간(198µs)이 비슷한 길이라 최악의 경우 겹칠 수 있음 → 합산 피크전류 `I_peak ≈ 0.98mA(LED) + 3mA(ADC) + ~0.5mA(MCU 기본) ≈ 4.5mA`
- 전하량 `Q = I × t = 4.5mA × 198µs ≈ 0.891µC`
- 전압강하: LDO 출력단(11µF) ΔV ≈ 81mV(2.5V 대비 ~3.2%), 배터리단(10µF) ΔV ≈ 89mV

### 14-3. VDDA 하한 관련 정정 — ADC 정확도는 1.8V가 아니라 2.4V가 기준

`STM8L151F3.pdf` Table 48~51 재확인 결과, ADC 동작 보장 최소전압은 1.8V이지만, **정확도(TUE 등) 스펙은 2.4V를 기준으로 등급이 나뉨**:

| VDDA 구간 | TUE Max |
|---|---|
| 2.4~3.6V | 4 LSB |
| 1.8~2.4V (zooming 모드, fADC1 최대 16MHz→8MHz 제한) | 5 LSB |

즉 "1.65~1.8V까지 여유가 크다"는 초기 판단은 MCU 코어 동작 하한 기준이었고, **ADC 정밀도 유지 기준으로는 2.4V가 실질적 하한**. VDD=2.5V 대비 여유는 100mV뿐이라, 계산된 강하폭(81~89mV)과 거의 맞닿아 있음 — 실측(ESR, LDO 과도응답, 배터리 노후화 등 계산에 못 넣은 요소)에 따라 변환 순간 2.4V 밑으로 내려갈 가능성을 배제할 수 없음. 오실로스코프로 변환 순간 VDDA 실측 확인 필요.

### 14-4. 듀티 사이클과 피크전류의 관계

실제 운용 시 LED PWM 듀티는 100%가 아니라 튜닝값(대략 50%대)으로 설정됨. 다만 **듀티는 "평균 전류"(배터리 총 소모량)만 줄이고, LED가 켜진 순간의 "피크 전류"(0.98mA)는 듀티와 무관하게 동일** — PWM은 켜짐/꺼짐 비율만 바꿀 뿐, 켜졌을 때의 전류 크기는 바꾸지 않기 때문. 따라서 콘덴서 강하폭 계산(최악의 순간 피크 기준)은 듀티 설정과 무관하게 그대로 적용됨.

### 14-5. 종합 결론

- LED+ADC 합산 피크전류 기준으로 콘덴서 용량 자체는 이론상 충분해 보임(강하폭 81~89mV)
- 다만 이 강하폭이 ADC 정확도 유지 마진(100mV)에 거의 맞닿아 있어, 실측 없이는 "문제없다"고 단정하기 어려움
- 최종 확인 필요: 오실로스코프로 ADC 변환 순간 VDDA 전압 실측

## 15. ADC 변환시간을 `GetSystemTick()`에 정확히 반영 — µs 단위 시간 보정 구현

### 15-1. 배경

12절에서 `Sample_Load_Wait`의 "5분→5분37초" 오차 원인이 `DM_HW_Drv_ADC_Read()`의 실제 ADC 변환 대기(`wfi()`, ADC 자체 EOC 인터럽트로 깨어남)가 `DM_HW_Drv_SystemSleep_10ms()`를 거치지 않아 `GetSystemTick()`에 전혀 안 잡히기 때문임을 확인했었음. 당시엔 이 문제를 근본적으로 고치는 대신 **실측 기반 고정 보정값**(`SAMPLE_LOAD_WAIT_CORRECTION`=3700, 37초)으로 임시 처리했었음.

이후 13절에서 `DM_HW_Drv_ADC_Read()`의 정확한 변환시간을 데이터시트로 계산: `t_conv = (12+384사이클)/2MHz ≈ 198µs` (→ 200µs로 반올림). 이 값이 정확하고 결정론적(deterministic)이라는 점에 착안해, **이번엔 매 ADC 변환마다 이 알려진 시간을 직접 `GetSystemTick()` 기준에 더해주는 방식**으로 근본적으로 해결하기로 함.

### 15-2. 1차 설계와 문제 발견 — ISR-foreground 레이스 컨디션

처음 제안한 방식:
```c
void SystemTick_AddUntracked_us(uint16_t wMicroseconds)
{
    gs_dwUntrackedTime_us += wMicroseconds;
    while (gs_dwUntrackedTime_us >= 10000)
    {
        gs_dwSystemTick_10ms++;        // ← 문제: TIM4 ISR도 이 변수를 증가시킴
        gs_dwUntrackedTime_us -= 10000;
    }
}
```
사용자가 직접 지적: `gs_dwSystemTick_10ms`는 원래 TIM4 인터럽트(ISR)에서만 증가되던 변수인데, 이 방식은 `DM_HW_Drv_ADC_Read()`(foreground, 메인 루프 코드)에서도 같은 변수를 증가시키게 됨. `uint32_t++`는 원자적 연산이 아니므로, foreground가 이 변수를 증가시키는 도중 TIM4 인터럽트가 끼어들면 한쪽의 증가가 유실되거나 값이 깨질 수 있는 **레이스 컨디션**이 발생함. 이 지적으로 최초 설계를 폐기.

### 15-3. 최종 설계 — "쓰기"가 아니라 "읽을 때 계산"

```c
static volatile uint32_t gs_dwSystemTick_10ms = 0;   /* ISR만 씀 */
static uint32_t gs_dwUntrackedTime_us = 0;            /* foreground만 씀 */

uint32_t GetSystemTick(void)
{
    return gs_dwSystemTick_10ms + (gs_dwUntrackedTime_us / 10000);
}

void SystemTick_AddUntracked_us(uint16_t wMicroseconds)
{
    gs_dwUntrackedTime_us += wMicroseconds;   /* 리셋하지 않고 계속 누적만 함 */
}
```

핵심 아이디어: `gs_dwSystemTick_10ms`에 값을 "이동/편입"시키는 동작(쓰기) 자체를 없애고, `GetSystemTick()`을 호출해 **읽는 시점에만** 두 변수를 더해서 계산하도록 바꿈. 이렇게 하면:
- `gs_dwSystemTick_10ms`는 여전히 ISR만 쓰기 때문에 레이스 없음(기존과 동일한 안전성)
- `gs_dwUntrackedTime_us`는 foreground(ADC_Read)만 쓰기 때문에 이것도 레이스 없음
- 서로 다른 변수를 각자 한쪽만 배타적으로 쓰므로 충돌 여지 자체가 없음

**"리셋 안 해도 되는 이유" (사용자 질문에 대한 답변, 기록용):** `gs_dwUntrackedTime_us`를 10ms(10000µs) 단위로 리셋하지 않고 계속 누적만 해도 정확한 이유는, `GetSystemTick()`의 정수 나눗셈(`/10000`)이 매번 나머지를 변수 안에 그대로 남겨두기 때문. 예를 들어 `gs_dwSystemTick_10ms=100`, `gs_dwUntrackedTime_us=25000`이면 `GetSystemTick()=100+2=102`(1020ms로 계산, 실제는 1025ms이나 5ms 나머지는 `gs_dwUntrackedTime_us`에 그대로 남아 다음 호출에서 자연히 반영됨) — 리셋하며 매번 "이동"시키는 것과 안 하고 매번 "다시 계산"하는 것은 수학적으로 결과가 동일. 오버플로 우려도 `uint32_t` 최대값(약 43억) 기준 200µs당 1회 증가로 약 2150만 회 호출이 필요해(하루 2000회 호출 가정 시 약 80년 이상 소요) 이 기기의 실사용 기간에서는 문제 되지 않음.

### 15-4. 구현

- `User_Main.h`/`.c`: `gs_dwUntrackedTime_us` 전역변수 추가, `GetSystemTick()`을 `gs_dwSystemTick_10ms + (gs_dwUntrackedTime_us/10000)`로 수정, `SystemTick_AddUntracked_us(uint16_t wMicroseconds)` 신규 추가(누적만 하고 리셋 안 함)
- `DM_HW_Drv.c`: `ADC_READ_TIME_US`(200) 정의 추가, `DM_HW_Drv_ADC_Read()`가 변환 완료 후 `SystemTick_AddUntracked_us(ADC_READ_TIME_US)` 호출하도록 수정
- `DM_Main_Sq_App.h`: 이제 ADC 변환시간이 `GetSystemTick()`에 정확히 반영되므로, 기존의 실측 기반 고정 보정값 `SAMPLE_LOAD_WAIT_CORRECTION`(3700, 37초)을 그대로 두면 이중 보정되어 5분보다 37초 짧게 끝나버림 — **0으로 재설정**(향후 재실측 없이 임의로 되살리지 말 것을 주석으로 명시)

### 15-5. 향후 확인 필요

이론상으로는 `Sample_Load_Wait`가 이제 실제로 5분에 훨씬 근접하게 동작해야 함 — 실물 보드로 재검증 필요.

## 16. 하드웨어 실측으로 타이밍 오차 근본 원인 규명 — `GetSystemTick()` 나눗셈 오버헤드 + TIM4 클럭 보정

### 16-1. 1차 재검증 — 소프트웨어 로직은 정확함을 실측으로 확인

15절 적용 후 사용자가 실물 보드로 재검증. `Sample_Load_Wait_Step_Handler()`의 타임아웃 직전 지점에 `g_TickCk = GetSystemTick() - dwStartTick;`을 추가해 브레이크포인트/변수 확인 방식(USART 사용이 어려운 상황이라 SWIM 디버거의 Watch/브레이크포인트로 대체)으로 측정:

- 스톱워치 실측: 5분 33초, 5분 35초 (2회)
- `g_TickCk` 값: **30028** (300.28초 — 의도한 30000/300초에 거의 정확히 일치)

**결론: `GetSystemTick()`의 카운팅 로직 자체는 정확함(오차 0.28초 수준, 루프 체크 주기에 의한 정상적인 오버슈트).** 그런데 실측 스톱워치(333~335초)와는 여전히 11% 정도 차이 — 이는 코드 로직 문제가 아니라 "10ms 틱"이라고 믿는 시간이 실제로는 10ms가 아니라는 뜻.

### 16-2. 원인 발견 — `GetSystemTick()`의 32비트 나눗셈이 예상외로 비쌈

`DM_HW_Drv_SystemSleep_10ms()` 재검토 중 발견: STM8은 32비트 나눗셈을 하드웨어로 지원하지 않아 컴파일러가 소프트웨어 루틴으로 처리하는데, 15절에서 추가한 `GetSystemTick()`의 `(gs_dwUntrackedTime_us / 10000)` 연산이 바로 이 32비트 나눗셈. `SystemSleep_10ms()`가 `GetSystemTick()`을 호출당 약 2~3회 호출하고, 이 함수 자체가 5분 대기 동안 약 3만 번 호출되므로, 나눗셈 1회당 약 1.1ms만 걸려도 `30000×1.1ms=33초` — 관찰된 33~35초 오차와 거의 정확히 일치. **15절에서 ADC 시간 추적 문제를 고치려고 추가한 코드가 새로운(그리고 더 큰) 오버헤드를 만든 것.**

### 16-3. 수정 — 나눗셈을 자주 호출되는 곳에서 드물게 호출되는 곳으로 이동

```c
static uint32_t gs_dwUntrackedTime_us = 0;   /* foreground 전용, 10000 미만 나머지 */
static uint32_t gs_dwUntrackedTicks = 0;     /* foreground 전용, 편입된 온전한 틱 수 */

uint32_t GetSystemTick(void)
{
    return gs_dwSystemTick_10ms + gs_dwUntrackedTicks;   /* 나눗셈 없이 덧셈만 */
}

void SystemTick_AddUntracked_us(uint16_t wMicroseconds)
{
    gs_dwUntrackedTime_us += wMicroseconds;
    while (gs_dwUntrackedTime_us >= 10000)   /* 뺄셈 루프 - ADC_Read당 1번만 실행되니 저렴 */
    {
        gs_dwUntrackedTime_us -= 10000;
        gs_dwUntrackedTicks++;
    }
}
```
나눗셈(비싼 연산)을 `GetSystemTick()`(매우 자주 호출)에서 `SystemTick_AddUntracked_us()`(ADC_Read 1회당 1번, 5분에 약 4000번 정도만 호출)로 옮김. ISR(`gs_dwSystemTick_10ms`)과 foreground(`gs_dwUntrackedTime_us`/`gs_dwUntrackedTicks`)가 각자 다른 변수만 쓰는 레이스 프리 구조는 그대로 유지.

**재검증 결과: 5분 35초 → 5분 23초 (12초 개선).**

### 16-4. 남은 23초 — 소프트웨어가 아니라 HSI 클럭 실측 오차

```
실제 1틱 주기 = 323초 / 30000틱 ≈ 10.767ms (의도한 10ms 아님, 약 7.7% 느림)
```

`STM8L151F3.pdf` Table 32(HSI 오차)의 최악의 경우(-4.5%)보다도 큰 편차 — 이 보드의 HSI가 유독 트리밍이 덜 맞았거나, 남은 자잘한 오버헤드가 소폭 더해진 것으로 추정. 이 시점부턴 소프트웨어 버그가 아니라 **하드웨어 클럭 특성을 보정하는 문제**로 판단.

### 16-5. 수정 — TIM4 ARR 값을 실측 기준으로 보정 (근본적 해결)

`Sample_Load_Wait`만 초 단위로 보정(`SAMPLE_LOAD_WAIT_CORRECTION`처럼)하면 같은 비율의 오차가 있을 `Over_Sample_Check`/`Low_Sample_Check`/`Reaction_Wait`(특히 화학적으로 민감한 3분 구간)는 안 고쳐지므로, **TIM4의 ARR 값 자체를 실측 클럭에 맞게 보정**하는 방향으로 결정:

```c
/* 기존: 2MHz 가정, ARR = (2,000,000/128/100)-1 = 155.25 -> 155 */
/* 실측 기준 보정: 실제 1틱 주기 10.767ms → 역산한 실제 클럭 ≈1.855MHz */
/* 새 ARR = (0.010 × 1,855,000 / 128) - 1 ≈ 144 */
TIM4_TimeBaseInit(TIM4_Prescaler_128, 144);   /* 155 → 144로 변경 */
```

`DM_HW_Drv_SystemTick_TIM4_Init()`의 ARR을 155→144로 변경(하드코딩된 곳은 이 한 곳뿐임을 확인). 이 한 번의 수정으로 `Sample_Load_Wait`뿐 아니라 TIM4 기반의 모든 대기(`Over_Sample_Check`, `Low_Sample_Check`, `Reaction_Wait`, `RESULT_OUT_WAIT_TIME`, `ERR_RUN_TIME`)가 동시에 보정됨.

**한계:** 이 값은 상온에서의 단일 실측치에 맞춘 보정이라, 데이터시트상 HSI가 온도에 따라 변하는 특성(Table 32)을 감안하면 온도가 크게 다른 환경에서는 오차가 다시 조금 벌어질 수 있음 — 그래도 보정 안 한 것보다는 훨씬 정확함.

### 16-6. 최종 하드웨어 검증 완료

ARR=144 적용 후 실물 보드 재검증 결과 **5분 2초** — 목표(5분) 대비 오차 2초(약 0.7%) 수준으로 크게 개선됨. 사용자 확인: 이 정도면 충분(OK).

**타임라인 정리:** 5:37(11절, GetSystemTick 도입 전) → 5:35(12절, 실측 보정값 도입, 이후 15절에서 근본 수정하며 보정값 0으로 되돌림) → 5:35(13절, ADC 변환 40→20회 절반 감소만으로는 거의 변화 없음) → 5:35(15절, ADC 시간 추적 추가했으나 나눗셈 오버헤드로 상쇄) → 5:23(16절, `GetSystemTick()` 나눗셈 제거) → **5:02(16절, TIM4 ARR 155→144 보정)**.

**후속 참고:** 이 ARR 보정은 TIM4를 쓰는 모든 대기에 공통 적용되므로, `Over_Sample_Check`/`Low_Sample_Check`/`Reaction_Wait`도 이론상 함께 개선되었을 것 — 필요시 추후 개별 재확인 가능하나 급하지 않음.
