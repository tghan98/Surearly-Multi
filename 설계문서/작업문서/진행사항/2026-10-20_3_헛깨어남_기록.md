# 헛깨어남 광학값 기록 (SW1 오검출 예외처리)

- 날짜: 2026-10-20 (착수)
- 브랜치: `feature/stage10-wake-fail-record`
- 단계: 10단계 ③ (지시 ③ SW1 오검출)
- 상태: 🔵 진행 중

---

## 왜 이 작업을 하나

2026-10-20 상급자 지시 ③ — "SW1이 눌리지도 않았는데, 또는 노이즈 때문에 잘못 감지돼서
눌려버리면 예외처리를 어떻게 할 건지 고려하면 좋다."
→ 지시 원문은 `00_v11-작업기준서.md` 1장.

### 방어는 이미 있다

`DM_Main_Sq_App.c` 190행. 주석에 `Spurious wake`(헛깨어남)라고 적혀 있다.

```c
    if (DM_App_Optic_Check_StickPresent())      /* CH3 원본값 >= 2600 */
    {
        /* LCD 시퀀스 시작 */
    }
    else
    {
        /* Spurious wake or stick pulled back out immediately: ... */
        DM_App_Main_Sq_Set_Step(MAIN_SQ_IDLE);   /* 다시 잠듦 */
    }
```

SW1이 잘못 눌려 깨어나도 광학값이 아니면 검사가 시작되지 않고 그대로 다시 잔다.
**실제 발생 사례는 없다.** 가정에 대한 지시다.

### 없는 것은 기록이다

`else` 로 가면 그냥 `MAIN_SQ_IDLE` 로 돌아간다. **몇 번, 왜 그랬는지 아무 데도 안 남는다.**

> **계측 사각지대** — 일어난 일이 어디에도 기록되지 않아, 사후에 확인할 수 없는 상태.

이것이 실제로 비용을 치르게 한 사례가 있다. **7·9번 기기**가 이 `else` 로 빠져 LCD 가
안 뜬 것이었는데, 원인을 알아내는 데 디버거를 붙이고 브레이크포인트를 걸어
반나절이 걸렸다 (→ `2026-10-19_간헐_스틱빠짐_오판_추적.md` 8절).
그때 잰 값이 덤프에 있었으면 **덤프 한 번으로 끝났다.**

### 횟수는 세지 않는다

| | 얻는 것 | 드는 것 |
|---|---|---|
| 횟수 | "몇 번" 만 안다 | **깨어날 때마다 EEPROM 쓰기** |
| 광학값 min/max | **"왜" 를 안다** | 범위가 넓어질 때만 쓰기 |

횟수는 매번 값이 달라지므로 매번 써야 한다. 전지를 아끼려고 넣는 기능이 전지를 더 먹는다.
광학값은 범위가 한 번 정해지면 그 안쪽은 전부 무시되어 쓰기가 거의 멈춘다.

실제로 전지 문제가 보고되면 그때 횟수를 넣어도 늦지 않다 (10-20 판단).

## 무엇을 바꾸나

### 1. 측정값을 밖으로 내놓는 함수 추가 — `DM_Optic_Handle_App.c/.h`

현재 `DM_App_Optic_Check_StickPresent()` 는 잰 값을 버리고 0/1 만 돌려준다.
부르는 곳이 **3군데**인데 숫자가 필요한 것은 190행 **하나뿐**이다.

```c
/* 새로 만든다 */
uint8_t DM_App_Optic_Check_StickPresent_WithValue(uint16_t* pADC)
{
    uint16_t wADC = DM_App_Optic_Measure(OPTIC_CH_3);
    *pADC = wADC;
    return (wADC < OPTIC_STICK_REMOVE_THRESHOLD) ? 0 : 1;
}

/* 기존 함수는 모양 그대로. 속만 위 함수를 부른다 */
uint8_t DM_App_Optic_Check_StickPresent(void)
{
    uint16_t wUnused;
    return DM_App_Optic_Check_StickPresent_WithValue(&wUnused);
}
```

**왜 시그니처를 바꾸지 않는가** — 바꾸면 부르는 3곳을 다 고쳐야 하고, 숫자가 필요 없는
2곳(`DM_Optic_Handle_App.c` 181·197행)이 쓰지도 않을 변수를 넘기게 된다.

**왜 밖에서 다시 재지 않는가** — 측정 1회가 더 붙는다. LED 점등과 ADC 20회가 추가되어
전지를 아끼려는 목적과 어긋난다.

판정하는 줄(`< OPTIC_STICK_REMOVE_THRESHOLD`)은 **한 군데**로 유지된다.

### 2. EEPROM 진단 영역 — `DM_Rom_Handl_App.c/.h`

```
244        Dump Pos                   (기존)
245 ~ 247  비어 있음                   244 와 같은 물리 블록 - 건드리지 않는다
248 ~ 249  WakeFail 최솟값             초기값 0xFFFF
250 ~ 251  WakeFail 최댓값             초기값 0x0000
252 ~ 255  Reserved (0xFF 유지)        다음 블록 - 깨끗하게 남긴다
```

**왜 248부터인가** — STM8L 의 EEPROM 은 1바이트만 써도 **물리적으로 4바이트 블록이 함께
소모된다.** 245 에서 시작하면 244번(Dump Pos)과 같은 블록(244~247)을 공유하므로,
헛깨어남이 생길 때마다 덤프 위치 칸도 함께 닳는다. 248 은 다음 블록의 시작이다.

```c
void DM_App_Rom_Update_WakeFail(uint16_t wADC)
{
    더 작으면 최솟값을 쓴다
    더 크면   최댓값을 쓴다
    둘 다 아니면 아무것도 쓰지 않는다
}
```

**초기값을 0xFFFF / 0x0000 으로 두는 이유** — 최솟값을 0 으로 두면 `if (잰값 < 0)` 이
영원히 거짓이라 한 번도 안 바뀐다. 가장 큰 수에서 시작해야 첫 값이 들어간다.
최댓값은 반대다.

#### ⚠ 최댓값 초기화는 공장 출하 상태 검사가 필요하다

**처음 설계에 구멍이 있었다.** 최댓값 초기값을 `0x0000` 으로 두기로 했으나,
**EEPROM 공장 출하 상태는 `0xFFFF` 다.** 아무도 0 을 써준 적이 없다.

```c
if (잰값 > 0xFFFF)   /* 영원히 거짓 — 최댓값이 한 번도 안 바뀐다 */
```

"최솟값을 0 으로 두면 안 된다"고 적어놓고 최댓값 쪽에서 같은 함정에 빠졌다.

**해결은 이미 코드에 있다.** `DM_App_Rom_Get_StickPtrData()` (`DM_Rom_Handl_App.c` 159행)가
같은 문제를 같은 방식으로 다룬다.

```c
void DM_App_Rom_Get_StickPtrData(uint16_t* pBuffer)
{
    DM_HW_Drv_EEPROM_Read(ROM_OFFS_STICK_PTR_DATA, (uint8_t*)pBuffer, 16);

    /* Guard-rail: Initial state check (0xFFFF) */
    if (pBuffer[0] == 0xFFFF)          /* 공장 출하 상태인가 */
    {
        for (i = 0; i < 8; i++) { pBuffer[i] = 0; }   /* 0 으로 채우고 */
        DM_App_Rom_Set_StickPtrData(pBuffer);          /* 다시 써둔다 */
    }
}
```

**읽을 때 함수가 알아서 처리한다.** 같은 꼴로 간다.

```c
void DM_App_Rom_Get_WakeFail(uint16_t* pMin, uint16_t* pMax)
{
    EEPROM 248~251 에서 4바이트 읽는다

    if (*pMin == 0xFFFF && *pMax == 0xFFFF)   /* 공장 출하 상태 */
    {
        *pMax = 0;                            /* 최댓값만 0 으로 */
        EEPROM 에 다시 쓴다
    }
}
```

> 상급자 지시(10-20 녹음)의 "**FF 가 있는지 확인해서, FF 면 EEPROM 을 지워주거나
> 어떤 작업을 한다. 최초 상태인 걸 확인할 수 있는 조치가 필요하다**" 가 이것을 가리킨다.
> 새로 만들지 말고 이미 있는 방식을 쓰라는 뜻으로 읽었다.

### 3. 부르는 자리 — `DM_Main_Sq_App.c` 190행

```c
    uint16_t wADC;

    if (DM_App_Optic_Check_StickPresent_WithValue(&wADC))
    {
        /* 통과 - 그대로 */
```

안 보이는 것은 못 넘고 다시 잔 경우뿐이다.

## 설계 검토에서 바뀐 것 (2026-10-20)

에이전트 검토를 거쳐 세 가지가 바뀌었다. **두 가지는 내가 틀렸던 것이다.**

### ① 주소 245 → 248 (받아들임)

4바이트 물리 블록 경계. 위 2절 참조.

### ② `최솟값 > 최댓값` 검사의 한계 (내가 과장했다)

부분 기록을 "체크섬과 같은 효과로" 잡을 수 있다고 했으나 **틀렸다.**

최솟값 1,500(`0x05DC`)을 1,000(`0x03E8`)으로 바꾸는 도중 한 바이트만 쓰이면,

| 섞인 값 | 십진수 | 최댓값 2,000 보다 작나 |
|---|---|---|
| `0x03DC` | 988 | 작음 → **안 걸림** |
| `0x05E8` | 1,512 | 작음 → **안 걸림** |

둘 다 통과한다. 정확한 표현은 이것이다.

> `min > max` 면 **확실히 무효.** `min <= max` 라고 해서 원자적 기록이 보장되는 것은 아니다.

진단용 값이고 펌웨어 판정에 쓰이지 않으므로, **잔여 위험을 문서화하고 받아들인다.**
checksum 이나 magic 은 넣지 않는다.

> 드라이버가 `FLASH_ProgramByte()` 를 바이트마다 부른다 (`DM_HW_Drv.c` 425행).
> 두 바이트 쓰는 도중 전원이 끊기면 상위·하위가 다른 시점 값으로 섞인다.

### ④ 상급자 녹음 피드백 (2026-10-21 확인)

착수 문서를 쓴 뒤 받은 피드백을 받아쓰기로 확인했다
(`상사피드백_20261020_받아쓰기.txt`). 세 가지가 나왔다.

| | 내용 | 이 단계에서 |
|---|---|---|
| ⓐ | **최초 상태(FF)를 확인하는 조치가 필요하다** | **반영함** — 위 2절 |
| ⓑ | 최초에는 **채널끼리 견줘서** 불량을 가린다 | 미룸 — 아래 「남은 것」 |
| ⓒ | 저장한 값으로 **기기가 비교 판단**한다 | 범위 밖 — 13단계 후보 |

> ⓐ 는 "새로 만들지 말고 이미 있는 방식(`Get_StickPtrData()`의 0xFFFF 검사)을 쓰라"는
> 뜻으로 읽었다. 그대로 따랐고, 덕분에 최댓값 초기값 버그가 드러났다.

**이 단계가 "쌓는" 단계라는 것을 보고 시 분명히 말한다.** 값만 쌓고 끝내는 것으로
보고하면 "그래서 판단은 언제 하냐"가 나온다. 쌓는 것이 판단의 재료라는 순서를 함께 말한다.

### ③ `0` 을 ADC 멈춤으로 단정할 수 없다 (내가 틀렸다)

"timeout 반환값은 0xFFFF 이므로 0 과 잘 갈린다"고 했으나 **틀렸다.**

드라이버는 `0xFFFF` 를 돌려주지만(`DM_HW_Drv.h` 27행),
`DM_App_Optic_Measure()` 가 그것을 발견하면 LED 를 끄고 **`0` 으로 접어서** 반환한다
(`DM_Optic_Handle_App.c` 81·96행).

따라서 EEPROM 만 보고는 둘을 구별할 수 없다.

- ADC 가 멈춰서 0
- 실제 입력이 0V 라서 0

## 덤프 읽는 법

| 최솟값 / 최댓값 | 뜻 |
|---|---|
| 65535 / 0 | **기록된 관문 실패값 없음** |
| 최솟값 > 최댓값 | **깨진 기록** — 쓰기 중 전원이 끊긴 흔적. 믿지 말 것 |
| 0 이 섞임 | **ADC timeout 또는 실제 입력 0** — 구별 불가 |
| 1 ~ 수십 | 변환은 됐고 광학 신호가 암전류 수준 (7·9번 실측 **4**) |
| 1,480 / 1,520 | 좁게 머묾 — 스틱 없이 깨어남, **진짜 노이즈** |
| 1,400 / 2,500 | 넓게 흔들림 — **턱걸이.** 스틱이 어중간하게 물림 |

**폭이 좁으면 늘 같은 일, 폭이 넓으면 그때그때 다른 일**이다.

> `65535 / 0` 을 "헛깨어남 없음"이라고 쓰지 않는다. 최댓값 초기값이 0 이라,
> 실패가 있었는데 값이 0 이었던 경우와 구별되지 않는다.

### ⚠ 한계 — 아예 안 깨어나는 기기는 덤프를 못 뽑는다

**이 기능으로 모든 경우를 보지는 못한다.**

덤프(`M` 명령)는 USART 로 받는다. 기기가 Halt 상태면 USART 가 살아 있지 않아
**명령 자체가 들어가지 않는다.** LCD 가 켜져 있어야, 즉 깨어 있어야 뽑힌다.

| 기기 상태 | 덤프 | 이 기능의 쓸모 |
|---|---|---|
| **간헐적으로** 안 깨어남 | 됨 | **있다** — 못 깨어났던 회차의 값이 쌓여 있다 |
| **아예** 안 깨어남 (7·9번) | **안 됨** | 없다. 디버거가 필요하다 |

> **실제로 겪었다 (10-21).** 5번 기기 LCD 가 안 켜진 상태에서 덤프를 뽑으려 했으나
> 받아지지 않았고, 깨어난 뒤에야 뽑혔다.

따라서 이 기능은 **"가끔 이상한 기기"** 를 위한 것이다.
7·9번처럼 완전히 죽은 기기는 여전히 디버거를 붙여야 한다.

> 그래도 7·9번 같은 경우에 무의미하지는 않다. 처음부터 죽어 있는 기기는 드물고,
> 대개 **가끔 되다가 점점 안 되는** 쪽으로 간다. 그 구간에서 뽑으면 값이 남아 있다.
> 오늘 5·12번이 그 구간으로 보인다 (→ `2026-10-21_1_정상기기_광량저하.md`).

**펌웨어는 이 값을 해석하지 않는다.** 에러 코드로 올리지 않는다.
"8 이하는 광학계 사망" 같은 기준을 아직 모르기 때문이다 — 지금 아는 것은 7·9번이 4 였다는
1건과 암전류가 8~9 라는 것뿐이다. 기준을 모르는데 기기에 박으면 나중에 회수해야 한다.
순서는 **측정 → 기준 → 판정**이고 지금은 첫 칸이다. 문턱값 556 도 같은 순서였다.

## 어떻게 확인할 건가

*(2026-10-21 논의 후 작성)*

동작이 예측 가능한 방어 코드이므로 재현 실험이 꼭 필요한 종류는 아니다.
읽고 비교하고 쓰는 것이 전부다. 확인 방법은 내일 정한다.

후보:

- **A. 스틱 없이 SW1 만 손으로 누른다** — 깨어나되 CH3 이 약 1,500 이라 관문에 걸릴 것.
  다만 SW1 을 손으로 누르는 것이 실제로 되는지 확인되지 않았다
- **B. 불량 기기(7·9번)에 구워본다** — 값이 4 라 확실히 걸린다. 다만 하드웨어 불량이라 범위 밖

- [ ] **채널 간 비교 판정** — 상급자 지시(10-20 녹음)에 "어떤 건 잘 나오고 어떤 건
      안 나오는" 경우를 불량으로 빼라는 대목이 있다.

      **현재는 채널별 절대 범위 검사 두 겹으로 갈음한다.**

      | 관문 | 보는 것 | 위치 |
      |---|---|---|
      | 1 | 원본값이 1,500 ~ 3,900 인가 | `DM_Optic_Handle_App.c` 189행 |
      | 2 | 배율 적용값이 1,175 ~ 1,225 인가 | 같은 파일 243행 (`OPTIC_TUNED_TOLERANCE` 25) |

      지금까지 겪은 불량은 모두 이 두 겹에 걸렸다 — 7·9번(네 채널 4), 3번(CH0 범위 밖).
      두 겹을 다 통과하면서 한 채널만 약한 사례는 **아직 나온 적이 없다.**

      채널 간 비교를 넣으려면 "정상 기기의 채널 차이가 얼마까지 벌어지나"를 먼저 재야 한다.
      정상 3대에서 25 ~ 60 (1.6% 이내)이고, 광량이 35% 낮은 2번 기기는 아직 안 봤다.
      4단계에서 관측된 채널 간 5% 기울어짐의 원인도 모른다 (기준서 7장 보류 항목 ⓐ).

      **기준을 세울 데이터가 모자라 미룬다. 데드라인 때문이며 모르고 넘어간 것이 아니다.**
      문턱값 625 를 1대로 정했다가 틀린 전례가 있어, 기준은 데이터가 모인 뒤에 세운다.

      데이터는 공짜로 모인다 — **덤프 세 번째 덩어리(T/BT/BC/C)가 초기 측정 네 채널**이다.

- [ ] **비교 판정 (13단계 후보)** — 상급자는 저장된 값을 기기가 **읽어서 스스로 판단**하는
      것을 전제하고 말씀하셨다. 이 단계는 거기까지 가지 않는다.

      > "인서트가 1보다 크면 저장된 값이 있으니 **비교 판단이 가능해.**
      >  그런데 인서트가 0이야. 최초라 비교할 게 없어. **그럼 뭘로 판단해야 돼?**"

      기기가 판단하려면 "몇 이하가 불량"이라는 **기준**이 있어야 하는데, 지금 가진 것은
      7·9번 1건(값 4)과 암전류 8~9 뿐이다. 4 와 8 사이 어디가 경계인지 모른다.

      **순서는 측정 → 기준 → 판정이고 이 단계는 첫 칸이다.** 문턱값 556 도 6대를 재고
      울타리를 찾은 뒤에 박았다.
