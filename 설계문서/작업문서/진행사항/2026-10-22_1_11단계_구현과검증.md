# 11단계 QC 모드 — 1·2·3번 구현과 실기 검증

- 날짜: 2026-10-22 ~ 10-23
- 브랜치: `feature/stage11-qc-mode`
- 단계: 11단계 1번(기반), 2번(카운터), 3번(측정·판정 분리와 구간별 화면)
- 상태: 🟢 세 단계 모두 실기 검증 완료. 미검증 항목 없음 (10-23 마감)

> **한 줄** — 결과 슬롯을 6칸으로 줄여 QC 기준값 자리를 확보하고, `Q` 명령으로
> 데이터 EEPROM 전체를 초기화할 수 있게 했다. Insert Count 를 IDLE 관문 통과
> 시에만 올리도록 옮기고 254 에서 멈추게 했다. 3번에서 네 채널을 먼저 재고
> 판정한 뒤 LCD 를 켜도록 순서를 바꾸고, QC 구간에서 네 채널 한 벌을 남긴다.

### 2번 — 카운터 (`9ef6818`)

| 바꾼 것 | 위치 |
|---|---|
| Insert Count 증가를 **IDLE 관문 통과 직후**로 이동 | `DM_Main_Sq_App.c` 195~202행 |
| **254 포화** | 같은 자리, `if (bStickInsertCnt < 254)` |
| 1단계에 있던 증가 코드 제거 | `DM_Main_Sq_App.c` 263행 |
| 카운터 변수를 IDLE 핸들러 지역 변수로 내림 | `DM_Main_Sq_App.c` 162행 |

**왜 관문 통과 시에만 세나** — Insert Count 가 QC 구간(1~5)과 사용자 구간(6~)을
가르는 기준이기 때문이다. 깰 때마다 세면 포장·운송 중 SW1 이 눌리는 것만으로도
QC 구간이 소진된다. 실제로 11번 기기는 오늘 수십 번 꽂는 동안 관문을 통과한 것이
세 번뿐이었다. 깰 때마다 셌다면 **검사 기록이 하나도 없는 채로** 사용자 구간에
들어갔을 것이다.

**왜 254 에서 멈추나** — 255 를 저장하면 `Get_InsertCount()` 의 `0xFF` 분기
(`DM_Rom_Handl_App.c` 57~62행)에 걸려 미기록으로 해석되고 0 이 된다. 0 이면
QC 구간이 다시 열린다. 254 는 사용 횟수 제한이 아니다. 사용 제한은
Test Complete Count 쪽(`_nSCAN_MAX_CNT`)에 그대로 있다.

## 2. 검증 결과

덤프는 `설계문서/Test_UI/RawDump/6_11단계QC_20261022/` 아래에 있다.

| 항목 | 기기 | 전 | 후 | 폴더 |
|---|---|---|---|---|
| `Q` 초기화가 EEPROM 전체를 지운다 | 11 | Insert 23 / Complete 6 | **1 / 0** | `1_초기화검증` |
| 관문 통과 시 정확히 +1 | 1 | 65 | **67** | `2_관문통과` |
| 관문 실패는 세지 않는다 | 11 | 2 | **3** | `3_관문실패` |
| 254 포화 | 1 | 253 | **254** | `4_포화` |
| 완주 시 Test Complete +1 | 1 | 0 | **1** | `5_완주` |

**관문 통과(67)** — 65 에서 꽂았다 빼기 1회 + 덤프용 삽입 1회 = 67. 두 번 셌다면
69, 빠뜨렸다면 66 이다.

**관문 실패(3)** — 같은 구간에서 Wake Fail Max 가 2,482 → 2,559 로 올랐다.
관문 실패가 새로 기록됐다는 뜻인데 카운트는 1만 올랐다. 기록은 되고 세지는 않는다.

**포화(254)** — 254 까지 꽂을 수 없으므로 디버거로 EEPROM `0x1000` 에 `FD`(253)를
써넣고 시작했다. 멈춤 상태의 메모리 쓰기는 디버거로 가능하다. 그 뒤 삽입 2회.
포화가 없었다면 255 가 저장되고 읽을 때 0 으로 나온다. **254 와 0 은 헷갈리지 않는다.**

**완주(Test Complete 1)** — 2번에서 1단계의 증가 코드를 들어내며 그 자리를 건드렸다
(263행). `TestCompleteCount` 읽기가 같이 망가지지 않았는지는 완주해 봐야 알 수 있다.
빌드가 통과한다고 보장되지 않는다.

## 3. 판정 기준 — 되돌아갈 수 없는 숫자가 되돌아갔는가

초기화 검증에서 Wake Fail 이 **615 / 2475** 로 나왔다. 0 도 65535 도 아닌데 통과로
판정했다. 이 값의 성질 때문이다.

| | 성질 | 전 | 후 | |
|---|---|---|---|---|
| Min | 작아지기만 한다 | 0 | 615 | **올라갔다** |
| Max | 커지기만 한다 | 2,591 | 2,475 | **내려갔다** |

지워지지 않았다면 Min ≤ 0, Max ≥ 2,591 이어야 한다. 둘 다 있을 수 없는 방향으로
움직였다. 한 번 지워지고 새로 기록됐다는 뜻이다.

> **기준을 세우는 방향** — "고쳐졌으면 이렇게 보인다" 가 아니라
> **"안 고쳐졌으면 절대 이렇게 못 나온다"** 쪽으로 세운다. 후자가 더 강하다.

가장 짧은 판정은 **Insert Count 23 → 1** 한 줄이다. 올라가기만 하는 숫자가
내려갔으므로 원인이 하나로 좁혀진다. 광학값이나 레코드는 0 이 되는 경로가 여럿이라
단독으로는 증거가 약하다.

**오염을 기대값에 넣는다** — 덤프를 받으려면 기기를 깨워야 하고, 깨우면 카운트가
올라간다. 그래서 초기화 직후 기대값은 0 이 아니라 **1** 이다. 관측 때문에 값이
변하는 것은 막을 수 없지만, **얼마나 변하는지 알면 계산에 넣을 수 있다.**

## 4. 틀린 진단 — 디버거를 범인으로 지목했다

오전에 11번 기기가 지그에 물린 채로 스틱에 반응하지 않았다. 떼면 됐다.
이것을 STM8 의 SWIM 디버거 간섭(저전력 모드 동작이 달라진다)으로 **단정했다.**
`관측 간섭` 이라는 이름까지 붙였다.

오후에 1번 기기는 **지그에 물린 채로 멀쩡히 깨어났다.** 설명이 성립하지 않는다.

실제 원인은 11번 기기 쪽이다. 같은 시각 덤프의 Wake Fail 이 615 / 2,475 였다.
**깨긴 깼고**, CH3 가 관문 2,600 에 못 미쳐 도로 잔 것이다. 밖에서는 LCD 가 안
켜지니 "안 깨어났다" 로 보인다. 지그를 떼고 됐던 것도 여러 번 꽂다 **어쩌다
통과한** 것이었다.

### 무엇을 놓쳤나

같은 기기로 비교했으니 괜찮다고 생각했다. 그런데 **그 기기 자체가 같은 조건에서
다른 결과를 내는 상태**였다.

> 어제 적은 것 — "A 와 B 를 비교한다고 할 때, A 와 B 사이에 바뀐 것이 하나뿐인지 센다"
>
> **빠진 것** — 바뀐 것이 하나여도, **그 하나가 안정적인지**를 함께 본다.
> 간헐적으로 동작하는 기기는 비교의 기준이 될 수 없다. 1회 시도로는 아무것도 못 가른다.

### 대가

11단계 1번을 디버거 메모리 창으로 확인하려다 포기하고 덤프 비교로 돌아갔다.
막혔다고 본 길이 사실 열려 있었으므로, **쓸 수 있는 방법을 스스로 닫았다.**
결과적으로 덤프 비교가 기록을 남겨 더 나았지만 판단 자체는 틀렸다.

## 6. 곁다리

### Wake Fail 은 관문 실패를 다 잡지 못한다

`DM_Rom_Handl_App.c` 306~314행. 범위를 벗어날 때만 쓴다.

```c
if (wADC < wMin) { ... }
if (wADC > wMax) { ... }
```

615~2,475 가 들어 있는 상태에서 1,800 으로 실패하면 **아무것도 변하지 않는다.**

> 변했으면 실패가 있었다 — **성립**
> 안 변했으면 실패가 없었다 — **성립하지 않는다**

관문 통과 여부는 **Insert Count** 로 본다. LCD 점등은 판단 근거가 아니다 — 9장 참조.

### Test UI 의 `Q` 버튼

개발용이다. 생산용 UI 분리 시 제거할 수 있도록 CSS·마크업·스크립트 각 구역에
주석을 남겼다. 오클릭 방지는 **버튼 자신을 4초간 무장 상태로 두는** 방식이다.
`confirm()` 모달은 자바스크립트를 멈춰 273바이트 수신이 밀리므로 쓰지 않았다.

### 에러 대기 중에는 카운트가 오르지 않는다

에러 화면은 `ERR_RUN_TIME` 12,000 틱 = **2분**이다(`DM_Main_Sq_App.h` 27행).
그 동안 기기는 깨어 있으므로 IDLE 을 지나지 않는다. 중간에 다시 꽂아도 세지 않는다.
연속 시험을 할 때는 **화면이 꺼지는 것**이 다음 회차를 시작해도 좋다는 신호다.

## 7. 11단계 3번 — 측정·판정 분리와 구간별 화면 처리

### 무엇을 바꿨나

| 바꾼 것 | 위치 |
|---|---|
| 네 채널을 모두 측정한 뒤 범위 판정. 측정 함수에서 범위 검사와 EEPROM 저장을 떼어냄 | `DM_Optic_Handle_App.c` `MeasureInitialStick()` |
| `DM_App_Optic_CheckInitialRange()` 신설 | 같은 파일 |
| QC 구간(증가 후 1~5)에서 완전한 네 채널 한 벌을 **매회** 저장 | `DM_Main_Sq_App.c` 294~298행 |
| 정상 삽입 LCD 를 두 관문 통과 뒤로 이동 | `DM_Main_Sq_App.c` 322행 |
| `Initial_Optic_Error()` 신설 — QC 는 에러 LCD + 2분, 사용자는 무음 IDLE | `DM_Main_Sq_App.c` 128행 |
| 초기 CH3 관문 실패는 결과 슬롯을 쓰지 않음 | `DM_Main_Sq_App.c` 800~802행 |

마지막 항목은 **오전 코드 검토에서 잡은 버그**다. 처음 구현은 관문 실패에도
`Save_Result_To_Rom()` 을 불렀다. 11번처럼 헛깨어남이 잦은 기기에서는 여섯 칸이
헛깨어남으로 차서 **실제 검사 이력이 밀려난다.** 10단계 ③ 의 목적과 정반대다.

고친 방식은 `ERROR_WAIT` 핸들러에 조건을 하나 둔 것이다.

```c
if ((gs_wMain_Sq_Timer == ERR_RUN_TIME) &&
    (gs_bErrorSequence != MAIN_SQ_IDLE))
```

관문 실패는 IDLE 에서 나므로 `gs_bErrorSequence` 가 0 이 되고, 저장을 건너뛴다.

## 8. 10-22 에 얻은 것

### LCD 순서를 바꿔도 체감 지연이 없다

가장 걱정했던 항목이다. 네 채널 측정과 두 관문 검사가 LCD 앞으로 왔으므로
그만큼 화면이 늦게 켜진다. 1초를 넘으면 사용자가 고장으로 본다 — **고장으로
보이지 않으려고 바꾼 순서가 거꾸로 체감을 해치는** 상황이다.

실측은 기기 단독 동작에서 했다. 꽂자마자 삽입 애니메이션이 떴고 바로 시료 투입
화면으로 넘어갔다. 측정 한 번이 짧아 네 번 해도 사람이 못 느낀다.

> 사전 측정을 하자고 했으나 **구현 후 재는 쪽이 맞았다.** 미리 재면 참고값일
> 뿐이고, 늦게 알아서 순서를 되돌리는 비용도 크지 않다.

### 코드를 바꾸면 판정 기준도 같이 바뀐다 — 오늘의 교훈

2단계까지는 이랬다.

> 화면이 안 켜졌다 = 초기 CH3 관문에서 떨어졌다

3단계에서 LCD 를 뒤로 옮기면서 **이 등식이 깨졌다.** 화면이 안 켜지는 경우가
셋이 됐다.

| | 어디서 떨어졌나 |
|---|---|
| ① | 초기 CH3 관문 |
| ② | 네 채널 원본값 범위 검사 |
| ③ | 배율 맞추기 |

셋 다 밖에서는 똑같이 보인다.

11번에서 이것이 실측으로 드러났다. 화면이 **한 번도 안 켜졌는데** 회차는
06 에서 0d 로 **7 올랐다.** 일곱 번 모두 관문은 통과했고 그 뒤에서 떨어진 것이다.

> **다음부터** — 코드의 순서를 바꾸면, 그 코드로 무엇을 판정하던 기준도
> 같이 점검한다. 어제의 기준을 그대로 들고 오지 않는다.

### 덤프 위치로 저장 횟수를 세지 않는다

`0x10F4` 가 03 에서 04 로 바뀐 것을 보고 "일곱 번 모두 저장됐다"고 적었다.
6칸 링이므로 `03 → 04` 는 저장이 **1회·7회·13회** 일 때 모두 같다.

이 문서 3장에 "되돌아갈 수 없는 숫자가 되돌아갔는가" 를 판정 기준으로 적어
두고, 정작 **되돌아올 수 있는 숫자(링)로 횟수를 단정**했다.

### 관문 실패를 확정적으로 만드는 방법

`OPTIC_STICK_REMOVE_THRESHOLD` 를 **4096** 으로 임시 상향한다.

판정식이 `DM_Optic_Handle_App.c` 302행의 `wADC < 문턱값` 이고 ADC 가 12비트
(최대 4,095)이므로, 4096 이면 **어떤 값이 와도 반드시 실패**한다.

| 시도한 방법 | 왜 안 썼나 |
|---|---|
| 스틱 뒤쪽에 불투명 테이프 | 얼마나 가려질지 모른다 |
| 발색된 스틱 | 79.3%, 젖음까지 더해도 60.9% — 1번 기기는 통과할 수 있다 |
| 문턱값 3900 | 실측 한 번(3,692)을 근거로 한 값. 흔들리면 통과한다 |
| **문턱값 4096** | **확정 실패.** 재현에 운이 섞이지 않는다 |

원복 관리는 `git diff -- USER/Parameter_define.h` 로 확인한다. 3번 코드가
미커밋 상태라 **브랜치를 새로 만들어도 작업 트리가 그대로여서 격리가 안 된다.**

시험 후 2600 으로 되돌리고 재빌드·재다운로드까지 해야 기기도 원래 판정값으로
돌아온다. 1번 기기에서 정상 스틱 삽입 시 LCD 점등을 확인했다.

### 곁다리 — 1번 기기 CH3

관문에서 잰 값이 **3,695** 였다. QC 기준값의 CH3 가 2,774 로 낮게 나와 광량
저하를 의심했으나, 자리가 다른 값이다. 다만 **한 번의 측정이므로 간헐적 저하를
배제하지는 못한다.**

## 9. 10-23 — 미검증 두 항목 마감

### ① QC 구간에서 초기 관문에 실패하면 어떻게 되나

**목적** — 출하 검사 중 스틱을 못 알아보면 **작업자가 알아야 한다.**
사용자 구간은 조용히 돌아가지만 QC 구간은 화면을 띄워야 한다.
동시에 그 회차가 검사 회차를 깎거나 결과 칸을 먹으면 안 된다.
관문을 못 넘은 회차는 **검사를 한 것이 아니기** 때문이다.

**확인할 것** — 에러 화면이 뜨는가. 그러면서 회차와 결과 칸은 그대로인가.

**어떻게** — 1번 기기. 회차를 `0x1000` 에 04 로 직접 써 넣어 QC 구간으로
만들고, 문턱값을 **4096** 으로 임시 상향해 관문 실패를 확정시켰다.
1번은 CH3 가 3,695 라 2,600 으로는 늘 통과하므로 실패를 만들어야 했다.

**결과**

| | 시험 전 | 시험 후 |
|---|---|---|
| 화면 | — | **에러 표시 후 약 2분 뒤 소등** |
| `0x1000` Insert Count | 04 | **04** 유지 |
| `0x10F4` 덤프 위치 | 05 | **05** 유지 |
| `0x10D4~DB` QC 기준값 | 3264/3008/2932/2774 | 그대로 |
| `0x10F8` Wake Fail | 3695 / 3695 | **3695 / 3701** |

Wake Fail Max 가 3,701 로 갱신된 것이 그 회차의 관문 실패 기록이다.
**깼고, 떨어졌고, 기록만 남았다.**

10-22 의 사용자 구간 시험과 나란히 놓으면 구간 분리가 분명하다.

| | 회차 8 (사용자) | 회차 4 (검사) |
|---|---|---|
| 화면 | 안 켜짐 | **에러 + 2분** |
| 회차 / 결과 칸 / QC 값 | 유지 | 유지 |

같은 기기, 같은 실패 지점인데 **회차만 다른데 화면만 갈린다.**

11번에서도 같은 동작이 재현됐다. 1번은 임시 문턱값으로 만든 인위적 실패였고,
11번은 **코드를 건드리지 않은 상태의 실패**다. 다만 11번의 원인은 미확정이다.
확인된 것은 CH3 값이 낮고 관문을 넘지 못한다는 사실까지다.

### ② 측정 중간에 끊기면 QC 기준값을 건드리나

**목적** — QC 기준값은 **출하 상태의 증명서**다. 완전한 네 채널 한 벌만
들어가야 한다. 반쪽짜리가 들어가면 미측정 채널이 0 으로 남아, 나중에 꺼내 볼 때
**광량이 낮은 기기를 출하한 것처럼** 읽힌다. 실제로는 측정이 끊겼을 뿐인데
QC 팀이 누명을 쓴다. 더 나쁜 것은 **그 기록 자체를 못 믿게 되는 것**이다.
한 번 틀린 것이 드러나면 진짜 QC 미수행 건에서도 "측정이 끊긴 것 아니냐" 가
나온다. 증거로서의 힘이 사라진다.

> **"어디서 끊겼나" 는 결과 칸이 맡는다.** Error Step 과 Error Code 가 남는다.
> 반쪽짜리 숫자보다 에러 코드가 정확하다. 두 자리의 역할이 다르다.

**확인할 것** — 네 채널을 다 못 쟀을 때 기존 QC 기준값을 그대로 두는가.

**어떻게** — 조건이 둘이라 까다로웠다.

| | 필요한 것 |
|---|---|
| 초기 관문 | **통과** — 그래야 측정을 시작한다 |
| 측정 중 확인 | **실패** — 그래야 중간에 멈춘다 |

11번이 측정 중 실패는 잘 내는데 초기 관문을 자꾸 못 넘었다. 두 번 무효가 났다.

| 시도 | 결과 |
|---|---|
| 그냥 삽입 | `0x1000` 04 유지 — 관문에서 막힘, 무효 |
| 임시 관문 **1500** | 04 유지 — 그것도 못 넘음, 무효 |
| 임시 관문 **100** | 04 → 05 — 통과, **시험 성립** |

Wake Fail Min 이 145 까지 내려간 기기라 1,500 으로도 모자랐다.

**두 자리를 갈라야 했다.** 초기 관문과 측정 중 확인이 같은 상수를 쓰므로
(`DM_Optic_Handle_App.c` 302행), 상수를 낮추면 셋이 함께 느슨해져 보려던
중단이 일어나지 않는다. 그래서 **IDLE 핸들러의 조건식만** 임시로 숫자 비교로
바꾸고 측정 중 확인은 2,600 으로 두었다.

```c
/* TEMP TEST: lower only the IDLE gate; in-measure checks remain at 2600. */
(void)DM_App_Optic_Check_StickPresent_WithValue(&wGateADC);
if (wGateADC >= 100)
```

**결과**

| | 시험 전 | 시험 후 |
|---|---|---|
| `0x1000` Insert Count | 04 | **05** — 관문 통과 |
| `0x1002~03` Step / Code | 01 / 01 | **01 / 01** — 1단계 CH3 실패 |
| `0x10F4` 덤프 위치 | 04 | **05** — 이번 회차 기록됨 |

측정을 시작은 했고 끝내지 못했으며 **QC 기준값은 쓰지 않았다.**
결과 칸과 오류 정보(Step/Code)는 **썼다.** 측정까지 진입한 회차이므로 설계대로다.
두 자리의 역할이 다르다는 것이 그대로 드러난 셈이다.

## 10. 11단계 4-1 — 249바이트 덤프 (10-23)

기기 덤프만 먼저 273바이트에서 249바이트로 바꿨다. 결과는 7칸(마지막 0칸 포함) 대신 실제 6칸만 보내고, 결과 뒤와 Wake Fail 앞에 QC 기준값 8바이트를 넣었다. PC UI는 아직 273바이트를 기다리므로 4-2에서 따로 고친다.

1번 기기에서 `M` 덤프를 PuTTY 바이너리 로그로 받았다. 원본 사본은 `설계문서/Test_UI/RawDump/7_11단계4-1_20261023/putty_249bytes.log` (249바이트, SHA-256 `40A05909D6F6A750EB6C0AEBFC792AFF7E221DEA29F417288E3AE4848DAFE33B`)에 보관했다.

| 바이트 위치 | 내용 | 실측 |
|---|---|---|
| 0~20 | 펌웨어·LOT 헤더 | `v2.1` / `v2.1.1.2` / `HCGM` / `19001` |
| 21~28 | Insert / Complete / ErrStep / ErrCode | 9 / 1 / 2 / 1 |
| 29~44 | 초기 스틱 8워드 | 3262 / 3006 / 2978 / 2857 / 0 / 0 / 0 / 0 |
| 45~236 | 결과 레코드 | 6칸 전송, slot 4만 비어 있음 |
| 237~244 | QC 기준값 | `0e 8e 0e 6f 0e 70 0e 64` |
| 245~248 | Wake Fail min/max | `05 ff 0e 75` |

QC 기준값은 EEPROM `0x10D4~0x10DB`와 일치했다. Wake Fail (`0x10F8~0x10FB`) Min은 13:52 IAR에서 `0e 6f`였으나, 14:05 덤프에서는 `05 ff`였다. 그사이 스틱을 재삽입하며 관문 실패가 발생해 최솟값이 내려갔다. 14:07 IAR에서 다시 읽은 `05 ff 0e 75`는 덤프와 일치했다. 덤프와 EEPROM을 대조할 때는 두 측정 사이에 스틱을 재삽입하거나 기기를 동작시키지 않는다. 덤프 위치 `0x10F4`는 `03`이었다. 앞쪽 필드가 밀리지 않은 것도 확인했다. 이 QC 값은 임시 문턱값 100 시험 뒤 저장된 것이므로 정상 QC 기준값으로 해석하지 않는다.

덤프는 전역 측정 버퍼 대신 함수 지역 버퍼를 재사용하고, 초기 상태 정규화는 전송값에만 적용하도록 바꿨다. EEPROM Read/Write의 공유 `static` 반복 변수도 지역화했다. 빌드 7,193 + 284 = 7,477 B / 8,192 B, 남은 플래시 715 B, 에러·경고 0. 다만 이번 실기는 아래 두 안전 조건까지 증명하지는 않는다.

## 13. PC UI 생산용·개발용 분리

2차 녹음 [01:24]의 "넘겨주는 HTML에는 초기화 버튼이 없고 개발용에는 있다"는 지시에 따라, `설계문서/Test_UI/multi.html`을 개발용 원본으로 두고 `build_production.py`로 `multi-production.html`을 생성한다. 생산용은 `Q`(QC 세션 전체 초기화)와 `R`(Test Complete Count 초기화) 전용 버튼·핸들러·안내 문구를 포함하지 않는다. 포트 연결, `M` 덤프, 화면·CSV·PDF 출력, 수신 로그와 자유 입력 터미널은 공통으로 유지한다. 생산 공정에서 `R`이 필요하다는 지시는 없었으므로, 필요해지면 상급자 확인 후 추가한다.

**범위**: 이 분리는 전용 버튼을 실수로 눌러 이력을 지우는 경로를 없앤다. 생산용에도 자유 입력 터미널이 있어 `Q` 또는 `R`을 직접 입력할 수 있고, 다른 시리얼 도구로도 전송할 수 있다. 펌웨어 역시 두 명령을 계속 받는다. 따라서 생산용 HTML에는 초기화 **전용 코드**가 없지만 초기화 **수단이 완전히 차단된 것은 아니다**. 접근 통제나 보안 장치로 취급하지 않는다.

생성기는 `DEV-ONLY` 구간의 시작·끝이 각각 정확히 한 번 있는지 검사한다. 구간 제거 후 초기화 버튼 참조나 `Q`·`R` 명령 리터럴이 남으면 생성하지 않는다. UI를 바꾼 뒤 `python 설계문서/Test_UI/build_production.py`로 다시 만들고, `python 설계문서/Test_UI/build_production.py --check`로 생성물이 원본과 일치하는지 확인한다. 생성된 생산용 파일도 원본·스크립트와 함께 버전 관리한다.

생성기 단위 시험 4건과 Chrome 헤드리스의 생산용 HTML 로드 확인을 마쳤다. 2026-10-23 사용자가 생산용 UI 실기 검증 완료를 보고했다. 기기 번호, 항목별 결과와 덤프 증거는 전달받지 않아 이 문서에 기록하지 않았다.
