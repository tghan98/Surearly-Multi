# 6단계 — EEPROM 기록 구조 + PC UI 수정

> 상태: ✅ 완료 (2026-10-01)
> 브랜치: `feature/stage6-error-to-record`
> 선행: 5단계(기준값 2차 반영) 완료 · 기준서 `00_v11-작업기준서.md` 7장

---

## 왜 이 작업을 하나

에러 정보(Error Step·Error Code)가 **EEPROM 고정 주소 2·3번에 한 자리씩만** 있다.
새 에러가 나면 이전 것을 덮어쓰므로 **마지막 한 건만 남는다.**

검사 레코드는 32바이트짜리가 **7개 순환**한다. 그래서 덤프를 떠도 이렇게 된다.

```
[고정 주소]  Error Step 2 | Error Code 0x02     ← 한 건
[레코드]     회차 1~7 각각의 측정값              ← 일곱 건
```

**그 에러가 7회차 중 어느 회차 것인지 알 수 없다.** 실패한 회차의 측정값을
짚을 수 없으니 "실패할 때 값이 어땠나"를 볼 수가 없다.

생산 현상(검사오류 2, `ERROR_STICK_FAIL`)의 원인을 좁히려면 회차별 이력이 필요하다.
이것이 이 단계의 목적이다.

### 상급자 확정 (2026-10-01, 김효신 수석)

| 질문 | 답변 |
|---|---|
| 레코드로 옮기는 이유가 회차별 이력 추적이 맞는가 | **맞음** |
| 정상 종료 시 에러 변수를 0으로 지워도 되는가 | **그렇게 할 것.** 측정값과 같은 자리에서 같이 지운다 |

## 무엇을 바꾸나

### 펌웨어 ① — 레코드 끝 2바이트에 에러 정보

`USER/App/DM_Main_Sq_App.c`, `DM_App_Main_Sq_Save_Result_To_Rom()`

```c
/* 전 */
/* 5. Pack Dummy (2 bytes) */
awRomBuffer[idx++] = 0x0000;

/* 후 */
/* 5. Pack Error Step / Error Code (2 bytes) */
awRomBuffer[idx++] = (uint16_t)(((uint16_t)gs_bErrorSequence << 8) | gs_bErrorCode);
```

위 1바이트 = Error Step, 아래 1바이트 = Error Code (비트 패킹).
둘 다 `uint8_t`라 0~255, 자리를 넘지 않는다.

**레코드 크기는 32바이트 그대로**이므로 `DM_App_Rom_Save_CurrentResult()`의
주소 계산(`20 + 칸 × 32`)은 건드리지 않는다.

### 펌웨어 ② — 정상 회차에서 에러 변수 리셋

`DM_App_Main_Sq_Stick_Insert_Step_Handler()`의 0번 리셋 구역

```c
/* 0. Reset stale measurement/result data from the previous cycle ... */
DM_App_Optic_ResetGain();
gs_bErrorCode     = 0;        /* 추가 */
gs_bErrorSequence = 0;        /* 추가 */
for (i = 0; i < BAND_MAX; i++) { ... }
```

**근거**: `gs_bErrorCode`를 쓰는 곳은 두 군데뿐이고(`Enter_Error()`,
시료 미투입 타임아웃) 둘 다 에러 경로다. 정상 종료 때 0으로 되돌리는 코드가 없다.
그대로 두면 에러 다음 회차가 정상이어도 이전 에러 코드가 레코드에 찍힌다.

0번 구역의 기존 주석이 이미 같은 이유를 말하고 있다 —
"이전 회차의 묵은 데이터가 ROM에 저장되지 않도록". 에러 정보가 레코드의
다섯 번째 칸이 되는 순간 나머지 네 칸과 한 묶음이 된다.

### PC UI — `설계문서/Test_UI/multi.html`

| # | 내용 |
|---|---|
| 1 | 두 번째 표(Insert Count …)에서 **Error Step·Error Code 열 삭제** |
| 2 | 맨 아래 레코드 표 **맨 오른쪽에 Error Step·Error Code 두 열 추가** |
| 3 | 세 번째 표를 **T·BT·BC·C 네 열로** 정리 (아래 "지시 해석" 참조) |
| 4 | `PWM CH1~4` → **`Gain CH1~4`** (PWM을 걷어냈으므로) |
| 5 | Range 문구 → `1500 ≤ 측정값 ≤ 3900` (아래 "경계값" 참조) |
| 6 | **`buildRawDumpCsv()`도 같이 수정** — 화면과 CSV가 어긋나면 안 된다 |
| 7 | **Range 상수(356·357행)** `STICK_DUTY50_RANGE`·`STICK_DUTY100_RANGE` → `[1500, 3900]` 단일 상수로 |
| 8 | **초기화 기본값(365행)** 의 `initialStick` 모양을 파싱부(624행)와 같게 |
| 9 | `records`의 내부 변수명 `pwm` → `gain` |

**경계값은 포함(`≤`)이다.** 펌웨어 범위 검사와 UI `isOutOfRange()` 모두
`값 < 하한 || 값 > 상한`이라 1,500과 3,900은 **통과**한다.
상급자 지시도 "min 1500 ~ max 3900, 이 범위 밖이면 기계 에러"였으므로 경계는 범위 안이다.
문구를 `<`로 쓰면 표시와 판정이 어긋나므로 `≤`로 적는다.
**표시 문구에 맞추려고 펌웨어 검사를 바꾸지 않는다** — 1,500이 나온 스틱이 기계 에러로 떨어진다.
(에이전트가 구현 중 확인 요청한 항목. 2026-10-01)

**7·8번은 에이전트 검토(2026-10-01)에서 추가됐다.** 둘 다 "고치려는 곳과 짝을 이루는 다른 곳"이다.

- **7번** — Range 상수는 화면 문구와 `isOutOfRange()`의 경고색 판정에 **같이** 쓰인다.
  문구만 글자로 바꾸면 "1500~3900 정상"이라 써놓고 3,523에 경고색이 들어간다.
  상수를 바꿔야 문구와 판정이 같이 움직인다.
- **8번** — 365행은 데이터를 받기 전 화면(`-` 표시)을, 624행은 받은 뒤를 만든다.
  **두 곳이 같은 모양의 객체를 만들어야** 한다. 624행만 네 열로 바꾸면
  프로그램을 처음 열었을 때 표가 깨진다.

파서는 이미 레코드마다 `dummy`를 읽고 있다(`const dummy = readWord();`).
읽기는 그대로 두고 **쪼개서 표시**만 추가하면 된다.

```js
const errStep = (r.dummy >> 8) & 0xFF;
const errCode =  r.dummy & 0xFF;
```

## 지시 해석 — 세 번째 표는 네 열로

상급자 지시는 "Duty 50% 열은 지우고 100%만 남겨라"였다. 의도는 **밴드당 한 열로 줄이는 것**이고,
그 의도대로 하면 지금 구조에서는 읽는 칸이 달라진다.

`multi.html`의 파서는 초기 측정 16바이트를 밴드별 2워드(`duty50`, `duty100`)로 읽는다.

```js
const initialStick = STICK_BANDS.map(band => ({ band, duty50: readWord(), duty100: readWord() }));
```

PWM 시절에는 밴드마다 듀티 50%·100%를 각각 쟀으므로 8칸이 모두 찼다.
4단계에서 PWM을 걷어내며 **채널당 1회 측정**이 됐고, `MeasureInitialStick()`은
앞 4워드에 CH0~CH3를 넣고 **뒤 4워드는 0으로 둔다.**

```
PWM 시절:  T50  T100  BT50  BT100  BC50  BC100  C50  C100   ← 8칸 전부
현재    :  T    BT    BC    C      0     0      0    0      ← 앞 4칸만
```

채널과 밴드는 같은 것이다 — CH0=T, CH1=BT, CH2=BC, CH3=C.

따라서 문구 그대로 "100%만" 남기면 칸 1·3·5·7이 남아 **CH1, CH3, 0, 0**이 된다.
듀티라는 개념 자체가 없어졌으므로 **T·BT·BC·C 네 열로 바꾸고 앞 4워드를 읽는다.**
읽는 칸만 다를 뿐 지시의 의도(밴드당 한 열)와 결과는 같다. 보고 시 한 줄로 언급한다.

## 어떻게 확인할 건가

중단점은 `DM_Main_Sq_App.c`의 `DM_App_Main_Sq_Save_Result_To_Rom()` —
**`awRomBuffer[idx++] = ... ;`(5번) 직후**. 그 자리에서 `awRomBuffer` 전체를
Watch에 올리면 32바이트가 어떻게 조립됐는지 한 화면에서 보인다.

| 항목 | 기대값 | 어긋나면 |
|---|---|---|
| 빌드 | 에러 0, 경고 0, Flash 8,192B 이내 | — |
| `awRomBuffer[15]` (에러 회차) | `(Step << 8) \| Code`. 예: STICK_INSERT(2)+0x02 → **0x0202** | 비트 패킹 식 확인 |
| `awRomBuffer[15]` (정상 회차) | **0x0000** | 리셋 2줄이 빠졌거나 자리가 틀림 |
| 에러 → 정상 연속 2회 | 2회차가 **0x0000** | 리셋이 동작하지 않음 |
| EEPROM 덤프 | 회차별로 서로 다른 에러가 찍힘 | — |
| UI 화면 | 맨 아래 표 오른쪽에 두 열, 두 번째 표에는 없음 | — |
| CSV | 화면과 열 구성이 동일 | `buildRawDumpCsv()` 누락 |

**연속 2회 시험이 이번 검증의 핵심이다.** 1회차를 일부러 실패시키고(스틱을
중간에 빼면 된다) 2회차를 정상 완료시켜, 2회차 레코드가 0으로 찍히는지 본다.
리셋 2줄이 없으면 여기서 1회차의 에러 코드가 그대로 나온다.

| | 내용 |

| 펌웨어 ① | `Save_Result_To_Rom()` 5번 줄을 `(gs_bErrorSequence << 8) | gs_bErrorCode`로 교체 |

검토 과정에서 UI 항목이 6건 → 9건으로 늘었다. 7·8번(Range 상수, 초기화 기본값)은

남고, 파싱부만 바꾸면 데이터 수신 전 화면이 깨진다.

## 확인된 것

### 빌드

| 항목 | 값 |
|---|---|
| 에러 / 경고 | **0 / 0** |
| Flash 합계 | **6,764 B / 8,192 B (82.6%)** |

5단계(6,743 B) 대비 +21 B. 비트 패킹 연산과 리셋 2줄이 들어간 만큼이다.

### 보드 실측 (디버거 Watch)

**중단점 ①** — `Save_Result_To_Rom()`의 5번 줄 직후 (F10 한 번)

| 확인 항목 | 결과 |
|---|---|
| 재료 | `gs_bErrorSequence = 0x02`(STICK_INSERT), `gs_bErrorCode = 0x01`(STICK_REMOVE) |
| 결과 | `awRomBuffer[15] = 513` = `0x0201` |
| **비트 패킹 일치** | ✅ `0x02 << 8 = 512`, `512 \| 1 = 513`. 재료와 결과가 정확히 일치 |

**중단점 ②** — `Stick_Insert_Step_Handler()`의 `gs_bErrorCode = 0;` 줄

에러 1회 → 2분 대기 → 정상 삽입 순서로 확인.

| 시점 | `gs_bErrorCode` |
|---|---|
| 중단점에 걸린 순간 (실행 전) | **0x01** — 지난 회차 값이 남아 있음 |
| F10 한 번 뒤 | **0x00** — 지워짐 ✅ |

**묵은 값이 지워지는 순간을 직접 본 것이 이번 검증의 핵심이다.**
순서가 중요하다 — 에러를 먼저 만들어야 지울 것이 생긴다. 정상 → 에러 순서로는
아무것도 가려지지 않는다.

기기에서 최근 7회 기록을 읽어 `multi.html`로 띄워 확인했다.

| 확인 항목 | 결과 |

실패했는가"를 짚을 수 있다.


## 걸린 것 · 남은 것

보드 검증 중 LCD가 켜지지 않아 중단. 원인은 코인셀 방전이었다
(CH3 측정값 434 → 전지 교체 후 3,698). 반나절 소요.

**남은 이상 (원인 미확정)**: Insert Count 13 / Test Complete Count 0(시험 중 `R` 리셋 없음)인데
슬롯 0·4·6(화면 1·5·7회차)이 전부 0에 `ERROR NONE`으로 찍힌다.

삽입 카운트는 `Stick_Insert` 진입 즉시 EEPROM에 적히지만(`DM_Main_Sq_App.c:248`),
레코드는 `RESULT_OUT` / `ERROR_WAIT` / `SAMPLE_LOAD_FAIL` 세 곳에서만 저장된다.
**삽입 수와 레코드 수는 원래 일치하지 않는다.** 13회는 슬롯 0~6을 모두 한 번 이상 순환하며,
카운트가 13까지 누적된 것 자체가 그 기간 EEPROM이 지워지지 않았음을 뜻한다.

그럼에도 빈 슬롯을 "저장 실패"로 **단정할 수 없다.** 13회 구간에 6단계 적용 **전** 빌드가
섞여 있고, 구 빌드가 초기 단계 에러를 저장하면 word 15가 Dummy(0)이고 배율·밴드도 모두 0이라
**저장되지 않은 슬롯과 화면상 구분되지 않기 때문이다.**

**판별 시험**: EEPROM 초기 상태를 확인하고 전원을 유지한 채, **저장 경로가 실행되는 회차를 7회**
만들어 슬롯 0~6이 모두 갱신되는지 본다(정상 완료 7회가 아니다 — 에러 회차도 슬롯을 차지한다).
전부 현재 빌드로 돌리면 구 빌드 혼입 변수가 사라지고, 그래도 빈 칸이 남으면 그때는 결함이다.
7단계 스윕 때 병행한다.

**남은 것**: 커밋·푸시.

## 오늘의 교훈

**중단점은 그 줄을 실행하기 전에 멈춘다.** 결과를 보려면 F10 한 번 누르거나
다음 줄에 찍어야 한다. 이번에 `wADC`, `awRomBuffer[15]`, `gs_bErrorCode`
세 번 모두 같은 데서 걸렸다.

**최적화된 빌드에서는 지역 변수가 Watch에 안 잡힐 수 있다.**
짧은 함수는 줄 경계가 뭉개져 F10 한 번에 함수 전체가 지나간다.
`volatile` 전역에 담아 보는 방법이 있고, 확인 후 반드시 지운다.

**검증은 "무엇을 증명하려는가"가 중단점 위치를 정한다.**
비트 패킹은 재료와 결과를 한 화면에서 대조해야 하므로 조립 직후,
리셋은 묵은 값이 지워지는 그 줄이어야 한다. 위치를 먼저 정하고 조작 순서를 맞춘다.

## 끝맺음 한 문장

에러 정보를 고정 주소에서 레코드 안으로 옮겨, 최근 7회차가 각자 자기 에러를 들고
있게 만들었다. 이제 덤프만으로 "몇 회차에서, 어느 단계에서 실패했는가"를 읽을 수 있다.
