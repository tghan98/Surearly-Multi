## 2. 문제 ① — 상태 이월 (해결)

### 패턴 이름: 상태 이월

> 한 회차가 남긴 값이 다음 회차로 넘어가서, **첫 판정을 오염시키는** 것.

### 증거 — 최저값이 `65535`

임시 계측을 심은 뒤 뽑은 덤프(`기기05_20261019_145514`)에서 결정적인 값이 나왔다.

| 줄 | Step | Error Code | 배율 | ET | 최저값 |
|---|---|---|---|---|---|
| 1 | **1** | `STICK_REMOVE` | 32/32/32/33 | 채워짐 | **65535** |
| 2 | **1** | `STICK_REMOVE` | 32/32/32/33 | 채워짐 | **65535** |

65535(= 0xFFFF)는 초기값이다. **스틱 검사 함수가 한 번도 불리지 않았다**는 뜻인데,
에러는 "스틱이 빠졌다"로 났다. **재보지도 않고 내린 판정이다.**

### 원인 코드

```
USER/App/DM_LCD_Stick_Check_App.c   DM_App_Stick_Get_Status()

    static uint16_t wCheckCounter = OPTIC_STICK_CHECK_INTERVAL_COUNT;  /* = 25 */
    static STICK_STATUS_t tCachedStatus = STICK_STATUS_INSERTED;

    if (wCheckCounter < OPTIC_STICK_CHECK_INTERVAL_COUNT)
    {
        wCheckCounter++;
        return tCachedStatus;        ← 재지 않고 지난 답을 돌려준다
    }
```

- 두 변수가 `static` 이라 **전원이 끊기기 전까지 살아 있다.** 기기는 측정이 끝나도
  Halt 로 잠들 뿐이므로 RAM 이 지워지지 않는다.
- 카운터는 **시간이 아니라 호출 횟수**로 센다. 측정 사이에는 아무도 부르지 않으므로
  몇 분이 지나든 카운터가 올라가지 않는다.
- 실측까지는 25회 × 250ms = **6.25초**가 걸린다. LCD 삽입 애니메이션이 그 전에 끝나면
  한 번도 안 재보고 지난 답만 쓰다 끝난다.

```
이전 회차에 스틱을 뺐다   →  tCachedStatus = REMOVED 로 남음
새 스틱을 꽂는다          →  카운터가 25에 못 미침 → 저장된 REMOVED 를 반환
                         →  즉시 에러
```

선언부가 25로 시작하는 것은 **"처음 한 번은 무조건 재라"**는 의도다. 다만 그 "처음"이
**전원 켤 때 딱 한 번**이었던 것이 문제였다.

### 오늘 기록이 그대로 맞아떨어진다

| 그 run 의 끝 | 다음 run |
|---|---|
| 완주 | 정상 ✓ |
| 완주 | 정상 ✓ |
| 완주 | 정상 ✓ |
| **스틱 뺌 (REMOVED)** | **즉시 에러** ✓ |
| 11:25 Step 5 에러 (REMOVED) | 11:41 즉시 에러 ✓ |

**실패가 다음 실패를 부르고, 성공이 다음 성공을 부른다.** 리빌드(Download)를 하면
RAM 이 초기화되므로 그때마다 한 번씩 풀렸다 — "귀신같이" 됐다 안 됐다 하던 정체가 이것이다.

### 수정

```
USER/App/DM_LCD_Stick_Check_App.c   static 2개를 파일 범위로 올리고
                                    DM_App_Stick_Reset_Status() 신설
USER/App/DM_LCD_Stick_Check_App.h   선언 추가
USER/App/DM_Main_Sq_App.c           삽입 핸들러의 "0. Reset stale ..." 블록에서 호출
```

호출 자리는 이미 있던 "이전 회차의 묵은 값을 지운다" 블록 바로 옆이다. 원작자가 이 문제의
**종류**는 알고 있었고, 스틱 상태 캐시만 그 목록에서 빠져 있었다.

```c
    DM_App_Optic_ResetGain();
    DM_App_Stick_Reset_Status();   /* 추가 */
    gs_bErrorCode = 0;
```

리셋은 카운터를 0이 아니라 `OPTIC_STICK_CHECK_INTERVAL_COUNT`(25)로 되돌린다.
**다음 호출에서 곧바로 실측하라**는 뜻이며, 선언부의 초기값과 같다.

> **LED 절약 의도를 어기지 않는다.** 회차 안에서의 25회 규칙은 그대로고, 삽입 1회당
> 실측이 1회 늘 뿐이다 (5분 대기 기준 약 48회 → 49회).

### 검증

같은 조건(스틱을 뺀 직후 새 스틱)으로 재현했다.

| | 상황 | Step | 최저값 | 뜻 |
|---|---|---|---|---|
| 수정 전 | 뺀 직후 새 스틱 | **1** | **65535** | 안 재보고 에러 |
| **수정 후** | 뺀 직후 새 스틱 | **2** | **457** | **재보고 정상 진행** |

수정 후에는 물방울(시료 투입 요청)까지 정상 진행했고, 최저값이 초기값이 아닌
실측치로 기록됐다. **고리가 끊겼다.**

> 검증 시 주의: **전지를 빼면 안 된다.** 빼면 RAM 이 지워져 캐시도 같이 사라지므로
> 수정 여부와 무관하게 정상 동작한다. 리빌드·Download 도 마찬가지다.

### 양산 불량과는 별개다

구형 펌웨어(`MFx_v2.1.1_alpha.2`)를 확인했다.

```
BSP/BSP_StripCheck.c   38~54행

if (STP_CK_PORT->IDR & STP_CK_PIN)   ← 스위치 핀을 직접 읽음
```

| | 구형 (양산) | 신형 (지금) |
|---|---|---|
| 판정 수단 | **SW1 스위치** | **광학 CH3** |
| 캐시 | **없음** | 있음 |
| 카운터 | **없음** | 25회에 1회 |

구형은 부를 때마다 핀을 직접 읽는다. 저장해두는 값이 없으니 이월될 것도 없다.

→ **이 문제는 신형 펌웨어에서 새로 생긴 것이며, 양산 불량의 원인이 아니다.**

그리고 왜 광학으로 바꿨는지도 신형 코드 주석에 남아 있다.

> STP_CK switch is used only as the Halt wake-up trigger (**unreliable for continuous
> status: mechanical play lets contact momentarily separate while the stick is still
> inserted**)

```
양산 불량    스위치 접점이 순간 떨어짐 (기구 유격)
   ↓ 대응
신형 설계    광학으로 판정하도록 변경
   ↓ 부작용
새 결함      캐시 구조가 들어가면서 상태가 이월됨   ← 오늘 찾은 것
```

## 3. 문제 ② — 문턱값 625가 빠듯하다 (미결)

### 패턴 이름: 한 구간으로 정한 문턱값

> 여러 구간에서 쓰이는 판정선을, 그중 **한 구간의 데이터만** 보고 정한 것.

같은 스틱 체크가 네 군데에서 돈다.

```
DM_Main_Sq_App.c  296행   Step 1  삽입 (LCD 애니메이션 대기)
                  대기 루프 Step 2  시료 투입 대기
                  481행   Step 3  과유입 체크
                  535행   Step 4  소량 체크
                  583행   Step 5  반응 대기
```

10-14 에 625를 정할 때 실측한 것은 **시료 투입 구간 5분뿐**이었고, 기기도 1대뿐이었다.

### 측정 결과 (5번 기기, 모두 완주)

| 회차 | 덤프 | 젖은 최저 | 625와의 여유 |
|---|---|---|---|
| 1 | `기기05_20261019_140044` | 794 | 169 |
| 2 | `기기05_20261019_141002` | 750 | 125 |
| 3 | `기기05_20261019_144138` | **625** | **0** |

판정식은 `wVal < 625` 이므로 625는 **간신히 통과**했다. 1만 더 낮았으면 에러였다.

회차마다 내려가는 방향이 뚜렷하고, 결과 C밴드(`RC`)와 함께 움직인다.

| 회차 | 젖은 최저 | RC | C Intensity |
|---|---|---|---|
| 1 | 794 | 987 | 1210 |
| 2 | 750 | 958 | 1240 |
| 3 | 625 | 886 | 1273 |

### 바닥값 (스틱을 일부러 뺀 측정)

| 회차 | 덤프 | 뺀 값 |
|---|---|---|
| 1 | `기기05_20261019_145035_뺀값` | 454 |
| 2 | `기기05_20261019_162257` | 452 |
| 3 | `기기05_20261019_162436` | 457 |

452~457. 흔들림이 5뿐이다. **5번 기기의 바닥 ≈ 454.**
10-14 에 1번 기기에서 잰 449와도 거의 같다 — 배율이 기기 차이를 정규화하고 있다는 뜻이다.

### 기기별 측정 — 10-14 에 정상 완주했던 6대

측정 절차(기기당 덤프 1회):
스틱 꽂자마자 쭉 빼기(→ 바닥값) → 같은 스틱을 다시 꽂아 물 적시고 끝까지(→ 젖은 최저) → 덤프.
덤프 1번 줄이 젖은 최저, 2번 줄이 바닥값이다. 마른 스틱이라 한 기기에 스틱 1개면 된다.
2단계가 "빠짐"으로 끝난 직후 3단계를 하므로 **상태 이월 수정 검증도 기기마다 함께 이루어진다.**

| 기기 | 젖은 최저 | 바닥 | 여유 (젖은−625) | 덤프 |
|---|---|---|---|---|
| 5 | 794 / 750 / **625** | 454 / 452 / 457 | 169 / 125 / **0** | `140044` `141002` `144138` `145035` `162257` `162436` |
| 11 | **728** | 465 / **488** | 103 | `163546` `164304` |
| 1 | **800** | 447 | 175 | `165428` |
| 12 | **633** (20초 담금) | 482 | 8 | `170335` |
| 2 | **696** | 420 / 431 | 71 | `171342` · 아침엔 무반응, 오후엔 스틱으로 깨어남 |
| 10 | (1031) ※ | 451 | — | `172726` · **스틱이 제자리에 없었음. 아래 별도 항목 참조** |

> ※ 10번의 1031은 **유효한 젖은 최저가 아니다.** 검사 도중 스틱이 떠올라 값이 거꾸로
> 올라갔다(아래 "살짝 빠짐" 항목). 울타리 계산에서 제외한다.
>
> 11번의 728, 1번의 800, 12번의 633, 2번의 696 모두 5번의 범위(625~794) 안에 들어온다.
> **기기 하나가 유별난 것이 아니라 공통 현상이다.**
>
> 12번은 실수로 **20초**를 담갔다(규정은 10초). 담금 시간을 두 배로 했는데도 633으로,
> 5번의 625와 비슷한 수준이었다 → **담금 시간이 주된 변수는 아닌 것으로 보인다.**

#### 에러 아이콘과 코드의 대응 (10-19 확인)

| 화면 | 에러 코드 | 뜻 |
|---|---|---|
| 책 + 물방울 | `ERROR_STICK_REMOVE` (0x01) | C밴드 변화 **이전** 제거 |
| **책만** | `ERROR_STICK_FAIL` (0x02) | C밴드 변화 **이후** 제거 |

아이콘 번호(검사오류 1/2)와 코드 번호가 서로 다르게 매겨져 있으므로 혼동에 주의.

#### ★ 10번 기기 — "살짝 빠짐"의 실제 사례를 잡았다

10-15 에 상사분이 지시하신 **"카세트가 살짝 빠졌을 때도 기기가 잡아줘야 한다"**는 그
상황이 오늘 우연히 관찰됐다. (`기기10_20261019_172726` 1번 줄)

| | |
|---|---|
| Error Code | `ERROR_C_LINE_FAIL` |
| Error Step | **6** (결과 스캔) — 끝까지 진행했다 |
| 최저값 | **1031** |

**최저값이 1031이다. 스틱 빠짐 판정(625)에는 근처도 가지 않았다.** 즉 기기는 스틱이
정상적으로 꽂혀 있다고 믿은 채 끝까지 갔다.

##### 결과값이 빈 상태보다 높다

| 밴드 | 빈 상태 (E) | 결과 (R) | 차이 |
|---|---|---|---|
| T | 1191 | 1307 | +116 |
| BT | 1199 | 1269 | +70 |
| BC | 1190 | 1303 | +113 |
| C | 1204 | **1452** | **+248** |

시료가 적시면 어두워져야(값이 내려가야) 하는데 **밝아졌다(올라갔다).**
10-06 실측에서 확인된 "살짝 빠짐" 신호와 방향이 같다.

```
정상 안착   3,368
살짝 빠짐   3,618   ← 값이 올라간다
플라스틱만    701
```

##### 패턴 이름: 단방향 판정

> 판정이 **한쪽 방향만** 본다 — "낮으면 빠짐"만 보고, 값이 **높아지는 것은 보지 않는다.**

그래서 스틱 체크는 무사히 통과했고, 결과 스캔 단계에서 C선이 안 잡혀 `C_LINE_FAIL` 로 끝났다.
**판정이 한 단계 늦게, 엉뚱한 이름으로 난 셈이다.**

##### 정황 증거

측정 전에 **SW1 이 기구 유격으로 스틱 삽입을 못 잡아, 힘을 줘서 밀어 넣어야** 감지됐다.
(손으로 직접 확인한 사실이며 추정이 아니다.) 유격이 심한 기기이고, 검사 도중 스틱이
다시 떠오른 것으로 보인다.

##### 남는 과제

- 이 현상을 **의도적으로 재현**할 수 있는지 (스틱을 1~2mm 들어 올린 채 고정)
- 네 채널을 모두 재서 **채널 간 비교로 갈라지는지** 확인
  (→ `2026-10-15_살짝빠짐_검출.md` 의 4채널 실측 계획과 이어진다)
- 지금 계측(`g_DbgMinVal`)은 **최저값만** 본다. 살짝 빠짐은 값이 올라가므로
  **최댓값도 같이 봐야** 잡힌다

#### 관찰 — 2번 기기는 광량이 35% 낮다

| | 초기 원본값 | 배율 |
|---|---|---|
| 1·5·11·12번 | 약 3,700 | 32~33 |
| **2번** | **2,345 ~ 2,976** | **40 ~ 51** |

채널별 편차도 크다(BT 2,345 ~ T 2,976). 다른 기기는 네 채널이 거의 같다.
배율이 보정해 주므로 ET 는 1,190대로 정상이고 완주도 했지만, **광량이 낮은 원인은 따로
봐야 한다** (LED 열화 / 광학 경로 오염 등).

#### 관찰 — 깨우기는 여전히 스위치에 의존한다

2번은 아침에 스틱 삽입 무반응이었으나 오후에는 **전지를 바꾸지 않고** 스틱으로 깨어났다.
→ 전지 문제가 아니라 **간헐적 기구 접촉**이다.

10번은 더 분명하다. **SW1 이 눌리지 않아 힘을 줘서 밀어 넣어야** 삽입이 감지됐다.
스틱이 정상 삽입 깊이로는 스위치를 누르지 못한다는 뜻이며, 손으로 직접 확인한 사실이다.

신형 펌웨어는 스틱 유무 **판정**만 광학으로 바꿨고, **Halt 에서 깨우는 것은 여전히 SW1**이다.

```
스틱 유무 판정   스위치 → 광학으로 변경   (신형)
Halt 깨우기      스위치 그대로            ← 구형의 기구 유격 문제가 여기 남아 있다
```

구형 코드 주석의 "mechanical play lets contact momentarily separate"가 **깨우기 경로에는
그대로 살아 있다.** 아침의 2·10번 무반응이 이것일 가능성이 크다.

#### 관찰 — 스틱을 빼면 "시료 도착"으로 읽힐 수 있다 (가설, 미확인)

12번에서 꽂자마자 뺐는데 **Step 4(소량 체크)까지 진행**된 뒤 에러가 났다
(`170335` 2번 줄, 네 채널 모두 430~493으로 붕괴).
스틱을 빼면 C값이 뚝 떨어지는데, 그 변화가 "시료가 도착했다"로 해석되어 다음 단계로
넘어간 것으로 보인다. **확인된 바는 아니며, 따로 검증이 필요하다.**

#### 새 판정선을 가두는 울타리

```
위쪽 한계 = 젖은 최저 중 가장 낮은 값     ← 이보다 낮아야 정상 동작이 안 끊긴다
아래쪽 한계 = 바닥 중 가장 높은 값        ← 이보다 높아야 진짜 제거를 잡는다
```

현재까지(5·11번):

| | 값 | 출처 |
|---|---|---|
| 위쪽 한계 | **625** | 5번 3회차 |
| 아래쪽 한계 | **488** | 11번 |
| 창 폭 | **137** | |

6대 측정 완료 기준이며, 10번(스틱 미안착)은 제외했다.
젖은 최저는 625~800, 바닥은 420~488 범위에 모였다. **기기별 편차가 크지 않다** —
배율이 기기 차이를 제대로 정규화하고 있다는 뜻이다. 2번은 광량이 35% 낮은데도
젖은값 696, 바닥 420으로 같은 범위에 들어왔다.

지금 판정선 625는 이 창의 **맨 위에 붙어** 있다.

> 기기를 더 재면 창은 **좁아지지 넓어지지 않는다.** 6대를 다 채운 뒤에 정할 것.
> 그리고 젖은 최저가 625보다 더 내려갈 수 있다는 점(오전 에러가 그 증거)은
> 아직 수치로 잡지 못했다.

### 지금 서 있는 자리

```
마른 스틱     약 1,185   (ET)
젖은 최저       625      ← 더 내려갈 수 있음 (오전 에러가 그 증거)
판정선          625      ← 지금. 여유 0
바닥            454
```

판정선이 젖은 최저와 **딱 붙어** 있다. 내릴 수 있는 공간은 **171**.

> **정정** — 이 문서의 이전 판에 "마른 스틱 1,200 기준으로 절반 아래로 폭락한 것"이라고
> 적었으나 **틀렸다.** 시료가 도착하면 625 근처까지 내려오는 것이 정상 거동이다.
> 폭락이 아니라 원래 그만큼 내려온다.

## 4. 계측 방법을 두 번 바꾼 경위

### 시도 1 — 조건부 브레이크포인트 (실패)

`wVal < 625` 조건을 걸려 했으나 IAR 이 거부했다.

> One or more breakpoints could not be set and have been disabled.

코드가 플래시에 있어 하드웨어 비교기를 써야 하는데 STM8L 은 그것이 2개뿐이다.
조건부는 자원을 더 요구하고, 지역 변수 `wVal` 은 최적화로 레지스터에만 있거나 사라져
조건식을 평가할 대상 자체가 없다.

### 시도 2 — 전역 변수 + Break (실패)

#### 패턴 이름: 잠든 코어

> 저전력 구조(`while` + `wfi`)로 코어가 대부분 자고 있어서, 디버거가 붙잡을 대상이 없는 것.

물방울이 떠 있어도 LCD 만 켜져 있을 뿐 코어는 250ms 중 대부분 자고 있다.
**이 기기는 디버거로 실시간 관찰이 사실상 불가능하다.**

### 시도 3 — 덤프에 실어 보내기 (채택)

값을 결과 레코드에 실어 CSV 로 읽는다. 디버거가 필요 없고, 기기 단독 시나리오를
그대로 돌릴 수 있으며(꽂은 채로 적시기 가능), **성공한 run 에서도 값이 남는다.**

레코드 16칸은 전부 차 있다. 명세 문서(`EEPROM_UART.md`)는 word 15 를 `Dummy` 라고
적어두었지만 **실제 코드는 거기에 에러 단계·코드를 넣는다 (문서가 낡았다).**
그래서 `T Intensity` 칸을 빌렸다. 이 값은 같은 레코드의 RT·ET·RBT·EBT 로 다시
계산할 수 있으므로 잃는 정보가 없다.

#### 패턴 이름: 누적 상태 미초기화

> 매 회차 새로 재야 할 값이 이전 회차 값을 물고 있는 것.

최저값은 "더 낮을 때만" 갱신된다. 기기는 측정 후 전원이 꺼지지 않고 Halt 로 잠들 뿐이라
RAM 이 남는다. 되돌리지 않으면 1회차의 최저값이 이후 모든 회차에 계속 찍혀서
"매번 아슬아슬하구나"라고 잘못 읽게 된다. → **레코드에 실은 직후 `0xFFFF` 로 되돌린다.**

> 이 패턴은 문제 ①(상태 이월)과 뿌리가 같다. 계측 코드를 짜다가 같은 함정을 한 번 더
> 밟을 뻔했고, 그 덕에 ①을 알아보기 쉬웠다.

## 5. 측정 절차

```
1. 지그에서 분리 — 기기 단독 상태
2. 스틱 꽂기
3. 꽂은 채로 물 적시기          ← 빼지 않는다
4. 끝까지 둔다 (완주하든 에러나든)
5. 지그에 물려서 덤프
```

- **3번** — 빼서 적시면 기기 입장에서는 진짜로 스틱이 빠진 것이라 `STICK_REMOVE` 가
  정상 동작이 된다. 지그에 물린 채로는 빼서 적시게 되므로 조건이 달라진다.
- **4번** — 중간에 덤프를 뽑으면 이번 run 은 아직 저장 전이다. 레코드는 에러가 나거나
  결과가 나올 때만 저장된다.
- **바닥값을 잴 때**는 3번 대신 "한 번에 쭉 빼기". 스틱 검사가 6.25초마다 돌기 때문에
  천천히 빼면 어중간한 값이 기록된다.

덤프는 `설계문서/Test_UI/RawDump/최저값측정_20261019/` 에 `기기05_YYYYMMDD_HHMMSS.csv`
(바닥값은 `_뺀값` 꼬리표)로 모은다.
