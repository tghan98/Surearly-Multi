## 왜 이 작업을 하나

2단계에서 배율 방식이 성립한다는 것까지 확인했고(포화 없음, 여유 10%, 편차 0.2%),
2026-09-28 추가 지시로 **기준값이 모두 확정**됐다.

| 항목 | 확정값 |
|---|---|
| 양품 구간 | **1,500 ~ 3,900** (벗어나면 기계 에러) |
| 튜닝 목표값 | **1,500** |
| 필터 | 20샘플 정렬 → 위아래 2개씩 제외 → **중앙 16개 평균** |
| 배율 | `목표값 × 100 ÷ 측정값` (정수), 적용은 `÷ 100` |

지금까지는 진단 루틴으로만 측정했고 **본 광학 코드는 여전히 on-time 방식**이다.
이제 확정값을 본 코드에 반영한다.

## 무엇을 바꾸나

### 1. 필터 — 합계에서 평균으로

`DM_App_Optic_Measure()`의 반환을 **중앙 16개 평균**으로 바꾼다.

```
현재 : 20샘플 정렬 → 상하 3개씩 제외 → 중앙 14개 합계  (최대 약 57,330)
변경 : 20샘플 정렬 → 상하 2개씩 제외 → 중앙 16개 평균  (0 ~ 4,095)
```

이것으로 측정값이 단일 샘플 스케일이 되어, 확정된 1,500·3,900과 직접 비교할 수 있다.
채널 변경 후 **첫 변환 버림**도 함께 추가한다(현재 진단 루틴에만 있음).

### 2. on-time 잔재 제거

- `DM_App_Optic_Measure()`의 `wOnTime_us` 인자
- `OPTIC_ONTIME_DEFAULT / MAX / X1 / X2`
- `DM_HW_Drv_Delay_us()`, `DELAY_US_CAL`
- `MeasureInitialStick()`의 `awPWM_Set[2] = {199, 399}`
- `TuneTargetADC()`의 0~399 클램프, P제어 5회 반복

LED ON 후 대기는 **20ms 안정화**(`SystemSleep_10ms() × 2`)로 고정한다.

### 3. 배율 튜닝 구현

```c
/* 튜닝 시점 */
배율 = (uint16_t)((uint32_t)1500 * 100 / 측정값);   /* 0~100, 정수 */

/* 측정 적용 시점 */
최종값 = Cal_Ratio(측정값, 배율);                    /* = 측정값 * 배율 / 100 */
```

`Cal_Ratio()`는 `DM_Utill.c`에 이미 있고 내부가 uint32이므로 **추가 코드가 없다.**

**방어는 2중으로 한다.**

**1차 — 양품 구간 검사.** `MeasureInitialStick()`이 튜닝보다 먼저 실행되어 측정값을
1,500~3,900과 비교하고, 벗어나면 기계 에러로 빠진다. 하한이 목표값과 같으므로 이 검사를
통과한 시점에 배율은 이미 100 이하다. **별도의 `ERROR_OPTIC_FAIL_CHx` 경로는 두지 않는다.**

**튜닝은 재측정하지 않는다.** `MeasureInitialStick()`이 채운 `pInitBuffer`를 그대로 쓴다.
같은 시점·같은 조건의 값이라 다시 잴 이유가 없고, 채널당 약 34ms × 4채널 = 약 136ms의
LED 점등을 아낀다(코인셀 전력 여유 미확인).

**2차 — 범위 재검증 한 줄.**

```c
/* 방어적 재검증 — 호출자가 범위 검사를 거쳤다는 전제를 이 함수 안에서 다시 확인한다.
   정상 흐름에서는 걸리지 않으며, 걸린다면 호출 순서가 깨진 것이다.
   반환값 주의: 1은 OPTIC_ERR_STICK_REMOVED로 이미 쓰이고 있어, 1을 돌려주면
   호출부가 "검사 중 스틱이 빠졌다"(ERROR_STICK_REMOVE)로 기록한다.
   이 프로젝트가 추적 중인 현상과 같은 에러 코드라 로그 분석에서 오진을 유발한다. */
if ((측정값 < OPTIC_INITIAL_MIN_100) || (측정값 > OPTIC_INITIAL_MAX_100))
    return (uint8_t)(FAIL_OPTIC_CH0 + bCh);   /* 0x10~0x13 → ERROR_OPTIC_FAIL_CHx */

배율 = (uint16_t)((uint32_t)1500 * 100 / 측정값);
```

버퍼를 재사용하므로 값이 이미 1,500~3,900임이 보장된다. **0 나눗셈도 배율 100 초과도
구조적으로 발생하지 않으므로 가드를 따로 두지 않고, 이 한 줄로 둘 다 덮는다.**
이 함수가 호출 순서에 의존하지 않게 만드는 것이 목적이다.

**배율 적용 위치** — `Measure()`는 **원본값을 반환**하고, 호출부에서
`Cal_Ratio(Measure(ch), GetGain(ch))`로 적용한다. `DM_Main_Sq_App.c` 9곳
(400·401·414·415·486·540·624~627)을 일괄 변경한다.

**버퍼 처리** — 2점 측정 폐지로 채널당 1값, 총 4워드가 된다. 그러나
`gs_awInitialStickPtr[8]`과 EEPROM offset 4~19(16바이트) 레이아웃은 **그대로 유지**한다.
**앞 4워드에 측정값, 뒤 4워드는 0으로 채운다.** `EEPROM_UART.md`의 PC GUI 파싱을
건드리지 않기 위함이며, 0은 미사용임이 명확히 드러나는 값이다.

### 5. ADC 설정 복원

- `DM_HW_Drv_ADC_Init()`의 샘플링을 **384사이클**로 복원, 주석과 코드 일치
- `ADC_READ_TIME_US`(현재 14, 16사이클 기준) → **잠정 198**
  - 기존 14가 `(16 + 12) ÷ 2MHz`로 나온 값이므로, 같은 식으로 `(384 + 12) ÷ 2MHz = 198`
  - **이 상수는 ADC 1회 읽기마다 틱에 더해지고, 측정 1회당 20번 읽으므로 측정당 약 4ms다**
  - 레거시 실측값은 220이었으나 그것은 wfi/EOC 인터럽트 지연을 포함한 값이고, 현재는 폴링이다
  - **주석에 "잠정값 — 4단계 5분 대기 재측정에서 확정" 명시할 것**
- **폴링 루프에 타임아웃 추가** — 현재 무한 대기라 EOC가 안 뜨면 LED를 켠 채 Halt로
  복귀하지 못한다. 코인셀 제품이므로 안전 항목
  - 한도는 **루프 카운트**로, 정상 변환 시간(약 198µs)의 **10배 정도(약 2ms)**
  - 만료 시 `DM_App_Optic_Measure()`가 **LED 소등 + ADC 채널 해제 후 즉시 0을 반환**한다.
    샘플 일부만 0으로 두면 평균이 조금 낮아질 뿐 이상을 알아챌 수 없다
  - 반환된 0이 어떤 에러로 기록되는지는 **발생 지점에 따라 다르다**
    - 결과 스캔 중 → `ERROR_C_LINE_FAIL` (0 < 1050)
    - 초기 측정 중 → `ERROR_OPTIC_FAIL_CHx` (0 < 1500)
    - 스틱 확인 중 → `ERROR_STICK_REMOVE` (0 < 2600)
  - **세 경우 모두 에러 처리를 거쳐 Halt로 복귀**하므로 전력 보호 목적은 달성되나,
    에러 이름이 실제 원인(ADC 하드웨어 이상)과 다를 수 있다.
    **전용 에러 코드는 추가하지 않고 주석으로 남긴다**
- 죽은 코드 제거: `ADC1_COMP_IRQHandler`, `ADC_SetConvDone/GetConvDone/ClearConvDone`

## 어떻게 확인할 건가

중단점은 `DM_Main_Sq_App.c`의 `DM_App_Main_Sq_Stick_Insert_Step_Handler()` —
**`DM_App_Optic_CalcEmptyPTR()` 호출 직후(다음 줄)**.
그 줄에 찍고 F10으로 한 번 넘겨도 같다.

이 지점이어야 하는 이유: 초기측정·배율·적용후 **세 값이 모두 채워진 첫 자리**이므로
`gs_awInitialStickPtr` / `gs_wOptic_Gain` / `gs_awEmptyBand_LowData`를 한 화면에서 대조할 수 있다.
더 앞(`MeasureInitialStick()`의 `return`, `TuneTargetADC()`의 `return`)에서 멈추면
아직 채워지지 않은 배열이 0으로 보인다.

| 단계 | 확인 방법 | 합격 기준 |
|---|---|---|
| 빌드 | IarBuild Debug | 에러 0, 경고 0 |
| 코드 사이즈 | `.map` 하단 3줄 | Flash 8,192B 이내. TIM2·`Delay_us`·진단 루틴 제거분만큼 줄어야 정상 |
| 측정값 스케일 | 디버거 Watch로 `Measure()` 반환 확인 | **3,700 부근** (52,000이 나오면 평균 변경 실패) |
| 범위 판정 | 스틱 삽입 상태 초기 측정 | 4채널 모두 1,500~3,900 통과 |
| 배율 | 디버거 Watch | **약 41** (0.41) |
| 배율 적용 후 | 최종값 | **1,500 부근** |
| 폴링 타임아웃 | 코드 리뷰 | 무한 루프가 남아 있지 않을 것 |
| 범위 재검증 | 코드 리뷰 | `TuneTargetADC()` 앞에 1,500~3,900 재검증 분기가 있을 것 |
| 타임아웃 조기 반환 | 코드 리뷰 | LED 소등 + ADC 채널 해제 후 0 반환일 것 |
| 초기 버퍼 | 디버거 Watch `gs_awInitialStickPtr` | 앞 4개는 측정값, **뒤 4개는 0** |

여기까지 통과하면 `_DEBUG_LCD_SEQ_ONLY = 0`으로 4단계 전체 시퀀스 검증으로 넘어간다.

## 미리 적어두는 주의점

- **1,500~3,900은 배율을 곱하기 전 원본값 기준**이다. 곱한 뒤에는 전부 1,500 부근으로
  모여 범위 검사가 무의미해진다. 코드 주석에 명시할 것
- `Save_Result_To_Rom()`의 "PWM 값 4워드"가 **"배율 값 4워드"**가 된다.
  레이아웃·바이트 수는 그대로이므로 `EEPROM_UART.md` 문구만 갱신
- `CalculateIntensity()`는 제수가 약 6,553을 넘으면 내부에서 값이 잘린다.
  목표 1,500에서는 안전하나, 스케일을 키우는 변경을 할 때 반드시 재검토

### 채널 간 기울어짐 — 스틱 안착 문제로 판단

측정값이 앞에서 뒤로 갈수록 낮아졌다(3,653 → 3,468, **−5%**).
처음에는 LED 발열·전압 처짐을 의심했으나 **아니었다.**

근거: Empty 측정값을 배율로 역산하면 3,639 / 3,543 / 3,529 / 3,446이다.
발열이 누적된 것이라면 두 번째 측정 묶음은 처음부터 낮게 시작해야 하는데,
**채널 0이 다시 3,639로 올라갔다.** 즉 시간이 아니라 **채널 위치**에 묶인 현상이다.
두 묶음 사이의 차이는 0.5%로 작았고, 이것이 발열·전압 성분으로 보인다.

| 조건 | 앞→뒤 기울기 |
|---|---|
| 스틱 없음 (빈 챔버) | **−10%** |
| 스틱 정상 안착 (2026-09-23) | **−0.8%** |
| **오늘** | **−5%** |

스틱이 제대로 앉으면 흰 멤브레인이 반사를 지배해 앞뒤가 평탄해진다. 오늘 값은 그 중간이므로
**덜 들어갔거나 기울어 앉은 상태**로 판단된다. **유격 현상이 실측으로 잡힌 것이다.**

보조 근거: 중간 센서를 두 LED로 각각 읽는 BT(3,567)와 BC(3,549)의 차이는 **0.5%**다.
LED 개체차가 그 정도이므로, 앞뒤 5% 중 나머지는 위치 요인으로 볼 수 있다.

> **부수 발견** — 앞뒤 기울기가 **스틱 안착 품질의 지표**가 될 수 있다. 기울기가 크면
> 제대로 꽂히지 않았다는 신호다. 당장 쓰지는 않으나 기록해 둔다.

## 걸린 것 / 남은 것

### ① 광학 코드가 빌드에 들어가지 않았다

첫 빌드에서 Flash가 4,490 B로 나와 "1.2 KB 줄었다"고 판단했으나, `.map`의 MODULE SUMMARY를
확인하니 `DM_Optic_Handle_App.o`가 **12 B**였다. 광학 함수가 전부 링크에서 빠진 것이다.

원인은 `_DEBUG_LCD_SEQ_ONLY = 1`이 광학 경로를 우회하는데, 진단 루틴을 제거하면서
광학 함수를 참조하는 곳이 하나도 남지 않은 것. 링커가 미사용 함수를 버렸다.

→ **플래그를 0으로 전환**했다. 원 계획("1 유지")을 벗어나지만, 켜지 않으면 검증 자체가
불가능하다는 것이 확인되어 전제가 바뀌었다.

### ② 튜닝 함수의 스틱 확인이 절약분을 되쓰고 있었다

재측정을 피해 136 ms를 아끼기로 했는데, `TuneTargetADC()`가 채널마다
`Check_StickPresent()`(= 측정 1회, 약 34 ms)를 부르고 있어 정확히 그만큼을 되쓰고 있었다.

원본 주석에 근거가 명시돼 있었다 — *"채널당 최대 3초(P제어 5회 반복)라 그 사이 스틱이
빠질 수 있다."* **배율 방식에서는 채널당 수 µs이므로 그 전제가 사라진다.**
`MeasureInitialStick()`·`MeasureEmptyPTR()`의 스틱 확인은 실제 측정이 있으므로 그대로 두었다.

### ③ 검증 횟수가 부족하다

보드 확인을 2회만 했다. 기울어짐이 매번 달라지는지 확인하려면 반복이 더 필요하다.

### 남은 것 — 상급자 2차 피드백 (2026-09-28 오후)

기준서 1장 `추가 지시 (2026-09-28 오후)` 참조. 다음 작업 단위로 넘긴다.

1. Empty 측정 생략 → `초기측정 × 배율`로 계산
2. 목표값 1,200, 통과 기준 `목표 ± 25`
3. 배율 계산을 **반올림**으로 (정수 절삭 오차 때문에 ±20이 성립하지 않음)
4. 판정 2단계 (원본 범위 + 배율 적용값 범위)
5. **채널 간 회복 대기시간 스윕 시험** (10 / 200 / 500 / 700 / 1000 ms)

## 오늘의 교훈

**빌드 성공은 "문법이 맞다"까지만 증명한다.** Flash가 줄어든 것을 성과로 보고했으나
실제로는 모듈이 통째로 링크에서 빠진 결과였다. 크기를 논할 때는 `.map`의
**MODULE SUMMARY로 해당 모듈이 실제로 들어왔는지** 먼저 확인한다.

**측정값을 보고할 때는 가공 방식을 함께 말한다.** "3,700"이 단일값인지 합계인지 밝히지 않아
상급자와 한 차례 왕복이 생겼다. 숫자만으로는 스케일을 알 수 없다.

**한 가지 지표만 보고 바꾸자고 하지 않는다.** 배율 스케일을 100에서 1000으로 올리자고
제안했으나, 그 값이 이후 나눗셈에서 **약분되어 정밀도 이점이 없다는 것**과
`Cal_Ratio()` 재사용이라는 더 큰 이점을 놓칠 뻔했다. 제안 전에 그 값이 **어디서 어떻게
쓰이는지**부터 확인한다.

**기존 코드에 이유가 적혀 있는지부터 찾는다.** 스틱 확인을 "P제어 시절 잔재"라고 넘겨짚었으나,
원본 주석에 전임자가 근거를 명시해 두었다. 확인 결과 제거해도 되는 것이 맞았고,
**근거를 확보한 덕분에 판단이 단단해졌다.**

**문서가 둘이면 둘 다 고친다.** 결정 사항을 기준서에만 반영하고 착수문서를 빠뜨려,
에이전트가 낡은 지시를 읽는 일이 있었다. 기준서는 "왜", 착수문서는 "어떻게"로 역할이
나뉘어 있으므로 양쪽 모두 갱신해야 한다.

## 끝맺음 한 문장

배율 방식이 보드에서 실제로 동작하는 것을 확인했고, 그 과정에서 **스틱 유격이 채널 간
기울어짐으로 드러난다는 실측 근거**까지 함께 얻었다.
