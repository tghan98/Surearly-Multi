## 왜 다시 도나

1사이클은 **물방울이 안 뜨는 상태**에서 돌았다. 물방울은 "지금 시료를 넣으세요"를
알리는 유일한 신호라, 그것이 없으면 시료를 넣을 수 없고 사용자는 고장으로 알고
스틱을 뺀다. **정상 기기도 오동작으로 찍힌다.**

10-13에 원인이 밝혀졌다 — **핀 매핑 불일치.** 기판의 물방울은 PC4인데
신형 펌웨어는 PB0으로 보내고 있었다. (근거: 1사이클 문서의 12번 기기 절)

그 수정본으로 **1~13번을 처음부터 다시 돌린다.** 3·4번은 화면 이전 단계에서
막히므로 제외한다.

## 관찰 중인 것 — Step 5 / `STICK_FAIL` (2026-10-13 제기 → **당일 재현 확인**)

1번 기기에서 **물방울이 뜨고 깜빡인 뒤** 이 코드로 끝났다. 1사이클 전체를 통틀어
시료 투입까지 간 것은 5번 기기 한 번뿐이었으므로, 이 구간은 거의 처음 보는 것이다.

**Step 5는 `MAIN_SQ_LOW_SAMPLE_CHECK`(시료 부족 검사)인데, 코드는 `LOW_SAMPLE`이 아니라
`STICK_FAIL`이다.** 둘은 다른 자리에서 나온다.

```c
/* 20초 기다리는 동안 250ms마다 스틱 확인 */
if (DM_App_Main_Sq_Sleep_And_CheckStick_250ms(ERROR_STICK_FAIL, ...))
    return;                                   /* ← 여기서 끝났다 */

/* 20초 뒤 C 밴드를 재서 부족 판정 */
... Enter_Error(ERROR_LOW_SAMPLE, ...)        /* ← 여기까지 못 갔다 */
```

**시료 부족이 아니라, 20초 대기 중에 "스틱이 빠졌다"고 판단한 것이다.** 스틱은 꽂혀 있었다.

**가설 — 시료가 스틱 감지를 밀어낸다.**

스틱 감지는 **CH3(C 밴드) 원본값 ≥ `OPTIC_STICK_REMOVE_THRESHOLD`(2,600)** 로 한다.
그런데 시료가 퍼지면 C 밴드가 젖어 반사가 줄고 그 값이 떨어진다.

```
스틱 꽂힘 기준 : CH3 원본 ≥ 2,600
시료가 C에 닿음 : CH3 원본이 떨어진다
                   ↓
         "스틱이 빠졌다"로 오인
```

**같은 측정값을 두 가지 판단에 쓰고 있다** — 스틱이 있느냐, 시료가 왔느냐.
시료가 진행될수록 스틱 감지가 위태로워진다.

사실이면 **생산 검사오류의 유력한 후보**다. 멀쩡한 기기가 정상 시료에서도 오류를 낸다.

**확인 방법** — `g_DbgStickADC`를 20초 구간에서 보면 되지만, 디버거를 보려면 지그에
물려야 하고 그 상태로는 물에 적실 수 없다. **덤프로 재현 빈도를 먼저 센다.**

| 덤프에서 볼 것 | 뜻 |
|---|---|
| Step 5 / `STICK_FAIL` | 20초 대기 중 스틱 감지 실패 — 이 가설 |
| Step 5 / `LOW_SAMPLE` | 20초를 버티고 시료 부족으로 정상 판정 |

### 실측으로 확인했다 (2026-10-13 오후, 1번 기기 2.91V)

상급자 지적으로 방향을 바꿨다 — "문턱값보다 낮아서 생기는 거면 얼마로 낮춰야
통과할지를 생각해야 한다." 그러려면 `wADC`가 상태별로 얼마인지 알아야 한다.

**측정 방법** — `DM_Optic_Handle_App.c` 296행에 브레이크포인트, Watch에 `g_DbgStickADC`.
지그에 물린 상태에서도 **브레이크포인트에 걸려 있을 때 스틱을 빼서 적신 뒤 다시 꽂으면**
된다. MCU가 멈춰 있으므로 펌웨어는 아무 영향을 받지 않는다.
→ 그동안 막혔던 "지그에 물리면 적실 수 없다"는 제약이 여기서 풀렸다.

| 상태 | `wADC` (원본값) | 2,600 기준 |
|---|---|---|
| 빈 상태 (스틱 없음) | **1,402** | 아래 — 빠짐으로 판정 (정상) |
| 마른 스틱 | **3,688** (3,600대 안정) | 위 — 꽂힘으로 판정 (정상) |
| 스포이드로 적심 | 3,036 → 3,170 안정 | 위 — 통과 |
| **10초 담그기, 20초 경과** | **3,656** | 위 |
| **10초 담그기, 1분 경과** | **2,506** | **아래 — 빠졌다고 오판** |

**가설이 확인됐다.** 실제 시나리오대로 10초 담그면 CH3는 **1분 안에** 문턱값을
지나간다. 스틱은 내내 꽂혀 있었다.

스포이드로 적십을 때 3,170에서 멈췄던 것은 **액량 차이**다. 실제 시나리오와
다른 방법으로 적시면 결과가 바뀜다 — 앞으로 이 종류의 측정은 **반드시 10초 담그기**로 한다.

**덤프의 결과 밴드 C는 이번 건에 대해 아무것도 말해주지 않는다.**
`wMeasured_C`는 20초 대기가 끝난 뒤에야 재는데, 그 전에 에러로 빠졌기 때문이다.
덤프의 C 칸(1,185)은 빈 밴드 값 그대로다. → 패턴: **계측 사각지데**

### 곁달아 드러난 것 — 이중 스로틀링

20초 대기 루프는 250ms마다 `Sleep_And_CheckStick_250ms()`를 부르지만,
그 안은 `Check_StickPresent()`가 아니라 `DM_App_Stick_Get_Status()`를 부른다.
그리고 `Get_Status()`는 **25번 불릴 때까지 캐시를 돌려주고** 26번째에만 실측한다.

```c
#define OPTIC_STICK_CHECK_INTERVAL_COUNT (OPTIC_STICK_CHECK_INTERVAL_MS / LCD_TICK_10MS)
/* = 250 / 10 = 25 — "10ms마다 불릴 것"을 전제로 한 숫자 */
```

호출부가 이미 250ms를 자고 부르므로 실제 실측 간격은 **25 × 250ms = 6.25초**이다.
20초 동안 CH3를 진짜로 재는 횟수는 **약 3번**이다 (80번이 아니다).

> **이중 스로틀링** — 이미 간격을 두고 부르는 쪽을, 피호출자가 또 한 번
> 간격으로 깎는 것. 두 간격이 곱해진다.

### 문턱값이 원본값과 비교되는 것 자체의 문제

상급자 지적 — "배율을 구해놓고 왜 원본값과 비교하나."

맞는 지적이다. `Check_StickPresent()`의 호출처는 네 군데인데, 그중 세 군데는
배율이 계산되기 **전**에 불린다.

| 부르는 곳 | 시점 | 배율 |
|---|---|---|
| `DM_Main_Sq_App.c` 189행 | 스틱 꽂혀 깨어난 직후 | **0** |
| `DM_Optic_Handle_App.c` 181행 | 초기 4채널 측정 루프 안 | **0** |
| `DM_Optic_Handle_App.c` 197행 | 초기 측정 끝, EEPROM 쓰기 전 | **0** |
| `DM_LCD_Stick_Check_App.c` 236행 | 대기 루프 (`Get_Status` 경유) | 있음 |

`Cal_Ratio(x, 0)` = 0이므로 앞 세 군데에서 배율을 적용했다면 스틱이 꽂혀 있어도
무조건 "빠졌다"가 된다. 그래서 원본값을 쓸 수밖에 없었다.

> **암묵적 호출 순서 의존** — 같은 함수가 전제가 다른 두 시점에서 불리는데,
> 그 차이를 함수 자신은 모르는 것.

다만 9월 문서(`2026-09-28_stage4_배율방식_본코드반영.md` 110행)에 적힌 근거는
틀렸다. "배율을 적용하면 스틱 유무 구분이 사라진다"는 것은 **마른 스틱 상태의
4채널끼리**에만 해당한다. 한 채널의 상태별 변화는 배율을 적용해도 그대로 남는다
(1,180 / 802 / 449). 해당 문서에 보정 각주를 달았다.

**고칠 방향** — 함수를 둘로 나눈다. 배율 전용(원본값 비교)과 배율 후용(배율 적용 비교).
축을 바꾸면 문턱값도 같은 축으로 옮겨야 한다 (2,600 → 약 832).
그렇지 않으면 **단위·스케일 불일치**가 된다.

   아래쪽(449) 침범 = 스틱을 빼도 검사가 계속 돈다 ← 결국 다른 에러로 끝난다.
   위쪽이 더 아프니 중간보다 약간 아래가 안전하다.
2. **데이터가 1번 기기 하나뿐이다.** 젖은 최저 2회, 빈 상태 **1회**.
   2사이클을 돌면서 다른 기기에서도 확인해야 확정이다.
