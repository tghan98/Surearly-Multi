## 1. 무엇이 문제였나

### 패턴 이름: 순서 정보 분리

> 데이터는 저장되는데 그 순서를 알려주는 정보가 데이터 옆에 없고 딴 데 있어서,
> 읽는 쪽이 매번 맞춰봐야 하는 것.

결과 레코드는 7칸짜리 링버퍼다. 저장 자리는 이렇게 정해진다.

```c
bChannel = bIndex % RESULT_CHANNEL_MAX;   /* bIndex = 삽입횟수 - 1 */
```

삽입을 10번 한 기기의 덤프를 뽑으면 0번 칸부터 물리적 순서대로 찍힌다.

| 칸 | 담긴 것 |
|---|---|
| 0 | 8회차 |
| 1 | 9회차 |
| 2 | **10회차 ← 방금 뽑은 것** |
| 3~6 | 4~7회차 |

최신이 한가운데 박힌다. 명세 문서(`설계문서/Test_UI/EEPROM_UART.md`)에도
"슬롯 인덱스 자체는 시간순이 아니다"라고 적혀 있다.

## 2. 두 가지 방법과 선택

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A** | EEPROM에 위치 변수 1바이트 추가. 저장할 때마다 갱신 | 255 넘어가도 안전 | 같은 정보가 두 군데 — 어긋날 수 있음 |
| B | `InsertCount`에서 계산. 변수 추가 없음 | 중복 없음 | 255에서 리셋되어 최신 위치를 잘못 짚음 |

**A를 선택했다.** 이유는 세 가지다.

1. **읽는 사람이 바로 이해한다.** `Get_DumpPos()`는 "저장 위치를 읽는다"로 끝나지만,
   `(bCnt - 1) % 7`은 왜 1을 빼고 왜 7로 나누는지 아는 사람만 읽힌다.
2. **B의 이점이 EEPROM 1바이트 절약뿐이라** 상사 지시와 다르게 갈 근거가 못 된다.
3. **A는 실제로 저장된 칸을 가리킨다.** `InsertCount`는 스틱을 꽂는 순간 올라가지만
   레코드는 에러가 나거나 결과가 나올 때 저장된다. 둘은 어긋날 수 있다.
   (3번은 작업 도중에야 알아차린 이유다. 처음 A를 고를 때는 1·2번만 근거였다.)

안정성으로는 못 골랐다. A의 "두 번 쓰는 사이에 전원이 끊기는" 위험도,
B의 "255 도달" 위험도 둘 다 확률이 낮고 몇 번 측정하면 저절로 맞춰진다.

## 3. 코드 변경

### `USER/App/DM_Rom_Handl_App.c`

```c
#define ROM_OFFS_DUMP_POS   244 /**< Offset for latest result slot (1 Byte) */
```

현재 EEPROM은 0~243까지 사용 중이고 244~255가 비어 있다. 기존 맵은 건드리지 않았다.

함수 두 개를 기존 `InsertCount` 함수와 같은 모양으로 추가했다.

```c
uint8_t DM_App_Rom_Get_DumpPos(void);
void    DM_App_Rom_Set_DumpPos(uint8_t bPos);
```

그리고 `Save_CurrentResult()` 안에서 위치를 기록한다.

```c
    DM_HW_Drv_EEPROM_Write(wAddr, (uint8_t*)pBuffer, RESULT_DATA_SIZE);
    DM_App_Rom_Set_DumpPos(bChannel);              /* 추가 */
```

**호출처(442/749/781행)가 아니라 여기서 적는다.** 저장 위치를 계산하는 자리가
여기 하나뿐이라, 두 값이 어긋날 틈이 없기 때문이다.

> 참고 — 같은 식 `(cnt > 0) ? (cnt - 1) : 0`이 442·749·781행 세 군데에 복사돼 있다.
> 이번 변경과는 무관하지만 정리 대상이다. (**흩어진 계산**)

### `USER/App/DM_Main_Sq_App.c` — `Send_RawDump()`

```c
    bStart = DM_App_Rom_Get_DumpPos();
    for (i = 0; i < 7; i++)
    {
        bSlot = (uint8_t)((bStart + 7 - i) % 7);
```

최신 칸부터 거꾸로 돈다. **PC 툴(`multi.html`)은 손대지 않았다.** CSV 형식은

## 4. 구형 기기 대응 (되돌림 계산)

구형 펌웨어로 이미 결과를 쌓아둔 기기는 244번지가 비어 있다. 그 기기들은
새 펌웨어를 구워도 첫 덤프가 정렬되지 않는다.

그래서 `Get_DumpPos()`가 미기록일 때 삽입 횟수에서 역산하도록 했다.

```c
    if (bData >= RESULT_CHANNEL_MAX)
    {
        uint8_t bCnt = DM_App_Rom_Get_InsertCount();
        bData = (bCnt > 0) ? (uint8_t)((bCnt - 1) % RESULT_CHANNEL_MAX) : 0;
    }
```

### 알려진 결함 — 0을 구분하지 못한다

실제로는 이 되돌림이 **동작하지 않았다.**

10:50:33 덤프(5번 기기)는 정렬이 안 된 상태로 나왔다. 244번지에서 읽힌 값이
`0x00`이었고, `>= 7` 검사에 안 걸려 "0번 칸이 최신"으로 그냥 통과했기 때문이다.

| 0의 뜻 | |
|---|---|
| "0번 칸이 최신이다" | 진짜 정보 |
| "아직 안 적었다" | 빈 상태 |

**이 둘을 구분하지 못한다.** 고치려면 저장한 칸 번호에 1을 더해서 적으면 된다
(0번 칸 → 1, 3번 칸 → 4). 그러면 0이 "빈 상태" 하나만 뜻하게 된다.

새 기기에 처음 구울 때 같은 문제가 또 나므로 **고쳐둘 것.**

## 6. 사용상 주의

- **앞으로는 1번 줄만 보면 된다.** 칸 번호는 더 이상 따질 필요가 없다.
- CSV 첫 열의 숫자는 이제 **칸 번호가 아니라 최신순 순번**이다. 의미가 바뀌었다.
- `cycle2_20261013` 폴더 등 **이전에 뽑아둔 CSV는 옛날 규칙**이다. 거기서는
  첫 열이 칸 번호다. 섞어 볼 때 주의할 것.
- 레코드는 에러가 나거나 결과가 나올 때만 저장된다. **중간에 덤프를 뽑으면
  이번 run은 아직 저장 전이라 직전 run의 값을 보게 된다.**
